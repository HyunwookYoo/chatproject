iOS

  • iOS는 임의 코드의 백그라운드 상시 실행을 허용하지 않는다. 앱이 suspend되면 소켓이 끊긴다. 상시 소켓은 내비게이션·오디오 재생 등 특정 카테고리에만 허용된다.
  • PushKit(VoIP push) 우회 불가: iOS 13부터 VoIP 푸시를 받으면 반드시 CallKit에 통화를 보고해야 하며, 안 하면 앱이 강제 종료되고 반복되면 푸시 전달 자체가 중단된다. 과거 메신저들이 쓰던 이 우회로는 막혔다.

  • 2026년 기준 동적 전력 예산 정책으로, 잦은 wake나 지속 연결은 "excessive"로 플래그된다.
  • ⇒ iOS에서 백그라운드 메시지 수신은 APNs를 반드시 거쳐야 한다. 그리고 APNs로 푸시를 쏘려면 당신의 APNs 인증키를 가진 송신 주체가 필요하다 — 그게 곧 서버다. (인증키를 앱에 넣는 건 보안상 불가능. 디바이스 토큰도 상대가 알 수 없다.)

VPN 익스텐션은 Apple 개별 승인이 필요 없다. com.apple.developer.networking.networkextension 의 packet-tunnel-provider 값은 2016년 11월 정책 변경 이후 일반 개발자가 그냥 쓸 수 있다. 앱 익스텐션으로 백그라운드 상시 실행되고 소켓이 유지되며, on-demand 룰로 항상 켜둘 수 있고, 익스텐션에서 로컬 알림도 띄울 수 있다.

성립하는 아키텍처: VPN 익스텐션이 피어와의 QUIC 연결 유지 → 메시지 도착 시 암호문 보관 + 로컬 알림 → 앱 실행 시 본체가 처리. 서버 0대로 iOS 백그라운드 수신이 실제로 성립한다.

  • 사용자가 VPN 프로파일 설치를 승인해야 한다. 채팅앱이 VPN 권한을 요구하는 것은 신뢰 측면에서 큰 마찰이다.

  • 배터리 소모, 시스템 재량 종료.
  • App Store 정식 배포 불가 — 가이드라인 5.4는 VPN 앱을 Organization 계정으로 한정하며 VPN이 앱의 실제 목적일 것을 요구한다. 채팅앱의 VPN 익스텐션 사용은 리젝 사유다.

순수 P2P는 양쪽이 동시에 온라인일 때만 전달된다. "메시지 보냈는데 상대가 자고 있으면 못 받는다"는 UX가 된다. 저장-전달(store-and-forward)이 필요하면 무언가는 항상 떠 있어야 한다.

벽 셋(iOS · Android · 오프라인)이 다 드러났다 — 이제 요구사항 #2를 어떻게 읽을지가 남는다

나갈 때L1(최소 인프라)을 기본, L2(익명 큐)를 옵션으로 권장. 그리고 "iOS를 지원하면서 인프라 0대"는 기술이 아니라 제품 결정이라고 못박는다

3.4 현실적인 스펙트럼 — 요구사항 #2를 지키면서 고를 수 있는 것

원문 산문 펼치기 · 81자 · 문단 1

요구사항 #2("기록은 당사자만 보유")를 "서버가 평문과 메타데이터에 접근할 수 없다"로 해석하면, 서버가 존재해도 요구사항은 지켜진다.

레벨인프라오프라인 전달iOS요구사항 #2

권장: L1에서 시작하고 L2를 옵션으로 설계한다.

  • 릴레이는 E2EE 암호문만 통과시키고 평문을 못 본다 (iroh 릴레이도 동일한 성질).

  • 이 구조면 "채팅 기록은 당사자만 보유"가 실제로 지켜진다.

3.5 요구사항 #1과 #2의 충돌 — 명시적으로 짚어야 할 지점

iOS를 지원하면서 인프라 0대를 유지하는 것은 불가능하다. 둘 중 하나를 골라야 한다.

  • (A) iOS 포기 → Windows + Android만. L0 순수 P2P 가능. Briar가 택한 길.
  • (B) 최소 인프라 수용 → 3개 플랫폼 전부. 요구사항 #2는 "서버가 평문 못 봄"으로 재정의.

이건 기술로 풀 수 있는 문제가 아니라 제품 결정이다.

두 질문이 닫혔다. 세 번째 질문은 아직 붙이지 않은 것에 관한 것이다

원칙: 블록체인을 메시지 경로에 두지 말 것.

원문 산문 펼치기 · 165자 · 문단 1

온체인 메시지 저장은 요구사항 #2와 정면 충돌한다 — 영구 보존·공개·삭제 불가이며, forward secrecy를 원천적으로 파괴한다. 비용과 지연(초~분)도 채팅에 맞지 않다. 업계 표준 사례인 XMTP도 메시지는 오프체인에 두고, 온체인에는 아이덴티티와 MLS 그룹 커밋만 올린다.

4.1 지금 정해야 하는 것 (나중에 바꾸면 비싼 것)

원문 산문 펼치기 · 1,086자 · 문단 4 · 목록 4

a. 키 아키텍처 — 가장 중요

  • 채팅 아이덴티티 키와 지갑 키를 분리하되, 서명으로 바인딩 가능하게 설계한다 (XMTP 방식: 지갑 서명으로 installation key를 인가).
  • 곡선 선택이 나중을 좌우한다: 채팅 측은 Ed25519/X25519 (iroh의 EndpointID도 ed25519 공개키), EVM 측은 secp256k1. 둘을 억지로 통일하지 말고 바인딩 레이어를 처음부터 둔다.
  • 원칙: PeerID = 공개키. 이 구조면 나중에 온체인 레지스트리를 얹는 게 자연스럽다.

b. 주소 해석(resolver)을 플러그인화

  • PeerID → 주소를 해석하는 지점을 인터페이스로 추상화한다.
  • 지금: DHT / QR 티켓 / mDNS. 나중: ENS류 온체인 네임 레지스트리를 추가만 하면 되게.
  • 이걸 안 해두면 나중에 네트워크 코드 전반을 뜯어야 한다.

c. 그룹 암호는 MLS(RFC 9420) 고려

  • Signal Double Ratchet은 1:1 설계다. 100명 그룹에서 멤버 변경 시 99회 재배포가 필요하다.
  • MLS는 TreeKEM으로 O(log N). 2026년 5월 Google Messages와 Apple Messages가 RCS에 MLS E2EE 롤아웃을 시작했고, Discord도 음성/영상 E2EE에 MLS를 쓴다.
  • XMTP는 MLS를 쓰고 그룹 커밋만 온체인 계약(GroupMessages)에 기록한다 — 온체인 멤버십을 원한다면 이 경로가 정석이다.
  • Rust openmls(참조 구현) + Dart 바인딩 openmls 2.0.1(flutter_rust_bridge 기반, Android/iOS/macOS/Linux/Windows/WASM 지원)이 이미 존재한다. 단 likes 5, 신생이므로 성숙도는 낮다.
  • 1:1만 할 거면 Double Ratchet이 더 단순하다. 그룹 계획이 있으면 처음부터 MLS로 가는 편이 싸다.

d. 로컬 해시체인

  • 메시지에 로컬 해시 체인을 걸어두면, 나중에 앵커링(타임스탬프 증명) 만 온체인으로 올릴 수 있다. 메시지 자체는 계속 로컬에 남는다.
  • 초기 비용 거의 0, 나중 옵션 가치 큼.

  1. 양쪽 모두 상시 기기가 없다 — 폰만 쓰는 사용자끼리 접속 시간대가 안 겹치면 메시지가 며칠 지연된다

9.1 큐 모델

원문 산문 펼치기 · 196자 · 목록 1
  • 큐는 단방향이다. A↔B 대화에는 큐 2개가 존재한다
  • 큐 ID는 32바이트 랜덤. 아이덴티티에서 파생하지 않는다

    • senderKey — 큐에 넣을 권한. 송신자만 개인키를 안다
    • recipientKey — 큐에서 뺄 권한. 수신자만 개인키를 안다
  • 릴레이는 두 공개키와 큐 ID만 안다

9.2 명령

CREATE  { recipient_pub, sender_pub, ttl_secs }   → { queue_id }   sig: recipient
SEND    { queue_id, ciphertext, ts }              → { ok }         sig: sender
RECV    { queue_id, since_seq, max }              → [ {seq, ct, ts} ]  sig: recipient
ACK     { queue_id, upto_seq }                    → { ok }         sig: recipient → 즉시 삭제
SUB     { queue_id }                              → 스트림          sig: recipient
DELETE  { queue_id }                              → { ok }         sig: recipient
COMMIT_APPEND { group_queue_id, commit_ct }       → { seq }        (6.1절)

확장 — 원문이 멈춘 자리

무엇을 — Signal Double Ratchet. 1:1 전용 래칫 프로토콜이고 MLS의 대안이다.

왜 여기서 갈라지는가 — 타당성 문서가 "1:1만 할 거면 Double Ratchet이 더 단순하다. 그룹 계획이 있으면 처음부터 MLS로 가는 편이 싸다"고 이름을 대고 기각한 뒤, 설계 문서는 §1 결정 표에서 MLS로 확정하고 Double Ratchet을 다시 다루지 않는다. 원문이 그은 경계가 바로 이 한 줄이다.

어디부터 보면 되는가 — c1-s12(Q3 — 지금 정해야 하는 것)가 이 기각을 적은 자리이고, c2-s9(MLS 커밋 순서 문제)가 그 선택의 비용(전역 순서 요구)을 처음 치르는 자리다. Double Ratchet이었다면 이 스텝 자체가 존재하지 않았을 것으로 보인다 — 커밋이라는 개념이 없기 때문이다.

무엇을 — SimpleX의 SMP(Simple Messaging Protocol) 원본. 큐 릴레이 설계가 참고했다는 그 프로토콜.

왜 여기서 갈라지는가 — 설계 §9가 "SimpleX의 SMP를 참고하되 단순화한다"고만 적고 원본이 무엇을 더 갖고 있는지는 말하지 않는다. 타당성 §3.4의 L2도 "SimpleX형"이라고 이름만 댄다. 즉 무엇을 덜어냈는지가 두 문서 어디에도 없다.

어디부터 보면 되는가 — c2-s16(큐 모델과 명령 일곱)의 명령 표가 단순화의 결과물이다. 원본과 대조하려면 SimpleX 문서를 따로 봐야 한다 — 이 두 문서에는 대조할 원본이 실려 있지 않다.

원문 인용 — 타당성 §3.1: "IPFS/libp2p DCUtR 기준 4.4백만 회 시도, 85,000+ 네트워크, 167개국에서 홀펀칭 성공률 70% ± 7.1%" / "iroh는 릴레이 폴백까지 포함해 ~90–95% 연결 성공을 주장하며".

무엇이 조건부인가 — 두 숫자가 서로 다른 것을 재고 있다. 70%는 릴레이 없는 순수 홀펀칭의 제3자 대규모 측정치이고, 90–95%는 릴레이 폴백을 포함한 벤더 자기 주장이다. 원문도 "주장하며"라고 적어 출처의 성격을 구분해 두었다. 그런데 설계 §1의 결정 표는 전송 선택 근거로 후자만 인용한다 — 구성 P의 릴레이가 뭄바이(~146 ms)라는 사실과 겹쳐 읽으면, "90–95% 성공"의 상당 부분이 실제로는 느린 경로일 가능성이 있다. 몇 %가 그런지는 두 문서 어디에도 없다.

근거 — c1-s7이 두 숫자를 나란히 적은 자리이고, c2-s1이 그중 하나만 골라 결정 표에 옮긴 자리다.

원문 인용 — 설계 §2.1 표: 구성 P의 "운영 부담 = 거의 0 (무료 티어)". §8.2: "프록시 키만 갖고 있으면 되므로 Cloudflare Workers 무료 티어로 충분하다".

무엇이 조건부인가 — "충분하다"의 전제인 요청 수 한도 · 동시 사용자 수가 원문 어디에도 없다. 그리고 같은 문서 §17의 리스크 7이 "그룹 규모 상한 미정 — 푸시 팬아웃 비용 확인 필요"라고 적는다. 즉 "거의 0"은 팬아웃 비용을 확인하기 전에 쓰인 값이다. 50명 그룹에서 한 통이 최대 50회 푸시가 되고(§17이 초기 상한으로 든 숫자), 그것이 무료 티어 안에 들어가는지는 판단할 근거가 문서에 없다.

근거 — c2-s2의 운영 부담 행과 c2-s27의 리스크 7이 같은 문서 안에서 서로를 지목하지 않은 채 남아 있다.

명령 — 설계 §8.3의 4 KB 상한과 §7.1의 패딩 버킷(1K / 4K / 16K / 64K)을 나란히 놓고 계산한다. 암호문은 "e" 필드에 base64로 들어가므로 4/3배로 부푼다. 4096바이트에서 aps 객체(mutable-content + alert.loc-key) 오버헤드 약 60~80바이트를 뺀 뒤 3/4을 곱한다.

기대 결과 — 실을 수 있는 원시 암호문은 대략 3.0 KB 안팎. 즉 1K 버킷은 확실히 들어가고, 4K 버킷은 들어가지 않는다.

무엇을 확인하는가 — §8.3은 "짧은 텍스트는 충분히 들어간다"고만 하고 어느 패딩 버킷까지인지는 말하지 않는다. 위 계산이 맞다면 §7.1의 두 번째 버킷부터는 항상 "새 메시지"로만 뜬다는 뜻이고, 그것은 §2.2가 구성 R 승격 조건 2번으로 적은 바로 그 상황이다. 계산 결과는 c2-s11(봉투와 페이로드)의 버킷 정의와 c2-s15의 4 KB 서술 사이의 빈칸을 메운다.

명령 — PowerShell에서 Test-NetConnection 5.223.48.185 -Port 443(iroh 뭄바이 릴레이)와 Test-NetConnection 162.159.207.0 -Port 3478(Cloudflare STUN)을 각각 세 번 돌려 최솟값을 본다.

기대 결과 — 타당성 §1.5가 적은 72.8 ms와 15.4 ms 근방. 크게 벗어나면 이 문서의 릴레이 판정(뭄바이 왕복 ~146 ms)이 지금 회선에서는 성립하지 않는다는 뜻이다.

무엇을 확인하는가 — §1.1이 스스로 "NAT/네트워크 측정은 이 회선 1개, 특정 시점 결과다"라고 못박은 그 제약이 아직 유효한지. c1-s4의 표가 구성 R 승격 조건 4번(릴레이 폴백 지연)의 유일한 근거이므로, 이 숫자가 바뀌면 승격 판단도 바뀐다.

질문 — iOS NSE의 메모리 예산 안에 OpenMLS 그룹 상태가 들어가는가?

왜 아직 모르는가 — 원문 스스로 미확정으로 남겼다. 설계 §12.3이 "⚠️ 구현 전 실측 필요: NSE 메모리 상한과 OpenMLS 그룹 상태 로드가 그 안에 들어가는지. 큰 그룹에서 문제가 될 수 있다"고 적고, §17의 리스크 1이 같은 항목을 "영향: 큰 그룹 iOS 알림 실패"로 다시 올린다.

답을 찾을 방법 — 원문이 방법과 시점을 함께 적어 두었다: 실패 시 폴백은 "새 메시지"만 표시하는 것이고, 실측 시점은 §18의 구현 순서 7번(푸시 — Android UnifiedPush → iOS 프록시 + NSE)이다. 그 자리는 c2-s28(구현 순서)이고, 위험의 근원은 c2-s21(NSE와 코어 공유)이다.

질문 — 동반기기(상시 켜둔 PC)가 없는 사용자의 비율은 얼마인가?

왜 아직 모르는가 — 설계 §17의 리스크 2가 이 항목의 "영향"을 "구성 P의 실효성 전체"라고 적는다. §3.4도 "상시 기기가 없는 사용자에게는 아무 도움이 안 된다"고 한계를 인정하고, §2.2가 이것을 승격 조건 1번으로 올렸다. 그런데 그 비율을 추정할 근거는 두 문서 어디에도 없다 — 원문이 스스로 미측정으로 남긴 값이다.

답을 찾을 방법 — 원문이 방법을 명시했다: "초기 사용자에게 측정. 높으면 즉시 R로 승격." 측정 대상 자체는 c2-s5(동반기기의 한계)가 정의하고, 그 판정이 뒤집는 것은 c2-s2(두 구성)의 기본값이다.

Q11.2절 측정 결과를 종합했을 때 이 회선의 NAT 유형은?

매핑은 Endpoint-Independent(응답한 5개 STUN 서버 모두 같은 203.0.113.10:62787)인데 필터링은 Address-and-Port-Dependent(CHANGE-REQUEST 무응답)다. 원문이 이 둘을 묶어 "종합: Port-Restricted Cone NAT"으로 판정한다. 매핑만 보고 Full Cone으로, 필터링만 보고 Symmetric으로 읽으면 갈린다.

Q2DataChannel RTT 64B(로컬, n=200)의 p50은?

표의 네 숫자가 각각 다른 것을 잰다 — 0.077 ms는 min, 0.142 ms가 p50, 5.4 ms는 DataChannel 오픈(ICE+DTLS+SCTP 전체), 47 ms는 ICE 게더링 완료다. 원문이 "스택 자체의 오버헤드는 0.15ms 수준"이라 요약할 때 근거로 삼은 값이 p50이다.

Q3한국에서 가장 가까운 iroh 공개 릴레이는?

가장 가까울 법한 apne1-1(아시아-북동)은 DNS 자체가 없다 — 존재하지 않는다. Tailscale DERP는 iroh 릴레이가 아니라 다른 인프라다. 그래서 한국에서 가장 가까운 iroh 공개 릴레이는 뭄바이 72.8 ms가 되고, 이것이 릴레이 폴백 왕복 ~146 ms의 근거다.

Q41.6절 실측에서 Tauri가 Flutter보다 유리하게 나오지 않은 항목은?

Tauri가 앞선 것은 NSIS 1.83 MB(대 26.5 MB) · 스레드 43개(대 149개) · 창 표시 69 ms(대 328 ms)다. 실행 시 RSS만 Flutter가 83.1 MB로 Tauri 348.2 MB를 크게 앞선다. 다만 원문은 창 표시 69 ms가 "첫 화면이 보인 시각"이 아니라고 따로 못박는다.

Q52.1절 후보 평가표에서 Tauri v2의 판정 사유는?

표의 판정 열은 후보마다 다르다 — "Windows가 약점"은 Compose Multiplatform(KMP)과 React Native, "iOS/Android 생태계 약함"은 .NET MAUI, "Kotlin/Native FFI 번거로움"은 KMP의 연동 칸이다. Tauri v2의 판정은 모바일 리스크이고, 근거는 모바일이 "stable API지만 first-class 아님"이라는 공식 입장이다.

Q6대규모 실측(IPFS/libp2p DCUtR)이 보고한 홀펀칭 성공률은?

같은 절에 숫자가 넷 있고 각각 다른 것을 말한다. 70% ± 7.1%가 4.4백만 회 시도의 실측 성공률이고, 90–95%는 릴레이 폴백까지 포함한 iroh의 주장, 97.6%는 성공한 연결 중 첫 시도에 성립한 비율, ~30%는 70%의 나머지(실패율)다. 이 구분은 재점검 항목에서 다시 다룬다.

Q7iOS 13부터 PushKit(VoIP push)을 우회로로 쓸 수 없게 된 이유는?

오답 셋은 모두 다른 경로의 제약이다 — 엔타이틀먼트 승인은 NEAppPushProvider, 시간당 1–2회는 background push, 50 MB 리밋은 NEPacketTunnelProvider의 것이다. PushKit이 막힌 이유는 CallKit 보고 의무이고, 원문은 이것을 "과거 메신저들이 쓰던 이 우회로는 막혔다"고 적는다.

Q8NEPacketTunnelProvider(VPN 익스텐션)의 메모리 하드 리밋은? (iOS 15+)

50 MB다. 15 MB는 iOS 14 이하의 값으로 같은 문단에 함께 적혀 있어 헷갈리기 쉽다. 초과하면 jetsam이 per-process-limit으로 즉시 종료하므로, MLS 그룹 상태와 암호문 버퍼가 이 예산 안에 들어가야 한다.

Q93.4절 스펙트럼에서 L1(최소 인프라)이 운영하는 것은?

표의 네 행이 각각 다른 레벨이다 — 0대는 L0, 암호문 큐 릴레이는 L2(SimpleX형), 중앙 서버는 L3다. L1만 유일하게 오프라인 전달이 "⚠️ 제한적"이면서 iOS가 "✅ 가능"인 조합이고, 원문의 권고가 바로 이 L1에서 시작하는 것이다.

Q10XMTP가 온체인에 올리는 것은? (원문이 업계 표준 사례로 든 것)

원문은 "XMTP도 메시지는 오프체인에 두고, 온체인에는 아이덴티티와 MLS 그룹 커밋만 올린다"고 적는다. 메시지·암호문을 올리는 것은 요구사항 #2와 정면 충돌하고 forward secrecy를 파괴하며, 연락처 목록은 4.3절이 부적합 열에 명시적으로 넣은 항목이다.

Q11구성 P에서 MLS 커밋 순서를 정하는 방식은?

2.1절 비교표의 "MLS 커밋 순서" 행이 두 구성을 정확히 갈라 적는다 — 구성 P는 지정 커미터(propose/commit 분리), 구성 R은 릴레이 시퀀서. 온체인 컨트랙트는 13.3절이 "나중"으로 남긴 확장 훅이고, UnifiedPush는 같은 표의 Android 푸시 행이다.

Q12꺼져 있던 A의 폰이 나중에 켜졌을 때, PC가 보관하던 메시지를 폰이 복호할 수 있는 이유는?

PC는 MLS 암호문을 그대로 재전송할 뿐 평문을 다시 만들지 않는다 — 폰이 같은 epoch 비밀을 가진 멤버이므로 그대로 복호된다. 릴레이 재전송은 구성 R의 방식이라 구성 P에는 큐가 없고, 키 복사는 4.2절의 "다단말은 MLS installation으로 표현한다"는 원칙과 정면으로 어긋난다.

Q13키 계층에서 WalletKey(secp256k1)를 다루는 방식은?

키 계층 그림에서 WalletKey만 DeviceSeed 아래 어디에도 연결되어 있지 않고, 원문이 그 옆에 "절대 위 계층에서 파생하지 않는다"고 적는다. 4.2절 원칙 3도 "지갑 키를 절대 파생하지 않는다. 서명 바인딩만"이라고 다시 못박는다 — 파생하면 채팅 키가 새는 순간 지갑도 같이 샌다.

Q14구성 P에서 지정 커미터가 오프라인이면 무엇이 지연되는가?

핵심은 "애플리케이션 메시지는 커밋이 아니다"라는 한 줄이다 — 누구나 언제든 보낼 수 있고 순서 문제가 없으므로 커미터가 오프라인이어도 대화는 정상 동작한다. 부재의 영향은 멤버 변경과 키 갱신 지연뿐이고 원문은 그 둘을 "드문 이벤트"라고 덧붙인다.

Q15stateless 푸시 프록시가 아는 것은?

PushHandle이 프록시 키로 AEAD 암호화된 불투명 문자열이라, 프록시는 그것을 복호해 토큰을 얻고 APNs로 넘긴 뒤 아무것도 저장하지 않는다. 원문이 "프록시가 아는 것: '이 토큰에 푸시가 갔다'뿐이다. 송신자가 누구인지, 내용이 무엇인지, 어떤 대화인지 모른다"고 세 오답을 그대로 부정해 둔다.

Q16상시 기기가 outbox 백오프 상한을 30초로 짧게 유지하는 이유는?

일반 백오프는 1s, 2s, 4s … 최대 5분인데, 원문은 "상시 기기는 백오프 상한을 30초로 짧게 유지한다 — 배터리 제약이 없으므로"라고 이유까지 붙여 적는다. TTL 24시간(9.3절) · 4 KB(8.3절)는 다른 절의 사실이고, epoch 만료로 인한 제약은 이 절에 없다.

Q17타당성 문서의 논증이 진행된 순서대로 배열하시오.

이 문서의 축은 요구를 세우고 → 재고 → 뚫리는지 보고 → 막히는 층을 찾고 → 요구를 다시 읽는 순서다. 요구사항(§0)이 먼저 서야 무엇을 잴지 정해지고, 회선 측정(§1.1–1.2)이 있어야 네트워크 계층 판정(§3.1)이 가능하며, 그것이 뚫린 뒤에야 OS 계층(§3.2)이 진짜 벽으로 드러난다. 재해석(§3.4–3.5)은 그 벽을 확인한 다음에만 정당하다 — 순서를 바꾸면 각 절의 전제가 무너진다.

Q181절 실측이 측정한 대상을 좁은 것에서 넓은 것 순으로 — 원문이 실제로 밟은 순서대로 배열하시오.

실측은 회선 → 스택 → 인프라 → 앱 순으로 좁은 데서 넓은 데로 나아간다. NAT를 먼저 알아야 홀펀칭 가능성이 판정되고, 스택 오버헤드가 무시 가능함을 확인해야 "지연은 경로에서 온다"는 결론이 서며, 그 결론이 있어야 릴레이 인프라를 재는 것이 의미를 갖는다. 프레임워크는 이 모든 네트워크 판단과 독립이라 마지막이다.

Q19설계 문서가 축을 세우고 첫 해법에 도달하는 순서대로 배열하시오.

결정 표(§1)에서 단 한 줄만 값이 아니라 축이었고(서버 의존도), 그 축이 구성 P/R(§2.1–2.3)로 펼쳐진 다음에야 경로 1~5(§2.5)를 그릴 수 있다. 동반기기(§3)는 그 경로 중 3번을 실제로 구현하는 것이므로 경로 정의보다 뒤에 온다 — 반대로 놓으면 "무엇의 3번인가"가 정의되지 않는다.

Q20B의 한 통이 실제로 만들어져 나가기까지, 설계가 계층을 쌓은 순서대로 배열하시오.

소유·의존의 층이 이 순서다. PeerId = 공개키(§4)가 없으면 dial 대상 자체가 정의되지 않고, 전송 경로(§5)가 없으면 MLS 핸드셰이크를 주고받을 수 없으며, 그룹 epoch(§6)가 서야 Envelope.payload에 담을 MLS PrivateMessage(§7.1)가 존재한다. 메시지 포맷이 가장 위에 오는 것은 그것이 아래 셋을 전부 전제하기 때문이다.
