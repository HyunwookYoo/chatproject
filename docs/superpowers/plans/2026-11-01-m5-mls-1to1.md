# M5 MLS 1:1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 1:1 대화의 텍스트와 읽음 receipt를 MLS `PrivateMessage`로 종단간 암호화하고, 지연·중복·순서 뒤바뀜·복호 실패·기기 변경·M4 혼합 버전에서도 기록을 잃지 않고 수렴하게 한다.

**Architecture:** 새 `chat_core::mls` 모듈이 OpenMLS 0.9를 감싼다. 그룹 상태는 대화별 범위로 SQLCipher `mls_kv` 표에 바이너리로 저장하고, 각 작업마다 메모리 KV로 읽어 들여 OpenMLS를 실행한 뒤 바뀐 행만 같은 SQL 트랜잭션에 쓴다. 이렇게 해서 MLS 상태와 `message`/`outbox`/`processed_ct`가 함께 커밋된다. 기존 account actor와 단일 storage writer, M3 인증 연결은 그대로 쓰고, MLS 제어(그룹 질의·합류·KeyPackage·Welcome·Commit·암호문·복호 실패)는 인증 연결의 새 frame kind 17로 보낸다.

**Tech Stack:** Rust 1.92.0, openmls =0.9.0, openmls_traits·openmls_memory_storage·openmls_rust_crypto =0.6.0, 기존 rusqlite =0.40.2 / libsqlite3-sys =0.38.2 (SQLCipher 4.14), minicbor, sha2, zeroize, ed25519-dalek, iroh 1.3, UniFFI 0.32.2, FRB 2.11.1, Flutter 3.44.6.

**Spec:** [승인된 M5 설계](../specs/2026-11-01-m5-mls-1to1-design.md). 구현자는 spec과 이 계획을 모두 읽는다. 사용자는 2026-11-01 spec을 승인했다. **실행 방식과 이 계획의 검토는 아직 미확정이다.**

## Global Constraints

- 새 메시지는 **MLS로만** 보낸다. codec 1(M4 평문) 송신 경로를 만들지 않는다. 실패 시 M4로 내려가지 않는다.
- 전환 기간: M4 상대의 codec 1 Text와 업데이트 전 메시지의 M4 Receipt/ReceiptApplied는 **계속 받는다**.
- MLS 파라미터: 사이퍼수트 `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, `max_past_epochs = 5`, `SenderRatchetConfiguration::new(200, 1000)`(out_of_order_tolerance 200, maximum_forward_distance 1000). proposal은 그룹에 보내지 않고 by-value Commit만 쓴다.
- 패딩 버킷: 1 KiB / 푸시 버킷(완성 암호문 ≤ 2,900 B) / 16 KiB / 60 KiB. 완성된 frame은 M4 상한 61,440 B를 넘지 않는다.
- MLS 저장값은 바이너리. **JSON 금지**(`serde_json`을 `mls_kv` 값에 쓰지 않는다).
- 메시지 하나를 처리하는 단위 = SQL 트랜잭션 하나. MLS 상태 변화와 `message`/`outbox`/`processed_ct`/`receipt_job` 변화가 함께 커밋되거나 함께 롤백된다.
- 일반 재시도는 같은 암호문을 다시 보낸다. 다시 암호화하는 경우는 복호 실패 응답과 그룹 교체·재가입뿐이다.
- 받는 쪽 화면에 복호 실패를 띄우지 않는다. 상대 기기 변경을 대화에 표시하지 않는다. 새 사용자 문구를 추가하지 않는다(spec §3의 "개발 상태 안내"는 앱에 해당 문구가 없으므로 바꿀 것이 없다).
- 기존 M4 규칙 유지: 단일 writer(`chat-storage-writer`), outbox 무기한 보관(10,000건 / 128 MiB 상한), 텍스트 16 KiB, page 50, 기기 최대 5대, 계정 lifecycle 펜스.
- 키·평문·그룹 상태·본문을 로그·오류 detail·제어 wire에 남기지 않는다.
- 버전 고정: Rust 1.92.0, FRB 2.11.1, UniFFI 0.32.2, libc 0.2.189, 기존 pin 유지. 새 의존성은 `=` 고정, `Cargo.lock`은 필요한 항목만 바뀐다.
- 작업 root는 실행 시 `superpowers:using-git-worktrees`로 만든 격리 worktree(브랜치 `m5-mls-1to1`에서 분기). `git add .` 금지, 경로를 지정해 커밋한다. push·merge·서명·업로드·실기기 설치는 이 계획의 자동 범위가 아니다.

## Review Focus

1. **복호와 저장 사이에서 프로세스가 죽는 경우:** MLS ratchet만 앞으로 가고 메시지가 없는 상태가 남으면 그 메시지는 영원히 못 푼다. 둘 다 롤백돼야 한다. — Task 6의 `crash_between_open_and_store_rolls_back_both`.
2. **오래 대기한 메시지의 epoch가 5개 넘게 지난 경우:** 같은 암호문 재전송은 계속 실패한다. 복호 실패 응답 → 한 번만 재암호화 → 전달로 수렴해야 한다. — Task 8의 `stale_epoch_retry_reencrypts_once`.
3. **재암호화 재전송이 두 번 표시되는 경우:** 같은 `msg_id`, 다른 암호문. 받는 쪽은 한 행만 가져야 한다. — Task 6의 `reencrypted_resend_stores_once`.
4. **해제된 기기로 가는 Commit/Welcome 전달 작업이 남는 경우:** 무한 재시도하지 말고 Remove 확정 시 버린다. — Task 7의 `removed_device_delivery_dropped`.
5. **악의적이거나 거대한 MLS 입력:** 큰 Welcome/KeyPackage/credential, 범위 밖 길이 필드는 파싱 전에 거부하고 상태를 바꾸지 않는다. — Task 5의 `oversized_mls_frames_rejected_before_parse`.

## 2. 공통 계약

**스키마 v2** (`storage_meta.schema_version` = 2, `user_version` = 2):

```sql
CREATE TABLE mls_kv (
    scope BLOB NOT NULL CHECK(length(scope)=32),  -- conversation id, 또는 installation 전역이면 zeroblob(32)
    key   BLOB PRIMARY KEY NOT NULL CHECK(length(key) BETWEEN 1 AND 4096),
    value BLOB NOT NULL CHECK(length(value) <= 4194304)
) STRICT;
CREATE INDEX mls_kv_scope ON mls_kv(scope);

CREATE TABLE mls_conversation (
    conversation BLOB PRIMARY KEY NOT NULL CHECK(length(conversation)=32),
    group_id BLOB NOT NULL CHECK(length(group_id) BETWEEN 1 AND 64),
    first_commit_hash BLOB NOT NULL CHECK(length(first_commit_hash)=32),
    epoch INTEGER NOT NULL CHECK(epoch>=0),
    previous_epoch_snapshot BLOB,              -- 직전 epoch 상태 하나(분기 되돌리기용), 바이너리
    own_commit_unacked INTEGER NOT NULL CHECK(own_commit_unacked IN (0,1)),
    rejoin_count INTEGER NOT NULL CHECK(rejoin_count>=0),
    rejoin_after_ms INTEGER NOT NULL CHECK(rejoin_after_ms>=0),
    peer_mls INTEGER NOT NULL CHECK(peer_mls IN (0,1)),  -- 상대 계정에서 MLS를 한 번이라도 받았는가
    FOREIGN KEY(conversation) REFERENCES conversation(id)
) STRICT;

CREATE TABLE mls_delivery (                     -- Commit/Welcome/그룹 제어의 기기별 전달 큐
    conversation BLOB NOT NULL CHECK(length(conversation)=32),
    recipient_install BLOB NOT NULL CHECK(length(recipient_install)=32),
    kind INTEGER NOT NULL CHECK(kind IN (1,2)),   -- 1 Commit, 2 Welcome
    epoch INTEGER NOT NULL CHECK(epoch>=0),
    body BLOB NOT NULL CHECK(length(body) BETWEEN 1 AND 61440),
    attempts INTEGER NOT NULL CHECK(attempts BETWEEN 0 AND 4294967295),
    next_retry_at_ms INTEGER NOT NULL CHECK(next_retry_at_ms>=0),
    PRIMARY KEY(conversation, recipient_install, kind, epoch)
) STRICT;

CREATE TABLE mls_hold (                         -- 기기 목록에 아직 없는 송신자의 Commit/Welcome 보류
    conversation BLOB NOT NULL CHECK(length(conversation)=32),
    sender_peer BLOB NOT NULL CHECK(length(sender_peer)=32),
    body_hash BLOB NOT NULL CHECK(length(body_hash)=32),
    body BLOB NOT NULL CHECK(length(body) BETWEEN 1 AND 61440),
    held_at_ms INTEGER NOT NULL CHECK(held_at_ms>=0),
    PRIMARY KEY(conversation, body_hash)
) STRICT;
```

`outbox.codec`은 `CHECK(codec IN (2,3))`로 바뀐다. 2 = MLS 암호문 준비됨(`wire`는 kind 17 App frame 전체), 3 = 암호화 대기(`wire`는 빈 blob 허용, 원문은 `message` 행). `outbox`에 `reencrypts INTEGER NOT NULL DEFAULT 0 CHECK(reencrypts BETWEEN 0 AND 3)`와 `waiting_peer_update INTEGER NOT NULL DEFAULT 0 CHECK(waiting_peer_update IN (0,1))` 열을 더한다. `processed_ct.codec`은 1(M4 수신)과 2(MLS 암호문 해시)를 쓴다. 보류 항목 상한은 대화당 32개, 전체 1,024개다.

**v1→v2 이관 (`migration::upgrade_v1_to_v2`)**: 한 트랜잭션에서 위 표를 만들고, `outbox`를 새 정의로 다시 만들며 기존 codec 1 행을 codec 3, `wire = x''`로 옮기고(`attempts`, `retry_delay_ms`, `next_retry_at_ms`, `dispatch_state = 0`, 취소·보류 상태는 그대로), `user_version = 2`, `schema_version = 2`로 올린다. 이관 실패면 v1 그대로 남는다. v2 DB를 v1 앱이 열면 기존 규칙대로 corrupt로 거부한다.

**frame kind 17** (`auth::envelope(17, inner)`, inner는 canonical CBOR `[1, op, ...]`, inner ≤ 61,434 B):

| op | 이름 | 필드 | 응답 |
|---|---|---|---|
| 0 | `App` | conversation32, ciphertext(`MlsMessageOut` TLS) | `Ack{ct_hash32}` 또는 `DecryptFailed{class, epoch}` 또는 M4 `Reject` |
| 1 | `GroupQuery` | conversation32 | `GroupInfo{exists:bool, epoch, first_commit_hash32?}` |
| 2 | `KeyPackageRequest` | — | `KeyPackage{bytes ≤ 4,096}` |
| 3 | `JoinRequest` | conversation32, key_package ≤ 4,096 | `Accepted` 또는 `Busy` |
| 4 | `Commit` | conversation32, epoch, commit(TLS) | `Ack{ct_hash32}` 또는 `DecryptFailed{class, epoch}` |
| 5 | `Welcome` | conversation32, welcome(TLS), sender_install32 | `Ack{ct_hash32}` 또는 `ContactRequired` |

`DecryptFailed.class`: 1 epoch 범위 밖(과거), 2 미래 epoch(Commit 누락), 3 순서 범위 밖, 4 그룹 없음, 5 그 밖. 응답에는 내용이 없다.

**M4 kind 16과의 관계:** M5 송신은 kind 17만 쓴다. kind 16 수신은 그대로 처리한다(M4 상대의 Text·Receipt). M4 상대에게 kind 17을 보내면 상대는 알 수 없는 kind로 `Reject(UnsupportedVersion)`(kind 16 응답)을 돌려주거나 연결 수준에서 거부한다. M5 송신자는 둘 다 "상대 업데이트 대기"(`waiting_peer_update = 1`, 화면은 `보내기 대기`)로 다룬다.

**Delivered/Read:** `App`의 동기 `Ack{ct_hash}`는 M4 Receipt와 같은 뜻(상대 기기 하나가 지속 저장)이다. 이것으로 `전달됨`이 된다. `읽음`은 MLS 앱 메시지 `Content::Receipt{kind: Read, targets}`로 보낸다.
