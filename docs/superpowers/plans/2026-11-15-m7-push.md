# M7 Push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 앱이 꺼져 있거나 잠들어 있어도 상대가 보낸 메시지가 잠긴 Android 폰과 iPhone에 보낸 사람과 내용이 담긴 알림으로 곧바로 뜨게 한다. 보내는 기기가 직접 전달하지 못한 상대 기기마다 무상태 푸시 프록시에 푸시를 요청하고, 프록시가 FCM·APNs로 전달한다. 다른 내 기기에서 읽으면 Android 폰의 알림을 조용한 푸시로 지운다.

**Architecture:** 새 crate `core/push_wire`가 PushHandle 봉투·프록시 요청 형식을 정의하고, 새 실행 파일 crate `server/push_proxy`(axum)가 `/handle`·`/push`를 받아 FCM HTTP v1·APNs(HTTP/2)로 보낸다. `chat_core`는 스키마 v4의 푸시 표, 새 MLS 내용 `Content::PushHandle`, 새 actor 모듈 `account/manager/push.rs`(handle 수명, 발송 결정, 받은 푸시 처리)를 더한다. Android는 `Application`·`FirebaseMessagingService`·WorkManager가 UniFFI로 같은 프로세스의 코어를 직접 시작하고 알림을 Kotlin이 띄운다. iOS는 코어가 App Group에 대화별 상태 파일을 쓰고, NSE가 `chat_nse`로 읽기 전용 복호한다.

**Tech Stack:** Rust 1.92.0, 기존 openmls =0.9.0 / rusqlite =0.40.2 / iroh 1.3 / FRB 2.11.1 / UniFFI 0.32.2, 새 의존성: `axum`(server만), `reqwest =0.13.5`(이미 Cargo.lock에 있는 버전, `http2`·rustls), `jsonwebtoken`(server만), `chacha20poly1305 =0.10.1`(이미 Cargo.lock에 있음). Android: `com.google.firebase:firebase-messaging`, `androidx.work:work-runtime-ktx`, Google services Gradle 플러그인. iOS: UserNotifications, BackgroundTasks. Flutter 3.44.6(새 Dart 패키지 없음).

**Spec:** [승인된 M7 설계](../specs/2026-11-14-m7-push-design.md). 상위: [P2P 설계](../specs/2026-10-04-p2p-chat-design.md) 2.5·7.2·8·12.3절, [로드맵](2026-10-04-p2p-chat-roadmap.md) M7, [M6 설계](../specs/2026-11-06-m6-mailbox-design.md), [M6 결과](../results/2026-11-08-m6-mailbox.md), [스파이크 C](../../../spikes/c-push/RESULTS.md). 구현자는 spec과 이 계획을 모두 읽는다. 사용자는 2026-11-15 spec을 승인했다.

## Global Constraints

- **프록시는 아무것도 저장하지 않는다.** 디스크 쓰기 없음(비밀 파일은 읽기만). 로그에는 시각·경로·결과 코드·item 수·걸린 시간만. 토큰·handle·tag·페이로드·IP를 로그·오류 응답·패닉 메시지에 넣지 않는다.
- **푸시 페이로드에 평문, 보낸 계정·기기 식별자, 대화 id를 넣지 않는다.** `e`는 MLS 암호문에서 `group_id` 필드를 뺀 것(`strip_group_id`). 받는 쪽만 tag로 대화를 알고 `restore_group_id`로 되돌린다.
- 값(spec 그대로): handle 수명 `HANDLE_LIFETIME_MS = 2_592_000_000`(30일), 갱신 `RENEW_AFTER_MS = 604_800_000`(발급 후 7일), tag 16바이트 무작위(기기·대화마다 다름), 지터 0–3,000 ms 균등, 페이로드 상한 4,096 B(문서상 한도), 동봉 암호문 상한 `PUSH_CIPHER_MAX = 2_900` B(strip 뒤), rate limit handle당 분당 60·순간 20, `/handle`은 IP당 분당 30, 요청 본문 상한 65,536 B, 한 요청 item 상한 100, Android 깨우기 받아 오기 상한 20,000 ms, 읽음 정리 묶음 1,000 ms, Android 갱신 작업 24시간 주기.
- 높은 우선순위(`cipher`·`wake`)는 Text 메시지에만. receipt·Commit·Welcome·PushHandle에는 푸시하지 않는다. 읽음 정리(`read`)는 일반 우선순위, Android에만.
- 푸시는 메시지를 봉인한 기기가 **첫 시도 결과가 나왔을 때 한 번만** 보낸다. 재시도·메일박스 인계(M6 7절)·받는 쪽 메일박스는 푸시하지 않는다. 대상은 상대 계정의 현재 기기 중 handle이 있고, 그 시도에서 `Acked`하지도 사본을 받지도 않은 기기.
- 푸시가 꺼진 기기(설정 끔, 알림 권한 없음, 프록시 주소 없음)는 프록시에 **어떤 요청도** 보내지 않는다(받기용 `/handle`, 보내기용 `/push` 모두).
- 알림: 같은 메시지로 두 번 울리지 않는다. 이미 읽은 메시지(`seen_local = 1`)로는 알림을 띄우지 않는다. tag를 모르는 푸시(철회했거나 지운 대화)는 알림을 띄우지 않는다. 그 밖의 `cipher`·`wake`는 반드시 보이는 알림으로 끝난다(복호 실패면 "새 메시지").
- 알림 문구: 제목은 연락처 별칭(없으면 "새 메시지"), 본문은 마지막 안 읽은 상대 메시지의 앞부분 최대 48바이트(UTF-8 글자 경계에서 자름, `chat_core::mls::nse::PREVIEW_BYTES`와 같은 값), 안 읽은 메시지가 2개 이상이면 `"<앞부분> 외 N개"`(N = 나머지 수). 앞부분을 모르면 "새 메시지 N개"(M6 문구).
- 릴리스 빌드는 `https://`만 쓴다. `http://`는 디버그 빌드(`debug_assertions`)만. 프록시 주소는 빌드 시 `CHATPROJECT_PUSH_URL`(`option_env!`), 없으면 릴리스는 푸시 끔. 디버그는 Dart 인자 `--push-url`로 바꿀 수 있다.
- iOS NSE: 그룹 상태를 쓰지 않는다(상태 파일 읽기만, inbox 파일 덧붙이기만). 피크 메모리 15 MB 미만. `chat_nse`에는 HTTP 클라이언트·iroh 발송 코드를 넣지 않는다(`chat_core` feature `push-http`를 끈다).
- 기존 규칙 유지: 단일 storage writer, 메시지 하나 처리 = SQL 트랜잭션 하나, frame 상한 61,440 B, 기기 최대 5대, test hook은 `#[cfg(all(feature = "test-hooks", debug_assertions))]`, 릴리스 산출물에 시험 표식 없음(`tools/ci/check_release_hooks.py`).
- 버전 고정: 새 Rust 의존성은 `=`로 정확히 고정한다(axum·jsonwebtoken은 구현 시점의 최신 안정판, Cargo.lock에 이미 있는 crate는 그 버전). Android 새 의존성도 정확한 버전. `Cargo.lock`의 `libc =0.2.189` 고정을 풀지 않는다(전체 `cargo update` 금지, M1b "지켜볼 것" 1).
- 플랫폼: 푸시 받기는 Android·iOS, 보내기는 Windows·Android·iOS 모두. Linux는 제품 대상이 아니지만 CI가 Linux에서 Rust 시험과 프록시를 돌리므로 서버·코어 시험은 플랫폼 중립.
- **이 PC에서 창이 뜨는 시험을 돌리지 않는다**: Windows 통합 시험, `flutter run`, 앱 exe, 보이는 에뮬레이터 금지. 그런 시험은 CI에서만 확인한다(브랜치 push로 CI를 돌린다. PR은 만들지 않는다). 로컬 Rust·Dart 단위 시험은 된다.
- 시험 실행: `cargo +1.92.0 ... -j 6` 이하, 명령은 하나씩 순서대로. CI 명령은 M6 계획과 같고, 이번에 `cargo test --locked -p push_proxy`가 `--workspace`에 들어간다.
- 작업 root는 실행 시 `superpowers:using-git-worktrees`로 만든 격리 worktree(브랜치 `HyunwookYoo/m7-push`). `git add .` 금지, 경로를 지정해 커밋. 커밋 메시지는 빈 줄 하나 뒤 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`로 끝난다. merge·서명·실기기 설치·실제 FCM/APNs 비밀값 다루기는 이 계획의 자동 범위가 아니다(사용자 준비, spec 13절).

## Engineering Principles (사용자 요구, 모든 Task)

모든 Task의 구현자는 아래를 지키고, 작업별 검토자와 마지막 전체 검토자는 네 항목마다 "지킴 / 어김(파일:줄과 이유)"을 판정한다. 어김은 Important 이상으로 다룬다. 원칙을 이유로 Task 범위 밖의 기존 코드를 고치지 않는다(필요해 보이면 보고만 한다).

1. **구조적 안정성**
   - 밖에서 온 입력(FCM data, APNs 페이로드, 프록시 요청·응답, App Group 파일, kind 17·18 frame)에서 패닉·`unwrap`·`expect`·인덱스 범위 초과가 없다. 모든 실패는 타입이 있는 오류(`CoreError`, `PushError`, `HandleError`, `NativeError`)로 돌아오고, FFI 경계(UniFFI·FRB·C ABI)는 패닉을 넘기지 않는다.
   - 네트워크 await를 SQL 트랜잭션에 걸치지 않는다. 한 처리 단위의 DB 변경은 한 트랜잭션이다. 같은 입력이 두 번 와도 결과가 같다(푸시·handle·전달 처리 모두 멱등).
   - 모든 대기에는 상한이 있다(요청 시간 제한, 큐 길이, 재시도 백오프 상한). 취소되거나 프로세스가 중간에 죽어도 다음 실행에서 상태가 맞는다.
2. **일관성**
   - 이미 있는 방식을 따른다: 전달은 `mls_delivery` 방식, 이관은 v2→v3 방식, 수신 경로는 `Origin`/`Via`, 오류는 기존 `ErrorCode`, 시험 hook은 `cfg(all(feature = "test-hooks", debug_assertions))`, 화면 문구는 지금 앱의 존댓말 짧은 문장.
   - 같은 것은 같은 이름: handle, tag, `cipher`·`wake`·`read`를 코어·서버·Kotlin·Swift·Dart에서 같은 뜻으로만 쓴다. 상수와 형식은 `push_wire` 한 곳에서 정의하고 다른 곳은 가져다 쓴다(값을 다시 적지 않는다).
3. **SOLID**
   - 단일 책임: SQL은 `message/push_store.rs`, actor 판단은 `account/manager/push.rs`, HTTP는 `push/client.rs`, 서버의 경로·제한·로그·발송은 각자 파일. 한 함수가 판단과 입출력을 함께 하지 않는다.
   - 확장에 열림: 플랫폼 차이는 `Upstream` 구현과 `Platform` 값으로만 갈린다. 새 플랫폼이 생겨도 판단 코드의 분기를 늘리지 않는다.
   - 대체 가능: 가짜 구현(`FakeUpstream`, `FakePushProxy`)은 진짜와 같은 계약을 지킨다(`FakePushProxy`는 진짜 `router`를 감싼다). 시험만 통과하는 다른 동작을 넣지 않는다.
   - 작은 인터페이스: `Upstream`·`PushProxy`·`NativeNotifier`는 필요한 메서드만 둔다.
   - 의존성 역전: actor는 `PushProxy` trait에, 서버는 `Upstream` trait에 기댄다. 시계·지터·무작위는 주입한다(시험에서 바꿀 수 있게).
4. **성능**
   - actor 스레드와 storage writer에서 네트워크를 기다리지 않는다. `/push`는 기다리지 않고 보낸다. 메시지 하나의 푸시는 `/push` 요청 하나에 묶는다. 읽음 정리는 1,000 ms로 묶는다.
   - 메시지마다 모든 대화를 훑지 않는다(handle 갱신 확인은 1시간마다와 지정된 시점에만). 조회는 기본 키나 색인으로 한다.
   - iOS 상태 파일은 그 대화의 MLS 상태가 바뀐 때만 쓴다. NSE는 피크 15 MB 미만, 파일 하나만 읽는다.
   - 프록시는 HTTP/2 연결을 다시 쓰고, OAuth 토큰과 APNs JWT를 캐시한다. 요청마다 메모리 사용이 본문 상한 안에서 끝난다.
   - 성능 주장은 시험이나 측정으로 보인다(예: 요청 수 세기, 응답이 지터를 기다리지 않음, NSE 메모리 기록).

## Review Focus

1. **지운 대화나 철회한 tag로 푸시가 온다** (handle은 30일 동안 살아 있다): 알림 없이 버리고, 코어가 죽거나 "새 메시지"를 띄우지 않아야 한다. — Task 8 `push_for_unknown_tag_shows_nothing`, Task 11 NSE `unknownTagDeliversNothingVisible`.
2. **같은 암호문이 푸시와 직접 연결로 거의 동시에 온다**: 메시지 한 행, 알림 한 번(두 번째는 소리 없는 고침이거나 아무것도 아님), 보낸 쪽 `전달됨` 한 번. — Task 8 `push_and_direct_same_ciphertext_alert_once`.
3. **FCM·APNs 토큰이 handle이 살아 있는 동안 바뀐다**: 모든 대화의 handle이 새로 발급되어 알려지고, 상대는 이전 handle을 더 쓰지 않는다. — Task 6 `token_change_reissues_every_conversation_handle`.
4. **갱신이나 발송이 진행 중일 때 푸시를 끈다**: 끈 뒤에는 프록시 요청이 0이고 철회가 상대에게 간다. 끄기 전에 시작한 요청의 응답이 와도 handle을 저장하지 않는다. — Task 6 `turning_push_off_mid_renewal_sends_nothing_after`.
5. **이모지·한글·결합 문자가 많은 긴 메시지의 미리보기**: 48바이트 안에서 글자 중간을 자르지 않고, NSE·Android·Windows가 같은 문구를 낸다. — Task 8 `preview_cuts_on_char_boundary_within_48_bytes`.

## 2. 공통 계약

**`core/push_wire`** (의존성: serde, serde_json, `chacha20poly1305 =0.10.1`, `data-encoding =2.11.1`, `getrandom =0.3.4`)
