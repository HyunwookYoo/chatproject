# M8 Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 메일박스 기기가 없는 사람의 기기마다 서버 큐를 자동으로 만들어, 꺼져 있던 동안 온 메시지를 켜진 뒤 받게 한다. 상대는 직접 닿지 못한 기기의 큐에 암호문을 넣고, 받는 기기가 받을 때까지 `보냄`을 유지하며, 큐 보관이 끝나면 다시 넣는다. 메일박스가 다시 믿을 만해지면 큐를 해제한다.

**Architecture:** 새 crate `server/http_guard`가 푸시 프록시의 연결 상한·연결 수명·토큰 버킷을 가져와 두 서버가 함께 쓴다. 새 crate `core/queue_wire`가 큐 명령·서명 바이트·상수를 정의하고, 새 실행 파일 crate `server/queue_server`(axum + SQLite)가 `/q/*`를 받는다. `chat_core`는 스키마 v5의 큐 표, MLS 내용 `Content::QueueRef`, Announce 다섯 번째 필드 `qualified`, 판정 함수, 새 actor 모듈 `account/manager/queue.rs`(맞추기, 가져오기, 넣기)를 더한다. Flutter는 설정 선택과 홈 상태 카드를 더한다.

**Tech Stack:** Rust 1.92.0, 기존 rusqlite =0.40.2 / axum / reqwest / ed25519-dalek / sha2 / serde_json (모두 Cargo.lock에 있는 버전). 새 의존성 없음이 목표다. 필요하면 `=`로 고정한다. Flutter 3.44.6(새 Dart 패키지 없음).

**Spec:** [승인된 M8 설계](../specs/2026-11-22-m8-queue-design.md). 상위: [P2P 설계](../specs/2026-10-04-p2p-chat-design.md) 2.2·2.5·9·10절, [로드맵](2026-10-04-p2p-chat-roadmap.md) M8, [M6 설계](../specs/2026-11-06-m6-mailbox-design.md), [M7 설계](../specs/2026-11-14-m7-push-design.md), [M7 결과](../results/2026-11-15-m7-push.md). 구현자는 spec과 이 계획을 모두 읽는다. 사용자는 2026-11-22 spec을 승인했다.

## Global Constraints

- **큐 서버는 spec 9.5의 표와 열만 저장한다.** 로그에는 시각·경로·결과 코드·명령 수·걸린 시간만. 큐 ID·공개키·서명·암호문·IP·크기를 로그·오류 응답·패닉 메시지에 넣지 않는다.
- 값(spec 그대로): 큐 ID 32 B(받는 기기가 정함), 암호문 상한 65,536 B, 큐당 미수신 256개, 항목 보관 24시간(`ENTRY_TTL_MS = 86_400_000`), `Retiring` 48시간(`RETIRE_MS = 172_800_000`), 미사용 큐 삭제 30일, 로테이션 7일, 서명 시각 허용 ±10분, 한 요청 명령 100개, 전체 저장량 2 GiB, 받는 기기의 주기 가져오기 5분, 판정 다시 하기 1시간, 메일박스 자격 900‰ 이상과 기록 24시간 초과, 메일박스를 본 지 24시간.
- rate limit(spec 9.4): `CREATE` 클라이언트마다 시간당 500·순간 200, `SEND` 큐마다 분당 60·순간 20, `RECV`·`ACK` 클라이언트마다 분당 120 요청. 클라이언트 = IPv4 주소 하나 또는 IPv6 /64 하나.
- 큐에 넣은 메시지는 상대의 수신 확인 전까지 `전달됨`이 아니다(사용자 결정). 큐 넣기는 직접 재시도를 멈추지 않는다.
- "서버 사용 안 함"인 기기는 큐 서버에 **어떤 요청도** 보내지 않는다(받기용 `CREATE`·`RECV`·`ACK`·`DELETE`, 보내기용 `SEND` 모두). 보내기도 막는 이유는 이 설정이 "우리 서버에 아무것도 남기지 않음"이기 때문이다(설계자 판단, 결과 문서에 적는다).
- 릴리스 빌드는 `https://`만, 그리고 `CHATPROJECT_QUEUE_URL`과 같은 주소의 `QueueRef`만 받는다(spec 7.2). 디버그는 Dart 인자 `--queue-url`로 바꿀 수 있다. 주소가 없으면 릴리스는 큐 끔(판정과 무관).
- 같은 메시지는 한 번만 저장하고 한 번만 알린다. 큐·푸시·직접 수신·메일박스 맞추기가 겹쳐도 `processed_ct`가 거른다.
- 기존 규칙 유지: 단일 storage writer, 메시지 하나 처리 = SQL 트랜잭션 하나, 네트워크 await를 트랜잭션에 걸치지 않음, frame 상한 61,440 B, 기기 최대 5대, test hook은 `#[cfg(all(feature = "test-hooks", debug_assertions))]`, 릴리스 산출물에 시험 표식 없음(`tools/ci/check_release_hooks.py`).
- HTTP 클라이언트 코드는 기존 feature `push-http` 아래에 둔다. `chat_nse`는 그 feature를 끄므로 NSE에 큐 코드가 들어가지 않는다.
- 버전 고정: `Cargo.lock`의 `libc =0.2.189`를 풀지 않는다(전체 `cargo update` 금지). 새 crate는 `cargo update -p <name> --precise`로만 더한다.
- **이 PC에서 창이 뜨는 시험을 돌리지 않는다.** 로컬은 Rust·Dart 단위 시험만, `cargo ... -j 2`, `chat_core` 전체 시험과 `--all-targets` clippy는 CI에서만(메모리). 명령은 하나씩. 그 밖은 브랜치 push로 CI를 돌린다. PR은 만들지 않는다.
- 작업 root는 격리 worktree(브랜치 `HyunwookYoo/m8-queue`). `git add .` 금지, 경로를 지정해 커밋. 커밋 메시지는 빈 줄 하나 뒤 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`로 끝난다. merge는 merge commit만. VM 배포와 main push는 사용자가 말할 때만.

## Review Focus

1. **판정이 깜빡인다** (메일박스 PC가 자격 경계에서 오르내림): 한 시간에 한 번만 다시 계산하고, 큐 만들기·해제가 그보다 자주 일어나지 않는다. 해제한 큐는 48시간 `Retiring`으로 남아 그사이 들어온 것도 가져간다. — Task 7 `verdict_recomputed_hourly_not_per_announce`, Task 8 `release_then_recreate_keeps_entries`.
2. **`CREATE` 중에 프로세스가 죽는다**: 다시 시작한 뒤 같은 큐 ID로 끝나고 큐가 둘이 되지 않는다. — Task 8 `crash_mid_create_converges_to_one_queue`.
3. **큐에 넣은 뒤 받는 기기가 48시간 넘게 꺼져 있다**: 보내는 기기가 만료 뒤 다시 넣고, 받는 기기는 한 번만 저장한다. — Task 10 `expired_queue_copy_is_sent_again_and_stored_once`.
4. **같은 암호문이 `cipher` 푸시와 큐로 온다**: 메시지 한 행, 알림 한 번, 큐 항목은 다음 가져오기에서 `ACK`. — Task 9 `push_and_queue_same_ciphertext_alert_once`.
5. **상대가 다른 서버 주소의 `QueueRef`를 보낸다**: 릴리스 규칙에서 버리고, 그 주소로 요청이 0. — Task 8 `foreign_queue_url_is_ignored`.

## 3. 공통 계약

**`core/queue_wire`** (의존성: serde, serde_json, `ed25519-dalek`, `sha2`, `data-encoding`, 모두 Cargo.lock 버전)

```rust
pub const MAX_CT: usize = 65_536;
pub const MAX_UNACKED: usize = 256;
pub const MAX_ITEMS: usize = 100;
pub const MAX_BODY: usize = 1_048_576;          // SEND 묶음: 기기 5대 × 64 KiB를 base64로 담는 크기
pub const ENTRY_TTL_MS: u64 = 86_400_000;
pub const RETIRE_MS: u64 = 172_800_000;
pub const IDLE_DELETE_MS: u64 = 2_592_000_000;
pub const ROTATE_MS: u64 = 604_800_000;
pub const TS_SKEW_MS: u64 = 600_000;
pub type QueueId = [u8; 32];

/// 서명할 명령과 본문 (Task 2 수정 ed5f52e: 명령과 본문을 잘못 짝지을 수 없다)
pub enum Signed<'a> { Create { sender_pub: &'a [u8; 32] }, Send { ct: &'a [u8] }, Recv { since_seq: u64 }, Ack { upto_seq: u64 }, Delete }
/// 서명할 바이트 = "chatproject-queue-v1" 0x00 | 명령 이름 | 0x00 | queue_id | ts_ms u64be | SHA-256(본문)
/// 본문 = CREATE sender_pub, SEND ct, RECV since_seq u64be, ACK upto_seq u64be, DELETE 빈 바이트
pub fn signing_bytes(signed: &Signed, queue_id: &QueueId, ts_ms: u64) -> Vec<u8>;
pub fn sign(secret: &[u8; 32], bytes: &[u8]) -> [u8; 64];
pub fn verify(public: &[u8; 32], bytes: &[u8], sig: &[u8; 64]) -> bool;

// JSON, 바이트 값은 base64url(패딩 없음). 요청 = { "items": [ ... ] }, 응답 = { "results": [ ... ] } (같은 순서)
pub struct CreateItem { pub queue_id: String, pub recipient_pub: String, pub sender_pub: String, pub ts: u64, pub sig: String }
pub struct SendItem   { pub queue_id: String, pub ct: String, pub ts: u64, pub sig: String }
pub struct RecvItem   { pub queue_id: String, pub since_seq: u64, pub ts: u64, pub sig: String }
pub struct AckItem    { pub queue_id: String, pub upto_seq: u64, pub ts: u64, pub sig: String }
pub struct DeleteItem { pub queue_id: String, pub ts: u64, pub sig: String }
#[serde(tag = "result", rename_all = "lowercase")]
pub enum ItemResult { Ok, Exists, Gone, Full, Limited, Bad, Entries { entries: Vec<Entry> } }
pub struct Entry { pub seq: u64, pub ct: String, pub ts: u64 }
```

경로: `POST /q/create`, `/q/send`, `/q/recv`, `/q/ack`, `/q/delete`. 서명이 틀리거나 `ts`가 범위 밖이면 그 item만 `bad`. `Debug` 출력에 큐 ID·키·서명·암호문을 넣지 않는다(`push_wire`와 같은 규칙).

**MLS 내용** (`mls/payload.rs`)

```
Content::QueueRef(Option<QueueRefBody>)      // [4, null] | [4, [server_url, queue_id, sender_secret]]
pub struct QueueRefBody { pub server_url: String, pub queue_id: QueueId, pub sender_secret: [u8; 32] }
```

frame 규칙은 `PushHandle`과 같다(lamport 0, 내용에서 만든 msg_id, 기기별 엄격히 증가하는 시각). 전달은 `push_delivery`와 같은 기기별 전달 표로 한다(Task 5에서 그 표에 `kind`를 더해 함께 쓴다).

**Announce** (`mailbox/wire.rs`): `[1, 5, mailbox, handle|null, qualified]`. 디코더는 3·4·5 필드를 받는다. 4 필드 이하면 `qualified = false`.

**판정** (`mailbox/verdict.rs`, 순수 함수)

```rust
pub enum QueueMode { Auto, Always, Never }
pub enum Verdict { HasMailbox { installation: InstallationId }, NoMailbox }
pub struct MailboxFact { pub installation: InstallationId, pub mailbox: bool, pub qualified: bool, pub last_seen_ms: Option<u64> }
pub fn verdict(me: &MailboxFact, others: &[MailboxFact], now_ms: u64) -> Verdict;
pub fn wants_queue(mode: QueueMode, verdict: &Verdict, me: InstallationId) -> bool;
pub fn qualifies(uptime_permille: u16, recorded_ms: u64) -> bool;   // >= 900 && recorded_ms > 86_400_000
```

`me`의 `last_seen_ms`는 언제나 "지금"이다. `HasMailbox`의 installation이 `me`이고 `me`가 자격이 있으면 큐를 쓰지 않는다.

**스키마 v5** (`upgrade_v4_to_v5.sql`)

```
queue_local(id=1, mode 0 auto|1 always|2 never, qualified 0|1, qualified_at_ms, verdict_at_ms)
queue_own(queue_id PK, conversation, recipient_secret, sender_secret, created_at_ms,
          state 0 active|1 retiring, delete_at_ms NULL, last_seq, server_confirmed 0|1)
          + UNIQUE(conversation) WHERE state = 0
queue_peer(conversation, installation, server_url NULL, queue_id NULL, sender_secret NULL,
           sent_at_ms, received_at_ms, dead 0|1, PRIMARY KEY(conversation, installation))   -- queue_id NULL = 철회 묘비
queue_delivery(outbox_id, installation, queue_id, expires_at_ms, PRIMARY KEY(outbox_id, installation))
mailbox_device + qualified 0|1 DEFAULT 0, last_seen_ms NULL
push_delivery + kind 1 push_handle|2 queue_ref DEFAULT 1, 기본 키에 kind
```

## 4. Tasks
