2026-10-18 한국 시간 기준, 10월 16–18일 검증·분석 현황이다(파일명은 최초 실행일 16일 유지). Tasks 1–12와 Task 13 코드 지적 수정, 전체 브랜치 검토·최종 수정·단일 scoped 재검토를 로컬에서 마쳤다. 기존 exact `06d36a4` 일반 CI 9/9 성공과 일반 EE Phase A 기능 성공은 유지한다. 사용자 요청대로 엄격한 연결 ≤500 ms / Direct ≤1000 ms 기준을 유지하며 일반 EE 10회 중 580 ms 미달은 열려 있다. 최신 v4 단일 진단·Task 15 분석은 제품 성능 수정이나 수용 시험 통과가 아니다. iPhone LAN 확인은 사용자 유예, signed app 실행 로그는 아래의 기존 증거 판정과 가시성 한계로 남는다. 로컬 `4bb4906`·`aadd2db`는 미push이며 원격/Draft PR #2의 마지막 관찰 HEAD는 `06d36a4`다. 이번 정리에서 원격을 새로 확인하지 않았다. **Task 14·M2는 미완료이며 통합도 미실행이다.** [39개 인계 항목과 후속 책임](../plans/2026-10-13-m2-carry-forward.md)을 함께 읽는다.

최초 제품 기준 [`751bb17`](https://github.com/HyunwookYoo/chatproject/commit/751bb173623b627b85d8b688df99bccd8ba65bdf)의 산출물·측정은 그대로 보존한다. 현재 제품은 티켓 주소 갱신을 수정한 [`ee9485c`](https://github.com/HyunwookYoo/chatproject/commit/ee9485cf90342170bf11e610557cf6aee5e87783)다. 중간 `3691396`/`41e7954`는 ready-file 시험, `21e806f`는 AVD 진단, `3780025`는 Android AVD 홈 준비를 바꿨다. EE 이후 `820f53b`는 유한 시나리오 진단, `1930853`은 시험 응답 deadline, `7a4c2b0`는 소유 snapshot 준비 후 종료 관찰 barrier를 수정했으며 제품은 EE와 같다. 후속 `c434021`은 일반 Android CI의 리소스 관찰기를 추가했고 `06d36a4`에서 Linux lifecycle 시험을 보강했다. exact `06d36a4` 일반 CI와 signed TestFlight는 실제 실행을 마쳤으며 제품은 EE와 같다. 사설 진단은 별도로 고정한 EE 소스 복사본에서 만든 임시 바이너리이며 이 CI HEAD나 일반 EE 산출물로 재명명하지 않는다. **751과 EE 바이너리·실제 측정은 서로 다른 기준**이다. scoped 수정 승인과 실제 CI/물리 통과도 구분한다.

아래 로컬 증거 경로는 gitignored `build/e2e/` 안에 보관되어 담당자가 열람할 수 있다. 공개 다운로드 링크는 아니며 티켓·EndpointId·주소·기기 serial·원시 콘솔은 공개하지 않는다. CI 근거는 실제 실행 링크로 남긴다. 이 문서 작성 중 빌드나 광범위 시험을 다시 실행하지 않았다.

## 빌드와 기기

일반 제품은 `lib/main.dart`로 빌드했다. Windows Release 전체 폴더 14개 파일과 Android ARM64/ARMv7 Release APK를 `build/e2e/task14-preparation/751bb17/`에 따로 보존했다. 전용 `Stopped`/`NotAvailable` 계약 산출물과 섞지 않는다. APK는 65,632,255 B, SHA256 `057a1546472b1307b7fe40dd43374358bf2f5d1773230710fefc0d3601d9b488`이다. Windows 전체 파일 해시는 같은 폴더의 `SHA256SUMS`와 `artifact-index.json`에 있다.

새 EE 일반 제품도 같은 `lib/main.dart`와 실제 Rust 1.92/default-no-hooks로 Windows 전체 14파일·ARM64/ARMv7을 빌드했다. 별도 `build/e2e/task14-preparation/ee9485c/`의 APK는 65,746,943 B, SHA256 `08bb710de0d54d45f80098d8d8b4b0cd39be7b13d442437b399a22211101e8cc`이며 Windows `chat_ffi.dll` SHA256은 `4db5ca056816713ef214b1c0b21aa0da74a5f1200e7ac0b568f47f5729cda23f`다. 두 실제 설치/실행 산출물의 정체성을 확인했다. 같은 폴더에 전체 `SHA256SUMS`/`artifact-index.json`이 있다. 두 ARM Rust payload는 새 EE이고, 부수 x64 세 파일은 기존 751과 같은 바이트다. 전체 x64 Flutter 실행이나 새 x64 빌드를 주장하지 않는다. ARMv7은 빌드만 확인했고 호환 기기 실제 실행은 배포 전 유예다.

Windows 앱은 `1.0.0+1`, Android는 `1.0.0`(1), 코어는 `0.1.0`이다. 실제 Rust 명령은 Windows·ARMv7·ARM64 모두 `rustup run 1.92.0 cargo build`였고 제품 빌드에 test-hooks를 켜지 않았다. Android minSdk 26/targetSdk 36, nondebuggable, INTERNET/ACCESS_NETWORK_STATE와 두 ARM ABI의 다섯 네이티브 라이브러리를 확인했다. Windows 네이티브 5개와 APK 네이티브 13개에서 조종 표식이 없었다. APK의 부수 x86_64 라이브러리 세 개는 완전한 x64 Flutter 실행 지원을 뜻하지 않는다. 현재 APK는 기존 로컬 debug-key 서명 설정이며 배포 서명 증거가 아니다.

실제 Android는 SM-F971N, Android 17/API 37, ARM64 전용이다. 751 및 EE 각각 설치 APK 해시를 확인했다. ticket 성능 코호트는 Windows Home Ethernet↔Android KT LTE에서 진행했고, 이후 751 이동 시험은 Wi-Fi도 사용했다. Windows는 MSI MS-7D75, Microsoft Windows 11 Pro 10.0.26300/build 26300, 64-bit/x64 PC다. 로컬 `build/e2e/physical-2026-10-16/windows-device-sanitized.json`에 비식별 사실을 보관했다. 확인 시점의 기본 경로는 물리 Ethernet이며 USB/RNDIS가 아니었다. 이는 모든 순간의 연속 추적을 뜻하지 않는다. 751 USB 중단 동안 프로세스/키 유지와 EE 설치를 위한 새 프로세스 시작은 별개다.

## 실제망 표본의 해석

연결 시간은 Rust의 같은 로컬 monotonic clock에서 connect 시작 직전부터 magic-ready 뒤 connected까지, Direct 시간은 그 시작부터 첫 selected-Direct 관찰까지다. 다른 기기의 wall clock을 빼지 않았다. 원본 JSONL은 `sample,connected_ms,direct_ms,path,success,error_code` 여섯 필드이며 식별 정보는 별도 비공개 기록에 있다.

최초 두 번과 절차를 고정한 다음 열 번을 모두 보존했다. 최초 두 번 집계는 connected 238–3635 ms/Direct 239–3747 ms, 두 목표 모두 1/2 미달이다. 주 평가 열 번은 Android Stop→Stopped, Windows 수동 Disconnect→Disconnected, Android Start→Ready, 새로 전달한 ticket 입력→새 connect 순서로 반복했다. 최초 두 번을 폐기하거나 유리한 열 번을 골라 대체하지 않았다. 12회 모두 연결·Direct 관찰에 성공했지만 이는 성능 목표 통과를 뜻하지 않는다. 목표 미달의 원인은 미확정이며 cold relay 같은 가설을 결론으로 쓰지 않는다. EndpointId 단독 DHT 시간은 이 ticket 표본에 섞지 않는다.

EE의 별도 열 번도 같은 Stop/Disconnect/Start/normal Ready 절차로 모았으며 새 JSONL에 전부 보존했다. 연결 목표 1회 미달은 제외하거나 재시도 값으로 대체하지 않았다. 사용자는 원인을 더 확인한 뒤 판단하기로 선택했다. 추가 RCA와 최종 수용 판단은 남아 있으며 성능 예외·면제는 승인되지 않았다. 두 코호트 모두 최종 Direct 관찰이며 초기/일시 Relay가 전혀 없었다는 증거는 아니다. 751 수동 해제 작업의 측정 밖 transportFailed 기록 두 건과 원격 fresh inbound는 실제 outgoing 표본과 분리 보존했다.

751 primary Ready ticket 열 개는 relay URL이 없었고 IP 범주만 별도 확인했다. 한 번 저장한 ticket이 후속 SDK 주소를 반영하지 않는 결함은 실제 manager 시험으로 RED→GREEN을 재현했다. EE는 epoch/cancel로 보호한 관찰 작업 하나가 변경된 주소를 다시 반영하며 Public Online·DHT·relay-only 정책이나 Ready 조건을 강화하지 않는다. hooked 88/default 56 시험과 별도 검토를 통과했다. 엄격한 test-hooks clippy에는 기존 ConfigureLocal `collapsible_if`가 남고 해당 lint만 허용한 검사는 다른 경고가 없었다. 이것이 751 지연의 단일 원인이라는 증거는 없다. 새 코호트도 normal Ready 뒤 별도 relay wait 없이 진행하며 시작 이력/UI 지연 차이로 단순 전후 인과를 단정하지 않는다.

일반 EE의 연결 580 ms인 한 회는 Connected/Relay 뒤 Direct가 실제 관찰됐다. 그 회의 Direct−connected 115 ms는 전체 83–120 ms 범위 안이며 relay가 80 ms 초과를 일으켰다고 단정할 수 없다. 저장된 core Instant 값은 UI의 250 ms 관찰 주기로 만들어진 값이 아니다. 이 과거 호출에는 SDK/CPM2/scheduling 경계를 나누는 timestamp가 없어 원인은 미확정이다. 별도 Windows v1 진단 10회는 pre-SDK 54–310 µs, SDK 177479–547521 µs, preparation 183867–229882 µs였고 SDK-return/ready 선택 경로는 모두 Relay였다. 이 선택 경로 snapshot은 초기 QUIC이나 모든 packet의 경로를 증명하지 않는다. 그 진단 호출들의 변화는 주로 SDK 구간에 있었으나 내부 resolver/relay/QUIC/RTT 원인을 나누지는 못한다. 계측·프로세스·주소/게시 이력이 달라 일반 EE 580 ms를 소급 설명하거나 통제된 전후 비교로 해석하지 않는다. Direct 값도 첫 선택 경로 관찰 시각이며 정확한 최초 전환 시각은 아니다. 사용자는 500 ms 목표를 유지하고 추가 조사를 선택했으며 진단의 5회 미달도 면제하지 않았다.

751 오프라인 검증은 물리 망이 없는 상태에서 UI가 Send를 막고 입력 글이 미송신/0수신임을 확인한 것이다. 실제 Core Send 호출이 거절됐다는 관찰로 바꾸지 않는다. 복귀 뒤 새 본문 1회와 이전 글 0회, 이동 세 단계의 새 본문 각 1회를 확인했다. Android 측 화면 재생성으로 최근 목록이 초기화된 구간은 Windows의 보존된 수신 기록과 구분했다. 원격 inbound를 막기 위해 자체 Android 프로세스를 종료한 뒤 Windows 수동 Disconnect를 관찰했고, 이후 새 Android 프로세스/새 ID는 확인했으나 그 새 ID의 연결 성공은 아직 없다.

751의 첫 uncached ID-only DHT 시도는 timeout이었고 Connect 직전 전경을 다시 확인하지 않았다. 35.6 s 관찰 동안 자동 성공이 없었으며 명시적 재시도도 timeout이었다. 후속 power 증거상 알려진 절전 경계는 첫 시도 뒤·두 번째 시도 전이다. 따라서 **두 번째 시도는 배경 상태가 섞여 유효한 전경 실패 증거가 아니며**, 첫 시도도 즉시 전경 검증 한계와 원인 미확정을 남긴다. 두 timeout을 숨기거나 통제된 전경 전체 실패로 확대하지 않는다. EE DHT는 ticket을 공유하지 않은 새 ID와 전·중·후 전경/awake 확인으로 별도 검증해야 한다.

EE에서는 새 Android process의 빈 peer/target와 SDK/Mainline cache 초기화를 소스로 확인하고, 기존 Windows의 정확한 ID만 입력한 fresh-client 방향을 별도로 시험했다. ticket을 주거나 사전 inbound로 주소를 학습하지 않았고 첫 시도 전·중·후 전경/Awake를 확인했다. 첫 시도와 같은 process의 수동 retry는 모두 transportFailed/Disconnected, core 연결·Direct metric null/Unknown이었다. UI에서 terminal을 관찰한 6398/5193 ms는 core 지연이나 정확한 tap→error 시간이 아니다. 이 유효한 방향별 실패의 원인은 미확정이다. Windows→새 Android publisher는 focus guard가 입력 전에 막아 미실행이며 실패로 세지 않는다. 751의 조건 제한 timeout과 합산하지 않는다.
