# M4 Windows–Android 공개망 실물 검증

검증일: 2026-10-25 KST. 기준 소스는 `3ec3382`이며, 아래 기능 관찰 후 계정 오류 코드 진단 로그를 추가했다. 일반 Windows Release와 별도 패키지의 실제 ARM64 Android Release를 사용했다. 사용자는 분리된 시험 계정의 공개 Mainline DHT 및 기본 n0 릴레이 사용을 명시적으로 승인했다.

## 기능 관찰

| 항목 | 관찰 결과 | 판정 범위 |
| --- | --- | --- |
| 최초 자동 연결 | 양쪽 네트워크 준비·자기 공개 목록 반영 확인 상태에서도 PC 메시지가 대기했고 휴대전화에 나타나지 않았다. | 실패 |
| 수동 주소 비교 시험 | 현재 PC 티켓을 이용한 일반 M2 진단 연결은 성공했다. 양쪽에서 실제 기기 식별자를 비교하고 상대 목록을 적용한 뒤 ACCOUNT 인증이 성공했다. | 주소를 공급한 상태의 접속·인증 관찰 |
| 양방향 표시 | PC→휴대전화 및 휴대전화→PC 메시지가 상대 화면에 각각 1개 표시됐다. | 위 비교 연결로 변경된 공유 주소 캐시의 영향을 받음 |
| 오프라인 복귀 | 휴대전화 시험 앱의 네트워크 중지 중 PC 메시지가 대기했다. 네트워크 재개 후 재전송 없이 휴대전화에 1개 표시되고 PC에 읽음이 반영됐다. | 해당 실행의 전달·읽음 성공 |
| PC 재시작 보존 | 대기 메시지를 만든 뒤 PC 시험 앱을 정상 종료하고 같은 실행 파일·저장 폴더로 재시작했다. 이전 대화와 대기 메시지 1개가 보존됐다. | 보존 성공 |
| 재시작 후 자동 복귀 | PC 프로세스와 휴대전화 엔드포인트를 다시 시작하고 추가 티켓·인증·재전송을 하지 않았을 때 메시지는 계속 대기했다. | 실패, 미해결 |

M2의 직접/릴레이 표시를 M4 메시지의 경로 증거로 사용하지 않았다. 메시지가 한 번 표시된 관찰은 ACK 유실·재생을 강제로 주입한 중복 억제 시험을 대신하지 않는다. 최초 PC 송신의 사용자 응답은 전달 또는 읽음을 묶은 선택지였으므로, 그 응답만으로 정확한 읽음을 주장하지 않는다. 오프라인 복귀 사례에서는 읽음이 별도로 확인됐다.

## 주소 검색 및 목록 충돌

휴대전화 인증 실패 시간대에 현재 PC 엔드포인트를 대상으로 한 DHT 조회와 `no signed packet found`, `All address lookup services failed or produced no results`가 확인됐다. 현재 PC 티켓에는 릴레이 주소가 있었다. 이후 휴대전화에서는 현재 엔드포인트 키의 게시 성공 기록도 확인했다.

별도의 읽기 전용 DHT 도구로 같은 Windows 호스트에서 현재 휴대전화 엔드포인트를 한 번 조회했다. 결과는 2,064ms 뒤 `no_item`, bootstrap true, 로컬 routing table 2였다. 도구는 게시하거나 앱에 연결하지 않았으며, 원문 티켓·키·주소·패킷을 보존하지 않았다. 오프라인 자체 검사에서 티켓 해석, 유효 서명, 다른 키 및 손상 서명 구분을 확인했다.

게시 성공은 최소 한 곳의 저장 응답을 뜻한다. 이 조회의 `no_item`은 값 없음, 유효 응답 없음 등을 구분하지 않으며 전역 부재를 증명하지 않는다. 1차 시험 당시에는 PC 자동 재접속 실패의 정확한 오류 코드를 수집하지 못했다. 후속 진단 결과는 아래와 같다. 기존 Minimal/DHT 구성과 `dns.iroh.link` 미사용 방침을 변경하지 않았다.

## 계정 오류 진단 변경

`AccountModel._failure`에 고정 문구와 오류 enum 이름만 기록하는 한 줄을 추가했다. 오류 상세, 예외 문자열, 인수, 식별자, 복구 문구 및 메시지 본문은 기록하지 않는다. UI 문구, 연결·저장·재시도 동작은 바꾸지 않았다.

- 오류 상세 및 알 수 없는 예외의 비공개 문자열이 출력되지 않고 기존 상태·UI 처리가 유지되는 시험 2개를 RED → GREEN으로 확인했다.
- 집중 시험 7건 통과. 전체 Flutter 시험 209건 통과, 기존 선택 시험 10건 건너뜀. 정적 검사 이상 없음.
- 독립 검토: 지적 없음.
- Windows 일반 Release 빌드 및 시험용 기능 제외 정적 검사 통과. 기존 번들과 비교하면 Dart AOT만 변경됐고 실행 파일 및 DLL은 동일하다.
- 같은 시험 저장 폴더로 진단 빌드를 실행한 뒤, 일반 UI에서 잘못된 초대를 확인해 실제 표준 출력에 `invalidInvite`만 기록되는 것을 검증했다. 이는 진단 수집 경로 검증이며 연결 실패 원인 수정은 아니다.

Android에는 새 진단 빌드를 설치하지 않았다. 원래 Android 앱·데이터는 유지했고, 별도 시험 패키지를 사용했다. 사용자는 USB 분리를 허용받았으며 시험 데이터는 후속 검증을 위해 유지한다.

상세 영수증·명령·해시·로그: Git에서 제외된 `build/e2e/m4-physical-2026-10-25/`, 현재 진행 상태는 그 안의 `session-state.json`과 `progress.md`에 저장했다. 다음 단계는 활성 상대 기기를 확인한 상태에서 실제 연결 실패 코드를 수집하고, 기존 DHT 구성 안에서 원인을 재현·수정한 뒤 자동 복귀를 재검증하는 것이다. 이번 결과로 M4 전체 완료를 판정하지 않는다.

## 재연결 후 충돌 비교 진단

PC에서 실제 오류 코드 `recordConflict`를 수집했다. 추가한 네이티브 진단은 변경 전 상태의 불리언과 순서 비교 분류만 기록한다. 원문 record·식별자·키·해시·순서 번호·시각 값은 출력하지 않는다. 쓰기 실패를 무시하는 stderr 출력이며, 기존 수용·권한·저장 판정과 오류 코드/상세 문자열은 유지한다. 오류 상세 문자열을 매칭하지 않는다.

실제 조회 경로에서는 `retained_before=true`, `hash_equal=false`, `seq_vs_accepted=Greater`, `below_prior_floor=false`, `generation_equal=true`, `devices_equal=true`, `time_valid=true`가 관찰됐다. 현재 거부는 이전 충돌이 남아 있기 때문이다. 현재 응답은 수용했던 목록과 세대·기기 구성이 같고 순서 번호는 더 크다. 이 사실은 최초 충돌의 원인이나 record 만료 여부를 설명하지 않는다.

사용자가 실제 기기 식별자를 대조하고 정상 목록 적용을 완료한 뒤, 추가 티켓 입력 없이 PC 인증이 성공했다. 기존 `M4-RESTART-01`은 재전송 없이 휴대전화에 1개 표시되고 PC에 읽음이 반영됐다. 목록 적용 내부에서 충돌 비교 로그가 발생할 수 있으므로 그 로그만으로 적용 실패를 판정하지 않는다.

진단은 실제 observer의 서명 fixture 16개와 stderr 쓰기 실패를 RED → GREEN으로 확인했고, 최종 Release 코어 단위 시험 94건 및 독립 검토를 통과했다. debug 전용 인증 control rollback 통합 시험은 변경하지 않았으나 이번 Release 실행에서는 제외됐다. 새 Windows Release는 직전 진단 빌드와 비교하면 DLL만 달라졌고, 실제 비교 출력과 조회 경로 표식을 수집했다. 시험 전용 표식은 Release에서 제외됐다.

충돌 해제 후 `M4-RESTART-02`를 대기시키고 같은 저장 폴더로 PC를 정상 재시작했다. 대기 메시지는 보존됐다. 휴대전화 USB 재연결 후 양쪽 네트워크를 시작했지만 PC에는 계정·기기 상태를 확인하라는 안내가 나타났다. 이 실행의 계정 오류 및 상대 목록 비교 로그는 모두 비어 있었다. 사용자가 PC ‘내 기기’에서 자기 공개 목록의 ‘목록 충돌’을 확인했다. 검토 목록은 데스크톱 1대이며 세대 변경·현재 기기 누락 경고는 없었다. 이는 자기 목록 권한 차단을 확인한 관찰이며 충돌의 최초 원인을 설명하지 않는다.

자기 목록 hold 진단도 기존 판정을 유지하면서 불리언과 순서 비교만 기록하도록 추가했다. 현재 응답과 수용 목록·보류 게시물의 일치 여부, hold 시점의 순서 관계, 시간 유효성·만료 여부를 구분한다. 실제 reconcile 서명 fixture 11개와 stderr 쓰기 실패 시험을 포함한 Release 코어 단위 시험 96건 및 독립 검토를 통과했다. Windows 진단 빌드를 같은 시험 저장 폴더로 정상 교체했다.

사용자가 자기 목록을 다시 조회한 실행에서 고정 비교 출력 2건을 수집했다. 두 출력 모두 기존 충돌·수용 목록이 존재하며, 응답은 수용 목록과 해시가 다르고 세대·전체 기기 구성이 같았다. 응답 순서는 hold 시점의 관찰·할당 high-water보다 낮고, 어떤 보류 packet과도 일치하지 않았다. 미래 시각 검사를 통과했고 만료되지 않았다. 이 비교는 응답이 수용 목록 자체보다 오래됐다는 증거는 아니며, 출력 2건을 수동 조회 2회로 해석하지 않는다. 사용자가 본 문구는 ‘다른 기기에서 목록이 바뀌었다’였지만 실제 기기 구성 변경을 입증하지 않는다. 최초 충돌의 원인은 미확정이고 보안 정책을 완화하는 수정은 하지 않았다.
