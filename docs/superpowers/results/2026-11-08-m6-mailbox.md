## 회복력 시험

`core/chat_core/tests/mailbox_resilience.rs::churning_devices_converge_in_order_with_one_notification_per_unread_text`. 설치마다 실제 core(자기 저장소·엔드포인트·actor·스케줄러)를 띄운다. A=[A1, A2, A3], B=[B1](기록에는 실행되지 않는 B2가 있다). 일정은 고정 시드(`0x4d366d61696c0b14`, splitmix64, M5 방식)로 정한다.

- 메시지 120개(실행 결과 B→A 52개, A→B 68개). 보내는 쪽은 시드로 고른다(A 쪽은 켜져 있는 기기 중 하나).
- 매 단계 20% 확률로 A 기기 하나를 끄거나 켠다(하나는 늘 켜져 있다). 실행에서 28번 껐다 켰다.
- 읽음 20회: 켜져 있는 A 기기 하나가 B의 가장 오래된 안 읽은 메시지 1개~전부를 읽는다.
- 60번째 메시지 직전, A 기기 하나가 꺼진 동안 B1이 B2를 추가하는 Commit 1회. 꺼져 있던 기기는 기록이나 B1의 재전송으로 받는다.
- 페이지 중간 종료 2회: 놓친 B 메시지가 3개 이상인 기기가 다시 켜질 때, 놓친 수의 절반을 저장한 직후 처리를 멈추고(`mailbox_test_halt_after`, cursor 이동·알림 없음) 그대로 죽었다가 다시 켜진다. 실행에서 2회, 그 사이 저장된 텍스트 6개.
- 기기를 끄면 남은 core들이 그 기기와의 세션을 닫는다(`mls_test_close_session`, 전송 계층이 상대가 사라진 것을 알아챈 경우를 흉내 낸다. 시험 하네스의 엔드포인트는 이것을 바로 알아채지 못한다).
- 기기가 다시 켜지면 그 기기가 따라잡을 때까지 기다린 뒤 다음 메시지를 보낸다(Lamport 순서 = 보낸 순서가 되게).

끝에 모든 기기를 켜고 확인하는 것:

1. A1·A2·A3·B1 모두 120개를 **보낸 순서 그대로, 한 번씩** 보인다(`(lamport, installation, msg_id)` 정렬 = 보낸 순서).
2. B의 메시지 52개 각각의 읽음 상태(`seen_local`)가 세 기기에서 같고, 어느 A 기기에서 읽었는지와 일치한다. B1에서는 읽은 메시지가 모두 `읽음`이다.
3. 기기마다 알림 이벤트의 `new_messages` 합 = "그 기기가 아직 아무 데서도 읽지 않았을 때 처음 저장한 B 메시지 수". 읽은 뒤에 처음 저장한 것은 0. 실행 결과 A1 32/32, A2 43/43, A3 45/45.
4. 모든 기기의 epoch가 B1과 같고(Commit 적용), `missing`(평문 넘김 `NoPlain`) 0.

**첫 실행 결과.** 첫 실행부터 통과했다(34 s). 제품 결함은 나오지 않았다. 시험이 실패를 잡을 수 있는지 보려고 `notify_items`의 `seen_local=0` 조건을 지운 소스로 한 번 돌렸더니 `A1: notifications 49 ≠ 32`로 실패했다(되돌림).

**알림 기대값과 중간 종료.** Task 14 때는 알림 합의 기대값에서 "죽은 실행이 저장한 텍스트"를 뺐다(그 텍스트는 알림 없이 남았다, spec §3·§4와 어긋남). 사용자 결정(2026-11-08, Ruling 35)으로 이것을 고쳤고(아래 "최종 리뷰 수정" I4), 이제 기대값에 **죽은 실행이 저장한 텍스트 중 그때 아직 읽지 않은 것**도 들어간다. 다음 실행이 그것을 알린다.

**연속 5회:** `cargo +1.92.0 test --locked -p chat_core --features test-hooks --test mailbox_resilience -j 6` 5회 모두 통과(33.0–34.3 s). 시드가 같아 일정(텍스트 120, 읽음 20, 껐다 켬 28, 중간 종료 2)은 매번 같고, 실제 스레드 순서만 다르다.

## 측정

명령:

```
CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true cargo +1.92.0 test --release --locked -p chat_core --features test-hooks --test mailbox_resilience -- --ignored thousand_entries_transfer --nocapture
```

시험 hook(`storage_fixture` 등)은 `test-hooks`와 `debug_assertions`가 모두 있을 때만 컴파일된다. 그래서 brief의 명령 그대로(`--release`만)는 **시험 0개**가 돈다(확인함: `running 0 tests`). 최적화(opt-level 3)는 그대로 두고 debug assertion만 켜서 쟀다. overflow 검사는 Release 기본값(꺼짐) 그대로다.

시험 `thousand_entries_transfer`(`#[ignore]`): A=[A1, A2], B=[B1]. A1이 꺼진 동안 B1이 1 KiB Text(본문 1,024 B) 1,000개를 50개씩 A2에 보낸다.

**메시지당 `mailbox_store` 크기.** A2가 기록한 1,000개 항목을 다른 계정의 쉬는 core 하나의 기록에 그대로 다시 넣고(`mailbox_record_as`), 그 DB의 `page_count × page_size` 차이를 1,000으로 나눴다(`pragma_page_count()`·`pragma_page_size()`. SQLCipher는 `PRAGMA page_size`를 직접 받아 다른 값을 돌려준다).

| 실행 | 항목당 | 본문 평균 | A2 DB 전체 증가 (메시지당) |
| --- | --- | --- | --- |
| 1 | 4,165 B | 2,778 B | 6,217 B |
| 2 | 4,165 B | 2,778 B | 6,221 B |
| 3 | 4,165 B | 2,778 B | 6,213 B |

본문 2,778 B는 kind 17 `App` inner(1 KiB 평문이 2 KiB 버킷으로 패딩되고 MLS 암호화·서명·헤더가 붙은 것)다. 항목당 4,165 B 중 나머지 약 1.4 KB는 행의 다른 열(id 3개 96 B, 해시 32 B 등), `hash` UNIQUE 색인, `recorded_at_ms` 색인, 그리고 **4 KiB 페이지의 1/4을 넘는 행이 overflow page로 넘어가며 남는 빈 공간**이다. 30일 보관 상한에서 하루 1 KiB 메시지 1,000개면 약 125 MB가 된다(내 다른 기기가 모두 가져가면 그 전에 지워진다). 이는 spec §5.2의 설계자 추정(하루 1,000통 × 30일 ≈ 45 MB)의 약 2.8배다(1 KiB 평문이 2 KiB 버킷 패딩과 MLS로 약 2.7 KB가 되고, 행이 overflow page로 넘어가기 때문). A2 DB 전체 증가(메시지당 약 6.2 KB)에는 기록 외에 `message`·`processed_ct`·MLS 상태가 들어 있다.

**1,000건 넘김 시간.** A1이 같은 저장 폴더로 켜지고(core 시작 0.04–0.05 s) A2·B1에 닿을 수 있게 된 뒤 `mailbox_sync_now`부터, 1,000개가 모두 저장될 때까지와 A2 기록을 다 처리(cursor 끝)할 때까지.

| 실행 | 1,000개 저장 | 기록 처리 끝 | 항목당 | 알림 |
| --- | --- | --- | --- | --- |
| 1 | 1.747 s | 1.748 s | 1.75 ms | 1회 (`new_messages` 1,000) |
| 2 | 1.756 s | 1.770 s | 1.77 ms | 1회 |
| 3 | 1.849 s | 1.850 s | 1.85 ms | 1회 |

이 시간에는 A1→A2 세션 연결·인증, 페이지 요청(항목 64개 또는 inner 61,434 B 중 먼저 닿는 쪽: 이 크기면 페이지당 약 21개, 약 48페이지로 추정), MLS 열기, 항목마다 SQL 트랜잭션 하나가 들어 있다. 같은 PC 루프백이라 네트워크 지연은 거의 없다. 참고로 B1이 1,000개를 보내는 데는 16.6–16.7 s가 걸렸다(메시지마다 kind 17 왕복과 A2의 저장).

**기기 확인 (미측정).** spec 11의 "폰 비행기 모드 → PC가 받음 → 폰 복귀 후 같은 LAN에서 5 ms 안팎으로 받음"과 LTE 복귀는 실제 폰·PC가 필요해 사용자와 함께 볼 항목으로 남겼다. ④ 시나리오는 복귀 후 저장까지 걸린 시간을 `mailbox-public-evidence.jsonl`의 `return_to_stored_ms`로 남기지만, 그 값에는 비행기 모드 해제와 재연결이 들어 있고 에뮬레이터·CI 환경이라 이 항목을 대신하지 않는다.

## 평문 넘김에 별도 키를 두지 않은 근거

설계 3.6절은 평문 넘김에 "별도 대칭키"를 말하지만 spec 12절이 구현자 판단에 맡겼고, 두지 않았다.

- 평문 기록(`PlainReq` → `Plain`)은 kind 18로만 오가고, kind 18은 **내 계정의 해제되지 않은 기기와의 인증된 account 세션**에서만 처리된다(`grant.peer == 내 peer`, `grant_authorized`, 해제 확인을 요청 전후 두 번). 세션은 InstallationCert 상호 인증 위의 QUIC TLS 1.3이라 전송 중에는 이미 기밀·무결성이 있다. 그 밖의 세션은 `Refused`(Task 7 `revoked_device_open_session_gets_nothing`, 다른 계정 거부 시험).
- 저장 시에는 받은 기기의 SQLCipher DB(기기 키 보호) 안의 `message` 행으로 들어가고, 넘겨주는 쪽은 자기 `message` 행에서 그때 읽는다. 따로 쌓아 두는 평문 사본이 없다.
- 별도 대칭키를 두면 그 키를 내 기기들에 나눠 주고 기기 해제 때 돌려야 하는데, 그 배포 경로가 바로 같은 인증 세션이다. 보호가 더해지지 않고 관리할 비밀만 하나 는다.
- 남는 위험은 세션 끝점(내 기기 자체)의 탈취이며, 이것은 별도 키로도 막지 못한다.

## `NoPlain`으로 빠지는 경우

열지 못한 항목을 평문으로 달라고 했는데 보관 기기가 `NoPlain`이라 답하면 그 항목은 건너뛰고(cursor는 지나간다) `missing` 카운터가 1 오른다. 보관 기기의 `plain_record`가 `None`인 경우다.

1. 그 항목이 Text 메시지가 아니다: receipt(내 Read receipt 포함), Commit·Welcome처럼 `msg_id`가 없는 kind 1 항목. 평문 기록은 Text만 있다. 내 Read receipt를 열지 못하면 읽음 상태가 그 기기로 오지 않는다(알려진 한계).
2. 보관 기기에 그 메시지 행이 없다: 그 대화를 지웠거나, 보관 기기도 그 메시지를 열지 못했다(손상된 암호문 — `mailbox_sync.rs::mailbox_entry_failure_sends_no_decrypt_failed_to_sender`).
3. 그 사이 그 항목이 보관 기기 기록에서 지워졌다(30일 정리).

열지 못한 Commit은 평문 넘김이 아니라 Ruling 25의 보류·레코드 조회로 다룬다. 회복력 시험과 ④에서 `missing`은 0이다.

## 알려진 한계

- **열지 못한 내 Read receipt는 잃는다.** 평문 넘김은 Text만 있어 보관 기기가 `NoPlain`으로 답한다. 그 메시지가 이 기기에도 있으면 여기서는 안 읽음으로 남는다(다른 기기에서 다시 읽거나 여기서 읽으면 맞춰진다).
- **`missing` 카운터에 receipt도 들어간다.** "빠진 메시지 수"가 아니라 "`NoPlain`으로 건너뛴 항목 수"다(시험 전용 카운터, 주석에 적음).
- **Android에서 최근 앱 목록으로 쓸어 없앤 뒤**에는 서비스와 core는 돌지만 앱을 다시 열 때까지 Dart 알림이 나오지 않는다(M7 범위).
- **Android API 26–33의 `startForeground` 경로는 시험하지 않았다.** CI 에뮬레이터는 API 36뿐이다.
- **Windows 트레이 메뉴, 더블클릭, 풍선 누르기는 자동 시험에서 다루지 않았다**(통합 시험은 트레이 추가·창 숨기기·전원 요청까지).
- **바깥에서 보낸 bare `WM_QUIT`**은 Flutter 템플릿 teardown에서 0xC000041D로 끝난다(M6 이전부터, 앱 경로에는 없음).
- **알림 id는 대화 id 앞 32비트**라 이론상 두 대화가 같은 id를 쓸 수 있다(무시할 수준).
- **알림 권한은 한 번만 묻는다.** 거절하면 사용자가 설정에서 켤 때까지 거절 상태로 남는다.
- **죽은 실행의 알림이 늦을 수 있다(I4).** 다시 켜진 뒤 그 보관 기기와의 pull이 끝나야 알리고, 그 기기에 닿지 못하면 시작 60 s 뒤에 알린다. pull이 "다른 기기에서 읽음"으로 찾은 대화(알림을 지우거나 고칠 것, 새로 울리지 않음)는 표시로 남기지 않는다. 죽으면 그 갱신은 다음 맞추기 때 온다.
- **그룹이 없을 때의 읽음(I2).** 읽는 순간 그 대화의 MLS 그룹이 없으면 Read receipt를 봉인하지 못해, 전처럼 그룹이 생길 때(상대와 연결될 때)까지 내 다른 기기에도 가지 않는다.
- **시험이 흉내 낸 것.** 회복력 시험은 꺼진 기기의 세션을 시험 hook으로 닫는다(하네스 엔드포인트가 바로 알아채지 못함). 실제 망에서 죽은 세션을 알아채는 시간은 QUIC idle timeout과 Ruling 23 규칙에 달려 있고 여기서 재지 않았다.

## CI

사용자가 이 브랜치의 push를 CI용으로 허락했다("CI 돌리는 용", PR은 만들지 않음).

- push CI(`ci.yml`, 9개 job): 코드 커밋 `4e60afc` push로 run 42398120629가 시작되었고, 이 문서 커밋의 push가 그것을 취소하고 같은 코드로 다시 돈다(브랜치 run은 cancel-in-progress). 최종 run id는 `task-14-report.md`와 작업 기록에 적는다. 직전 커밋 `917205b`의 run 42392478868은 9개 job 모두 통과(Task 11–13의 Windows·Android 통합 시험 포함).

- 최종 리뷰 수정의 push CI run id는 `final-fix-report.md`에 적는다.
- **e2e 연결은 이제 relay부터 (Task 18, `0502886`).** 시험용 `NetworkProfile::Local`(test-hooks debug 빌드에만 있고 puppet `configure_local`로만 고른다)에 relay가 있으면 그 ticket에 relay만 적는다. 에뮬레이터에서 노드로 가는 handshake를 relay와 모든 직접 주소로 한꺼번에 보내면 에뮬레이터의 user-mode NAT를 지나며 dial 기한까지 끝나지 않았기 때문이다(근거와 run id는 `task-18-report.md`). 그래서 e2e는 Windows job까지 모든 연결을 relay로 시작하고 직접 경로는 그 뒤 NAT traversal로 찾는다. **e2e는 더 이상 Public ticket 모양(relay + 모든 직접 주소, `endpoint.addr()`: 네트워크 화면과 M2 Connect)을 쓰지 않는다.** 그 모양으로 여러 직접 주소에 handshake를 보내는 경로는 e2e가 덮지 않는다. 실기기는 영향이 없다: `Local` 프로필은 release 빌드에 없고, 계정 dial은 Public에서 DHT relay-only 조회라 처음부터 relay로 시작한다.
