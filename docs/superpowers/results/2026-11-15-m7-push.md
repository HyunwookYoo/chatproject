검증일: 2026-11-15 KST. 기준 소스는 브랜치 `HyunwookYoo/m7-push`의 Task 1–13 커밋(`83f8bac`까지)에 Task 14 변경을 더한 것이다. ## ④ 다기기 시나리오 (`m7`)

`tools/e2e/lib/src/push_scenario.dart`, `dart run tools/e2e/bin/run.dart --profile android --scenario m7 --repo-root <절대 경로>`.

- **구성.** A1 = 에뮬레이터 1대의 디버그 앱(`android-1`), A2 = `chat_node puppet --account`(`mailbox`, A의 메일박스), B1 = `chat_node puppet --account`(`node`). 러너에서 `push_proxy --fake-upstream-url`(feature `fake-upstream`, Ruling R6)을 `127.0.0.1:8787`에 새 handle 키로 띄운다. 앱은 `adb reverse tcp:8787`로, 노드는 직접 닿는다. 프록시는 FCM 대신 각 `Delivery`를 하네스의 loopback HTTP 받는 곳에 JSON으로 넘기고, 하네스가 `adb shell am broadcast -n dev.chatproject.chat_app/.TestPushReceiver -a dev.chatproject.chat_app.TEST_PUSH --es t … --es e|w|r …`로 앱에 넣는다. 프록시의 경로·rate limit·지터·로그는 진짜 그대로다.
- **앱 설정.** 설치는 `adb install -r -g`(알림 권한 미리 허용, 권한 화면이 막지 않음). `am start`에 `chat_push_url`을 주면 디버그 빌드의 `MainActivity`가 Dart에는 `--push-url`로, Kotlin에는 `NativeCore.debugPushUrl`(→ `native_start(push_url)`)로 넘긴다. Dart의 `push_configure`가 설정 전체를 바꾸므로 둘 다 필요하다(Task 12 메모). 받는 쪽의 차가운 프로세스가 코어를 기본 저장 경로에서 시작하므로 `m7`은 `chat_data_dir`를 주지 않는다. Firebase가 없으므로 토큰은 puppet `push_local_set_token`으로 가짜 값을 준다.
- **흐름.**
  1. A1 계정 만들기 → A2를 같은 계정으로 연결 → B1 계정, 연락처(A1·A2가 B1을 `push fixture`로 저장), 경로 → B1이 첫 텍스트(그룹) → A2 메일박스 켬 → A1 토큰 → B1에 A1 handle(`push_local_test_counts.peer_handles`), A2에 A1의 내 기기용 handle(`own_handles`) 도착 → A1이 첫 텍스트를 읽음.
  2. A1 홈 키 뒤 `am kill`(프로세스 없음, 알림은 남음) → B1 텍스트 → 프록시 → `cipher` → 브로드캐스트가 차가운 프로세스를 띄움 → `dumpsys notification --noredact`에서 제목 = 별칭, 본문 = 미리보기(Ruling R19) → 앱을 다시 열면(`force-stop` 뒤 `am start`) 텍스트가 한 번만 있다.
  3. A1 `network_stop`(A2·B1이 세션 없음으로 볼 때까지) → B1 텍스트 → `cipher` → 알림 본문 `"<미리보기> 외 1개"` → A2가 두 텍스트를 읽음 → A2의 `read` 푸시 → A1이 내 기기와 맞추기 → 알림이 지워짐.
  4. B1이 16 KiB 텍스트 → `wake` → A1이 "새 메시지"를 띄우고 받아 와서 미리보기로 고침(일반 알림이 보였는지는 증거에 `generic_seen`으로만 남긴다. 받아 오기가 하네스의 읽기 간격보다 빠를 수 있다) → A1에 텍스트 4개가 한 번씩, 알림 하나, 남은 푸시 없음.
- **진단.** 진단 파일에 `push` 하나를 더했다: `push_items`(`cipher`·`wake`·`read` 수), `push_results`(받는 곳이 받은 수·거절한 수), `broadcasts`, `notifications`(앱의 메시지 알림 수). 수만 있고 본문·토큰·tag·handle은 없다. `write_e2e_summary.py`가 키와 값의 모양을 검사한다(스키마 11). 실패 문구(`Push scenario: …`, `Push scenario deadline: …`)와 참가자 `mailbox`를 `diagnostic_details.json`에 더했다. 컨트롤러는 `push_local_*` 결과와 오류 detail을 진단 로그에 남기지 않는다.
- **CI.** `e2e.yml` android 작업의 회귀 반복에 `m7`을 더했다(에뮬레이터 1대). 두 번 연속 GREEN은 **남음**.
- **`m7-fcm`(실제 FCM).** 같은 시나리오의 1–2단계만, 가짜 upstream 없이 진짜 FCM 발송으로 돈다. 토큰은 앱의 Firebase가 Dart로 넘긴다. `android-fcm` 작업(schedule·dispatch만, environment `push-e2e`)이 Google Play 이미지(`E2E_AVD_PROFILE=local` → `google_apis_playstore` API 36)로 돌린다. 두 시크릿은 `run:` 단계의 `env`에서 `$RUNNER_TEMP` 아래 파일로만 쓰고(규칙 (a)(c)), `google-services.json`은 그 작업 안에서 빌드 직전에만 `app/android/app/`에 복사하며 마지막에 지운다. 산출물을 올리지 않고 요약은 step summary에만 쓴다.

| R12 | 보낼 때 푸시가 꺼져 있었으면 `pushed=0`으로 두고, 나중에 켜졌을 때 아직 전달 안 됐으면 한 번 푸시 |
| R13 | 일반 알림("새 메시지") 뒤 그 대화의 텍스트는 읽을 때까지 울리지 않고 조용히 고친다(`push_tag.generic`) |
| R14 | JNI 재연결(`NativeInit`)을 Task 10으로 |
| R15 | 갱신의 네트워크 사용은 코어의 푸시 `NetworkUse` 임대를 통해서만 |
| R16 | `google-services.json`이 있을 때만 Google services 플러그인·Firebase 사용. 없으면 디버그 `TestPushReceiver`로 시험 |
| R17 | WorkManager의 부팅 재예약 수신기 허용(서비스·알림 시작 없음), 밀린 갱신이 부팅 뒤 코어를 잠깐 시작할 수 있음 |

## Announce 3/4 필드 호환 한계

kind 18 `Announce`는 M6에서 `[1, 4, bool]`(3 필드)였고 M7은 내 기기용 handle을 실어 `[1, 4, bool, handle_bytes_or_null]`(4 필드)를 보낸다. M7 디코더는 3·4 필드를 모두 받는다. **M6 디코더는 4 필드를 거절하므로, M6 기기는 M7 기기의 Announce에 `Refused`로 답한다.** 그 사이 M6 기기는 M7 기기의 메일박스 표시와 내 기기용 handle을 알지 못한다(메일박스 인계 대상이 되지 않고 읽음 정리 푸시도 보내지 않는다). 받아들였다: M6 기기는 곧 갱신되고, 갱신 뒤 다음 세션에서 Announce가 다시 오간다.

## 미룬 minor (작업별)

작업별 검토가 고치지 않고 넘긴 것이다. 최종 전체 리뷰가 분류한다.

- **Task 2 (프록시 경로·제한).** `cipher_fits` 문서가 Task 3 전까지 과장(Task 3에서 해소). IP 429 전에 본문을 읽음. handle당 제한은 한 토큰으로 handle을 많이 만들면 곱해짐, IPv6 /64 순환(VPS 전에 결정). APNs `read` 거절이 판단 코드의 플랫폼 분기. 열린 연결 수 상한 없음(각각 시간 제한은 있음). 응답 쓰기 시간 제한 없음. `ConnectInfo` 클라이언트 IP가 끝까지 시험되지 않음.
- **Task 3 (발송).** APNs 연결 풀 idle 90 s(spec "HTTP/2 연결 하나 유지"와 차이). FCM 토큰 가져오기 실패에 백오프 없음. 거절된 자격(401/403, APNs 403)이 캐시에 남음. `with_root`/`with_clock`/`reqwest::Url` 공개가 게이트 없음. 상태 분류가 `deliver` 안에. FCM data 두 번 직렬화, `rsa` dev-only가 `lazy_static spin`을 켬.
- **Task 4 (MLS).** `OpenedPushHandle`은 행이 바뀔 때만. RED가 통합 시험 컴파일 실패로만. `nse.rs:733` 중복 길이 검사. `nse_decrypts_stripped_ciphertext`가 `--features nse`에서만 돎(CI가 덮는지 최종 확인).
- **Task 5 (스키마 v4).** 새 DB 경로의 seed 오류 이름(`upgrade_failed` vs `corrupt`). v3→v4 시험이 `mailbox_*` 표 일부를 건너뜀. `downgrade_to_v3` DDL을 실제 v3 schema와 대조하지 않음. rustfmt 모양 몇 곳.
- **Task 6 (handle 수명).** `push_reload` 오류 조기 반환이 갱신 대기자를 남김. Seal 재시도에 백오프 없음. 순차 갱신이 첫 오류에서 멈추고 `/handle` IP당 분당 30이라 대화 30개 넘으면 회복이 느림. `push_set_token`이 설정된 플랫폼을 덮음. 끄기 커밋과 세대 이동 사이 틈. `Delivered` 노트의 `push_delivery` 정리·플랫폼 없는 기기의 `set_token` 시험 없음. `push_store.rs` 약 1,000줄. `PushRequest`의 Debug에 handle. 첫 tick 전 내 기기 handle 변경이 다시 알리기를 건너뜀. ticket 불일치 경로의 한 번 더 도는 것.
- **Task 7 (보내는 쪽).** `pushed=1` 뒤 재시도마다 Seal 왕복과 wire 읽기. 결정 때 현재 installation이 비면 영구 누락. 시험 빈틈(재시작 뒤 `pushed`, Welcome·프록시 없음, 큰 텍스트는 원래 길이로 단언). 긴 줄, import 순서. 첫 시도 전 인계는 `reached=[]`로 결정해 첫 시도로 닿은 기기도 푸시를 받을 수 있음(받는 쪽 한 번 알림이 덮음).
- **Task 8 (받는 쪽).** `Notified` 문서와 R13의 조용한 wake. Wake/Fetch의 actor 전송이 기한에 묶이지 않음. 같은 대화의 다른 새 텍스트에 받아 오기 완료가 걸릴 수 있음. `NetworkOp::Start` 중 취소가 stop을 잃음, 런타임 없는 Drop이 사용자 수를 샘. 겹치는 wake가 waker를 바꿔 stop/start 반복. 시작 카운터가 실패한 시작도 셈. `Info` 뒤 `before` 읽기의 미세한 경합. `store_text`의 `if seen` 정리 경로 단독 시험 없음. R13: 일반 알림보다 오래된 내 읽음이 표시를 지워 두 번째 알림 가능, 지운 항목 없이 표시만 지워 알림이 남을 수 있음.
- **Task 9 (FFI).** 실패한 받아들이기 묶음이 `inbox.taken.jsonl`을 남김(NSE 쪽 무한). `push_ingest_inbox`가 async FRB 작업 안에서 블로킹 파일 읽기(≤8 MiB). `renew_status_codes` 시험이 느슨함. scene의 대기 중인 suspend가 갱신 중에 다시 잠글 수 있음(좁고 안전한 끝 상태). 다시 잠그기가 best-effort, 문서 과장. `timeout_ms<2 s`도 resume 한 번. `account_suspended()`가 바란 상태를 보고. 한 시험이 이전 코드에서도 통과. `CoreSlot`이 iOS scene 개념 이름.
- **Task 10 (Android).** 8 s 예산이 코어 시작 시간을 빼지 않음. 매일 갱신이 푸시 꺼짐·권한 없음에도 코어를 시작. `NativeInit` 끝나기 전 WorkManager 실행 가능(무해). `AlreadyStartedDifferentConfig` 대체가 디버그에 한정되지 않음. 최종 확인: 앱 안에서 읽을 때 코어가 취소 항목을 내는지(Dart `cancelNotification`이 Android에서 no-op). wake 후속 판단은 시간 기반(마지막 약 1.5 s에 온 텍스트는 다시 돌림).
- **Task 11 (iOS).** 빈 본문을 "조용함"으로 처리(빈 텍스트를 보내면 숨겨짐). 시작 때 없는 파일만 써서 차가운 BG 갱신·별칭 변경 뒤 오래된 파일. BG 만료 때 SQLite 잠금 중 끝낼 위험(0xdead10cc). 보호 등급 시험이 시뮬레이터에서는 공허함, no-alias 일반 알림이 "새 메시지" 두 번. `guarded()`만 시험하고 `nse_open`은 아님. 기본 panic hook이 stderr에 씀.
- **Task 12 (Flutter).** iOS에서 거절 상태로 시작한 뒤 다시 켜면 다시 시작할 때까지 토큰 없음. OS 설정에서 돌아오면 스위치가 꺼진 채, "나중에" 뒤 이유 문구·플랫폼 차이. 꺼진 동안 resume마다 `push_set_enabled(false)` 쓰기. iOS 누르기 경로가 4바이트 `notificationId` 왕복, `_askPush`가 푸시된 경로 아래 `_page`를 바꿀 수 있음, iOS 채널 처리기 dispose 안 함. 설정 스위치가 토큰을 기다림(≤5 s), Kotlin의 대기 중 `MethodChannel.Result`가 쌓일 수 있음.
- **Task 13 (CI).** 시크릿 env의 `toJSON(secrets)` 허용, 규칙 (c)의 쓰기 탐지 한계(cp/mv/dd, `>|`, 나중 복사), run 단계의 `with` 허용, 시험 하나가 bash에 묶임. TestFlight 이월 6의 나머지(이른 시크릿 확인, IPA `find`, identity 수)가 workflow 셸.

## 알려진 한계

- **iOS 읽음 정리 없음.** spec 7대로 iOS에는 `read` 푸시를 보내지 않는다. 앱을 열거나 다시 연결될 때 M6 맞추기로 지워진다.
- **큰 메시지.** 버킷(2,900 B)을 넘으면 `wake`이다. Android는 받아 오면 내용으로 바꾸고, iPhone은 "새 메시지"로 남는다. 받아 오기가 20 s 안에 끝나지 않으면 Android도 "새 메시지"로 남는다.
- **`read`는 일반 우선순위**라 Doze 중이면 몇 분 늦게 온다(사용자 결정).
- **모르는 tag 푸시의 iOS 표시.** 알림 필터링 entitlement 없이 빈 `UNNotificationContent`가 알림을 숨기는지는 기기 확인 전까지 모른다(spec 8.2는 그 전까지 "새 메시지"를 받아들인다).
- **처리한 암호문 목록(iOS).** 별도 파일 대신 inbox 안의 같은 `(t, e)`로 확인한다(NSE가 앱 DB를 읽을 수 없음). inbox가 비워진 뒤 같은 암호문이 다시 오면 NSE가 한 번 더 보일 수 있다(앱이 받아들일 때는 `processed_ct`로 한 번만 저장).
- **handle은 30일 산다.** 철회한 tag나 지운 대화로 푸시가 올 수 있고, 받는 쪽은 아무것도 띄우지 않는다(Review Focus 1).
- **프록시 남용 방지.** handle당 제한은 토큰을 확인하지 않아 한 토큰으로 handle을 많이 만들면 곱해진다. IPv6 /64 순환. VPS 전에 정한다(Task 2 minor).
- **e2e가 흉내 낸 것.** `m7`의 푸시는 FCM이 아니라 하네스의 브로드캐스트로 들어간다(디버그 수신기, 같은 처리 함수). 실제 FCM은 `android-fcm`(시크릿 필요)과 기기 확인이 본다. 3·4단계는 A1을 앞에 둔 채 `network_stop`으로 떨어뜨린다(뒤로 간 앱은 cached-app freezer에 얼어 제어 RPC가 멈출 수 있다, M6과 같음).
