# M5 — MLS 1:1 설계

- 날짜: 2026-11-01
- 상태: 사용자 승인 (2026-11-01, builder check 반영)
- 상위 문서: [P2P Chat 설계](2026-10-04-p2p-chat-design.md) 4.4·6·7·11·12.3절, [로드맵](../plans/2026-10-04-p2p-chat-roadmap.md) M5, [M4 설계](2026-10-21-m4-storage-outbox-design.md) 11절, [M1b 이월](../plans/2026-10-11-m1b-carry-forward.md) "M5와 M7"
- 표기: **사용자 결정**은 이번 대화에서 사용자가 정한 것, **설계자 판단**은 설계자가 정했고 사용자가 검토 중에 바꿀 수 있는 것이다. 표시가 없는 것은 상위 문서에 이미 확정된 내용이다.

## 1. 의도

M4까지 메시지 내용은 기기 사이 iroh/QUIC 연결 구간에서만 암호화된다. M5는 1:1 대화의 메시지 내용 자체를 MLS로 종단간 암호화한다. 같은 암호문이 늦게, 두 번, 순서 없이 와도 받아낸다. M6(메일박스)·M7(푸시)·M8(큐)이 암호문을 저장하고 넘겨줄 수 있게 하는 기반이다. 그 경로들은 내용을 볼 수 없어야 하기 때문이다.

사용자에게는 거의 보이지 않는 마일스톤이다. 잘 되면 화면은 M4와 같다.

## 2. 목표·비목표·실패 조건

**목표**

1. 1:1 대화의 모든 텍스트 메시지와 receipt를 MLS `PrivateMessage`로 보낸다.
2. 지연(과거 epoch 5개 이내)·중복·순서 뒤바뀜(200개 이내) 수신을 받아낸다. 범위 밖은 자동 복구(6절)로 처리한다.
3. 대화의 MLS 멤버는 양쪽 계정의 현재 기기 전부다. M3 기기 목록 변화를 따라 멤버가 바뀐다.
4. M4 기록과 미전송 메시지를 잃지 않고 넘어온다(8절).
5. iOS 알림 확장이 쓸 읽기 전용 복호 경로를 만든다(10절). 실제 알림 연결은 M7이다.
6. 1 KiB 암·복호 1 ms 미만. 메시지당 저장 쓰기량을 바이너리 저장에서 다시 잰다(스파이크 B는 JSON 437 KiB).

**비목표**: MLS 그룹(3명 이상, M9), 메일박스(M6), 푸시 수신·표시(M7), 큐 서버·시퀀서(M8), 첨부(M10), 주기적 키 갱신(Update) 스케줄, 초대장 v2(KeyPackage 포함 `Invite`), 대화 정보 화면, 기기 변경 표시 UI.

**실패 조건** (기술적으로 돌아가도 실패로 본다)

- 어떤 경우에도 MLS가 아닌 평문 frame으로 새 메시지가 나간다. 실패 시 M4 codec으로 내려가는 것 포함.
- 업데이트 뒤 M4 기록이나 미전송 메시지가 사라지거나 대화방에서 안 보인다.
- 같은 메시지가 두 번 표시된다(재암호화 재전송 포함).
- 받는 쪽 화면에 복호 실패가 드러난다.
- MLS 상태와 메시지 저장이 어긋난 채로 커밋된다(한쪽만 저장).

## 3. 사용자에게 보이는 것

| 항목 | 결정 |
|---|---|
| 기존 M4 대화 기록 | **사용자 결정:** 대화방을 열면 그대로 보인다. M5 메시지와 같은 목록, 같은 정렬 `(lamport, sender_installation, msg_id)`. |
| 미전송 M4 메시지 | **사용자 결정:** 업데이트 뒤 MLS로 암호화해서 보낸다. 상대가 아직 M5가 아니면 `보내기 대기`로 남는다. 암호화하지 않고 보내는 경로는 없다. |
| 상대 기기 추가·해제 | **사용자 결정:** 대화방에 표시하지 않는다. 내부 기록만 남겨 나중에 대화 정보 화면에서 "상대 기기 N대"처럼 보일 여지만 둔다. |
| 복호 실패 | **사용자 결정:** 받는 쪽 화면에 띄우지 않는다. 보내는 쪽이 자동으로 다시 암호화해서 보낸다(6절). 계속 실패하면 보내는 쪽 메시지가 기존 `전송 실패`가 되고 기존 다시 보내기를 쓴다. |
| 개발 상태 안내 | **설계자 판단:** M4의 "종단간 암호화 없음" 안내를 "종단간 암호화됨"으로 바꾼다. 기존 M4 기록 앞에 따로 구분선은 넣지 않는다. |
| 상태 표시 | M4와 같다: 저장 중 → 보내기 대기 → 전송됨 → 전달됨 → 읽음, 보류·실패·취소. |

## 4. 대화 그룹

### 4.1 구성

- 1:1 대화(M4 `conversation`, 상대 PeerId 하나)마다 MLS 그룹 하나.
- 멤버(leaf)는 **installation 단위**: 내 계정의 현재 기기 전부 + 상대 계정의 현재 기기 전부. "현재 기기"는 M3가 검증한 IdentityRecord/로컬 기기 목록이다(초기 상한 5대).
- 사이퍼수트 `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, OpenMLS 0.9(이미 `chat_nse`·`tools/nse_fixture`에 `=0.9.0`으로 고정됨), `max_past_epochs = 5`, `out_of_order_tolerance = 200`, `maximum_forward_distance = 1000`.
- 그룹 생성·멤버 변경은 MLS Commit(by-value proposal)으로만 한다. proposal은 그룹에 보내지 않는다(상위 6.1절).

### 4.2 MLS 자격 증명 (설계자 판단)

- installation마다 **MLS 전용 Ed25519 서명 키**를 새로 만든다. iroh 전송 키를 MLS 서명에 재사용하지 않는다(프로토콜 간 키 재사용 금지).
- leaf credential에는 `(PeerId, InstallationId, MLS 서명 공개키)`와, 그 installation의 전송 키가 도메인 분리 문자열(예: `ChatProject/mls-credential/v1`)로 서명한 바인딩을 담는다. 전송 키는 이미 M3 `InstallationCert`로 계정 IdentityKey에 묶여 있으므로, 받는 쪽은 credential → InstallationCert → IdentityKey 순서로 검증한다. M3 인증서 형식과 pkarr 레코드는 바꾸지 않는다.
- 멤버를 받아들일 때(Welcome 처리, Commit 적용, 메시지 수신) leaf가 상대 또는 나의 **현재** 기기 목록에 있는지 확인한다.
- **목록에 없는 기기 (설계자 판단):** 내 캐시가 늦었을 수 있으므로 바로 거부하지 않고 보류한다. 그 계정의 기기 목록을 M3 규칙대로 새로 조회한 뒤 다시 판정한다. 새 목록에도 없으면 거부한다. 레코드를 가져올 수 없거나 충돌 상태면 해결될 때까지 보류하고, 보류 항목 수에 상한을 둔다. 보류 중에 그룹이 갈라지면 4.6절의 재가입으로 복구한다.
- 키 저장 위치·직렬화는 기존 계정 비밀과 같은 보호(M3/M4의 OS 보호 + SQLCipher) 안이면 구현자가 정한다.

### 4.3 KeyPackage (설계자 판단)

- M3의 `IdentityInvite v1`을 유지한다. 초대장에 KeyPackage를 넣는 `Invite v2`는 M5에서 만들지 않는다. M5의 전송은 M4처럼 직접 연결뿐이라, 연결된 상태에서 받으면 충분하다.
- 인증된 M3 연결 위에 KeyPackage 요청·응답 frame을 추가한다. 응답하는 기기는 1회용 KeyPackage를 새로 만들어 주고, 쓰인 KeyPackage의 private 재료는 Welcome 처리 뒤 지운다.
- last-resort KeyPackage는 M5에서 쓰지 않는다. 오프라인 상대에게 KeyPackage를 받는 일은 M6/M8에서 다시 본다.

### 4.4 생성, 합류, 두 그룹 (설계자 판단)

**전제:** 대화 기록은 각 기기의 로컬 DB에 있고 MLS 그룹 상태에 들어 있지 않다. 그래서 그룹을 바꾸거나 다시 만들어도 기록은 사라지지 않는다. 비용은 아직 수신 확인을 받지 못한 메시지를 다시 암호화하는 것뿐이다. 아래 규칙은 이 전제에 기댄다.

- **먼저 묻는다:** 그룹 상태가 없는 기기(새 대화, 새 기기, 재설치, 복구 후)는 보낼 메시지가 생기면 먼저 직접 연결된 상대 기기와 내 다른 기기에 "이 대화의 그룹이 있는지"를 묻는다. 그룹이 있다고 답한 기기에 합류를 요청하고, 그 기기가 Add Commit과 Welcome을 만든다(4.5절).
- **없으면 만든다:** 아무도 그룹이 있다고 답하지 않으면 그 기기가 그룹을 만든다. 연결할 수 있는 상대 기기와 내 다른 기기의 KeyPackage를 받아 Add하고 Welcome을 보낸다. 연결할 수 없는 기기는 나중에 합류한다.
- **Welcome을 기다리는 동안:** 합류 요청 뒤 Welcome이 오기 전에 쓴 메시지는 outbox에 원문으로 남겨 두고, 합류 뒤 암호화해서 보낸다.
- **그룹이 둘이면:** 동시 생성이나 합류 질문이 닿지 않은 경우처럼 한 대화에 그룹이 둘 생길 수 있다. 어느 기기든 두 그룹을 알게 되면 **언제나 같은 규칙**으로 하나를 고른다: 각 그룹의 첫 Commit 해시를 비교해 작은 쪽. 그룹의 나이나 크기는 보지 않는다. 진 그룹의 기기는 그 그룹을 버리고 이긴 그룹에 합류를 요청한다. 진 그룹으로 보냈지만 수신 확인이 없는 메시지는 이긴 그룹에서 다시 암호화해 보낸다. 같은 `msg_id`이므로 받는 쪽은 한 번만 표시한다. 모든 기기가 같은 결론을 낸다는 시험이 있어야 한다.

### 4.4a 내 다른 기기와 연락처 (사용자 결정)

- 연락처는 지금처럼 기기를 처음 연결할 때만 복사된다. 그래서 PC에서 새로 추가한 연락처가 휴대폰에는 없을 수 있다.
- **내 계정의 다른 기기가 보낸 Welcome은 그 상대를 허용한 것으로 본다.** 휴대폰은 그 대화에 합류하고, 상대를 연락처에 자동으로 추가한다. 사용자가 기기마다 연락처를 따로 추가할 필요가 없다.
- 조건 (설계자 판단): Welcome을 만든 leaf가 **내 계정**의 현재 기기로 검증되고(4.2절), 그룹의 상대 leaf들이 상대 계정의 IdentityRecord로 검증될 때만 이렇게 한다. 상대 계정이 보낸 Welcome만으로는 연락처를 만들지 않는다. 이 경우는 M4의 연락처 허용 규칙(`ContactRequired` 보류)을 그대로 따른다.
- 자동 추가된 연락처의 표시 이름은 비워 두거나 Welcome을 만든 내 기기가 함께 보낸 이름을 쓴다(구현자 판단). 안전번호 확인 상태는 복사하지 않는다.

### 4.5 멤버 변경과 커미터 (설계자 판단)

메일박스(M6)와 시퀀서(M8)가 없으므로 상위 6.1절의 커미터 표를 M5에서는 이렇게 좁힌다.

- **그룹의 어느 멤버 기기든 Add/Remove를 커밋할 수 있다.** 기준은 두 계정의 검증된 현재 기기 목록(4.2절)이다. 목록에 있는데 그룹에 없는 기기는 Add하고, 그룹에 있는데 목록에서 빠진 기기는 Remove한다. 그래서 상대가 오프라인이어도 상대의 새 기기나 해제된 기기를 내 쪽에서 처리할 수 있다. 해제된 기기가 계속 읽게 두지 않기 위해서다.
- 한 기기는 자기가 만든 Commit이 아직 다른 멤버의 수신 확인을 하나도 받지 못했으면 다음 Commit을 만들지 않는다. 연쇄 분기를 줄이기 위해서다.
- **같은 epoch에 Commit이 둘 생기면** 상위 6.1절 규칙대로 `hash(commit)`이 작은 쪽을 채택한다. 진 쪽을 이미 적용한 기기가 되돌릴 수 있도록 **직전 epoch 상태 하나**를 보관한다. 진 Commit에 들어 있던 변경이 여전히 필요하면 이긴 epoch 위에서 다시 커밋한다. 별도의 "확정" 단계는 두지 않는다.
- Commit과 Welcome은 그룹의 **모든 다른 멤버 installation에 개별 전달**하고, 각 installation이 수신 확인할 때까지 재시도한다(5.3절). 오프라인 기기가 Commit을 놓치면 이후 메시지를 풀 수 없기 때문이다.
- 주기적 키 갱신(Update)은 M5에서 하지 않는다. 기기 해제 Commit이 키를 갱신하는 효과는 있다.

### 4.6 재가입 (설계자 판단)

보관한 한 단계로 되돌릴 수 없을 만큼 분기가 깊거나, 보류(4.2절)·누락으로 그룹 상태가 어긋났으면 기기는 되돌리기를 시도하지 않는다. 대신 그 그룹 상태를 버리고 4.4절의 합류 요청으로 **재가입**한다. 새 KeyPackage로 Welcome을 받고, 수신 확인이 없는 메시지를 다시 암호화해 보낸다. 기록은 로컬 DB에 남으므로 잃는 것이 없다. 재가입이 남용되지 않도록 같은 그룹에 대한 재가입 횟수와 간격에 상한을 둔다(값은 구현 계획).

## 5. 보내기·받기

### 5.1 메시지 형식

- MLS 평문 = 상위 7.2절 `ChatMessage`의 M5 부분집합: `msg_id`, `lamport`, `prev_hash`, `sent_at`, `content`, `pad`. `content`는 `Text`와 `Receipt`만 쓴다. 나머지 variant는 디코딩에서 `Custom`으로 폴백하는 규칙만 지킨다. M4 `TextFrame`·`ReceiptFrame`의 의미와 필드 고정값을 그대로 재사용한다.
- 정렬·Lamport·`prev_hash` 규칙은 M4와 같다.
- **패딩:** MLS 암호화 전에 평문을 크기 버킷까지 채운다. 버킷은 1 KiB / 푸시 버킷 / 16 KiB / 60 KiB다. 푸시 버킷은 완성된 MLS 암호문이 2,900 B 이하가 되는 크기다. 정확한 평문 상한은 구현 계획에서 실제 오버헤드를 재서 상수로 고정한다.
- 전송: M4의 인증된 메시지 frame namespace 안에 새 codec(`m5-mls/v1`, `codec = 2`)을 둔다. 봉투 payload는 MLS `MlsMessageOut` TLS 인코딩이다. 상위 7.1절 `Envelope.target`(Queue 등)은 M6/M8에서 쓴다.
- receipt도 MLS로 보낸다. 상대의 KeyPackage 요청·응답, Welcome, Commit, "복호 실패" 응답만 MLS 밖의 인증된 M3 연결 frame이다. 이 프레임들에는 메시지 내용이 없다.

### 5.2 저장과 트랜잭션

- OpenMLS StorageProvider를 같은 SQLCipher DB의 새 `mls_kv` 표로 구현한다. 값은 바이너리로 직렬화한다(JSON 금지, 상위 6.3절 5).
- **메시지 하나를 처리하는 단위가 SQLite 트랜잭션 하나다.** MLS 상태 변화, `message`/`outbox`/`processed_ct`/`receipt_job` 변경이 같은 트랜잭션에서 커밋되거나 함께 롤백된다. OpenMLS는 처리 도중 저장소에 여러 번 쓰므로, 트랜잭션 경계를 우리가 둔다.
- M4 단일 writer(`chat-storage-writer`) 구조를 유지한다. MLS 암·복호와 SQL은 그 writer 안에서 실행한다.
- `processed_ct`: 복호 전에 `SHA-256(MLS 암호문)`으로 중복을 거른다(codec 2). 보낼 때도 자기 암호문 해시를 기록해 되돌아온 자기 메시지를 거른다. 같은 `msg_id`가 다른 암호문으로 다시 와도(재암호화) 논리 키로 한 번만 저장한다.
- 스키마 버전을 올린다. 미래 버전 DB는 구버전 앱이 쓰지 않는다(M4 규칙).

### 5.3 재시도와 전달

- 일반 재시도는 M4 규칙대로 **같은 암호문을 그대로** 다시 보낸다. 재시도마다 새로 암호화하지 않는다(M4 설계 11절).
- 다시 암호화하는 경우는 두 가지뿐이다: 받는 쪽의 "복호 실패" 응답(6절), 동시 생성에서 진 그룹(4.4절). 이때 outbox의 wire를 새 암호문으로 바꾸고, 원문은 수신 확인 전까지 보관한다.
- **전달 범위 (설계자 판단):** 애플리케이션 메시지는 M4처럼 상대의 유효한 기기 하나가 저장하고 receipt를 주면 `전달됨`이다. 연결 가능한 상대의 다른 기기와 내 다른 기기에도 같은 암호문을 보내되, 그 기기들의 전달은 상태 표시에 영향을 주지 않는다. 모든 기기에 빠짐없이 동기화하는 것은 M6이다. 반면 Commit·Welcome은 4.5절대로 모든 멤버에게 수신 확인까지 보낸다.

## 6. 복호 실패의 자동 복구 (사용자 결정 + 설계자 판단)

1. 받는 쪽이 암호문을 풀지 못하면(과거 epoch 범위 밖, 순서 범위 밖, 아직 받지 못한 Commit 이후의 epoch 등) 내용을 저장하지 않고, 인증된 연결로 "복호 실패" 응답을 보낸다. 응답에는 원인 분류와 받는 쪽의 현재 epoch만 담는다. 받는 쪽 화면에는 아무것도 띄우지 않는다.
2. 보내는 쪽은 그 메시지가 아직 수신 확인 전이면 현재 epoch로 다시 암호화해 보낸다. 받는 쪽이 Commit을 놓친 경우가 원인이면 먼저 그 Commit을 다시 보낸다.
3. 같은 메시지의 재암호화 횟수에 상한을 둔다(정확한 값은 구현 계획). 상한을 넘으면 보내는 쪽 메시지가 `전송 실패`가 된다. 사용자가 다시 보내기를 누르면 처음부터 다시 시도한다.
4. 받는 쪽은 실패 응답을 남발하지 않도록 같은 암호문 해시에는 한 번만 응답한다.

## 7. 혼합 버전

- **보내기 (사용자 결정):** M5 기기는 새 메시지를 MLS로만 보낸다. 상대 기기가 M5를 지원하지 않으면(M4 receiver는 알 수 없는 codec에 `UnsupportedVersion` 거부를 돌려준다) 메시지는 `보내기 대기`로 남고, 기존 백오프대로 다시 시도한다. 시간 제한으로 버리지 않는다(M4의 무기한 보관 유지). M5 송신자는 이 거부를 M4 코드와 달리 영구 실패가 아니라 "상대 업데이트 대기" 보류로 다룬다.
- **받기 (사용자 결정: 전환 기간에는 받는다):** M5 기기는 M4 상대가 보낸 평문 Text frame(codec 1)을 지금처럼 받아 저장하고 receipt를 준다. 이미 배포된 M4 코드는 `UnsupportedVersion` 거부를 받으면 메시지를 곧바로 `전송 실패`로 바꾸기 때문에, 거부하면 상대 메시지가 실패로 끝난다. 이 수신 경로는 상대가 M5로 업데이트하면 쓰이지 않는다. 상대의 기기 중 하나라도 MLS로 보낸 뒤에는 그 계정에서 오는 codec 1 Text를 거부할지는 구현 계획에서 정한다(평문으로의 되돌림 공격 방지).
- **receipt:** 업데이트 전에 주고받은 메시지의 M4 Receipt/ReceiptApplied frame은 양쪽 모두 계속 받는다. 이미 전달된 메시지가 `보내기 대기`로 돌아가지 않게 하기 위해서다.
- M5 이전에 이미 저장된 M4 기록은 그대로 둔다.

## 8. M4에서 넘어오기 (사용자 결정)

- `message`의 M4 기록(codec 1로 받은 것과 보낸 것)은 그대로 보존하고 그대로 표시한다. 복사·재암호화하지 않는다.
- `outbox`에 남은 미전송 M4 메시지(codec 1 wire)는 스키마 이관 때 "MLS 승격 대기"로 표시한다. 원문은 `message` 행에 있으므로, 대화 그룹이 준비되면 같은 `msg_id`·`lamport`로 MLS 암호화해 보낸다. 상대가 M4로 이미 받아 둔 메시지라면 상대는 논리 키로 중복을 알아보고 receipt를 다시 준다.
- 이관은 명시적 버전 이관이며, 이관 도중 실패하면 M4 DB 상태로 남는다(M4 이관 규칙과 같은 원자성).
- 취소·실패·보류 상태는 그대로 유지한다.

## 9. 시험과 측정

- **자동(가짜 네트워크):** 기존 chat_core 테스트 네트워크 위에 지연·중복·순서 뒤바뀜·유실을 넣는다.
  - 과거 epoch 5개 이내, 순서 200개 이내로 온 메시지를 모두 받는다.
  - 범위 밖은 6절 자동 복구로 결국 전달된다.
  - 되돌아온 자기 메시지와 재암호화 재전송이 한 번만 저장된다.
- **자동:** 동시 생성과 같은 epoch 이중 Commit에서 모든 기기가 같은 그룹·epoch로 수렴한다.
- **자동:** 기기 추가·해제 후 해제된 기기가 새 메시지를 풀지 못한다. 새 기기가 Welcome 이후 메시지를 푼다.
- **자동:** 메시지 처리 도중 프로세스가 죽어도 MLS 상태와 메시지가 함께 커밋되거나 함께 롤백된다(M4의 crash/restart 시험 방식).
- **자동:** M4 DB를 이관한 뒤 기록이 보이고, 미전송 메시지가 MLS로 전달된다. M4 상대에게는 대기로 남는다.
- **자동:** M4 codec으로 보내는 경로가 없다는 시험. M4 상대의 평문 수신과 업데이트 전 receipt는 계속 받는다는 시험.
- **자동:** 내 다른 기기가 만든 Welcome으로 연락처 없는 기기가 합류하고 연락처가 생긴다. 상대 계정의 Welcome만으로는 연락처가 생기지 않는다.
- **자동:** 그룹 상태 없는 기기(새 기기, 재설치)의 합류, 그룹 둘의 수렴, 깊은 분기 뒤 재가입, 목록에 없는 기기의 보류·재조회.
- **측정:** 1 KiB 암·복호 1 ms 미만(Release, 데스크톱). 메시지당 `mls_kv` 쓰기 바이트 수.
- **플랫폼:** 기존 CI 9개 job을 통과한다. 실제 기기 확인 범위는 구현 계획에서 사용자 승인으로 정한다.

## 10. iOS 알림 확장용 읽기 전용 복호 (사용자 결정: M5에서)

- `chat_core`에 `nse` 기능을 둔다. 저장된 그룹 상태로 암호문 하나를 풀고, **어떤 상태도 저장하지 않는다.** OpenMLS가 복호 중에 하는 쓰기는 메모리 사본에만 남기고 버린다(현재 `chat_nse`와 같은 원칙, 상위 12.3절).
- `chat_nse`는 이 기능을 감싸는 얇은 UniFFI 크레이트로 바뀐다. 상태 파일 형식(`state.rs`)이 남는지, SQLCipher DB를 읽기 전용으로 여는지는 구현자가 정한다. 다만 NSE 메모리 예산(M1b 실측)을 넘지 않아야 한다.
- 이월 6개를 같이 처리한다: 상태 길이 검사와 `with_capacity` 상한, `panic = "unwind"` 유지, NSE 견고성·퍼즈 시험, `fn u32` 이름 변경, 결정적 인코딩 시험 보강, `gen_bindings.sh`의 옛 생성물 삭제.
- M7로 미루는 것: 실제 푸시 수신, 알림 표시, App Group/Keychain 공유 설정, APNs·FCM.

## 11. 제약

- Rust 1.92, FRB 2.11.1, UniFFI 0.32.2, OpenMLS 0.9.0 / openmls_rust_crypto 0.6.0, rusqlite 0.40.2 / libsqlite3-sys 0.38.2(SQLCipher 4.14) 고정을 유지한다.
- 상태는 전부 Rust가 소유한다. Flutter는 기존 이벤트·조회만 쓴다(상위 12절).
- 비밀(키, 평문, 그룹 상태)을 로그에 남기지 않는다.
- M4의 단일 writer, 무기한 outbox 보관, 계정 lifecycle 펜스 규칙을 유지한다.
