- 날짜: 2026-11-06

- 상위 문서: [P2P Chat 설계](2026-10-04-p2p-chat-design.md) 2.2·3·4.5·6.3·11절, [로드맵](../plans/2026-10-04-p2p-chat-roadmap.md) M6, [M5 설계](2026-11-01-m5-mls-1to1-design.md), [M5 결과](../results/2026-11-02-m5-mls-1to1.md) "관찰"·"M6 진입 조건"
- 표기: **사용자 결정**은 이번 대화에서 사용자가 정한 것이다. **설계자 판단**은 설계자가 정했고 사용자가 검토 중에 바꿀 수 있는 것이다. 표시가 없는 것은 상위 문서에 이미 확정된 내용이다.

## 1. 의도

M5까지 메시지는 보내는 기기와 받는 기기가 동시에 연결되어 있어야 전달된다. 받는 쪽이 꺼져 있으면 보내는 기기의 outbox가 들고 있다가 둘이 함께 켜졌을 때 보낸다.

M6은 **내 계정에 연결된 내 다른 기기**(PC, 또는 메일박스로 켠 Android)가 폰 대신 메시지를 받아 두었다가, 폰이 돌아오면 넘겨주게 한다. 서버는 쓰지 않는다. 메일박스 기기는 M5에서 이미 모든 1:1 대화의 MLS 멤버이므로 암호문을 받아 그대로 보관하고 넘기기만 하면 된다. 폰은 넘겨받은 암호문을 자기 MLS 상태로 연다.

성공의 모습 (사용자 결정): 폰이 꺼져 있거나 비행기 모드였다가 다시 켜지면, 그사이 온 메시지가 **알림과 대화창에 기록되어 있다**. Android·Windows가 주 대상이고, iPhone도 설계에서 빠뜨리지 않는다.

맞추기는 **양방향**이다 (사용자 결정). PC가 꺼져 있던 동안 폰으로 주고받은 메시지도 PC를 켜면 PC 대화창에 있다. **읽음 상태도 맞춘다** (사용자 결정). 한 기기에서 읽은 메시지는 다른 내 기기에서도 읽은 것으로 처리하고 알림을 띄우지 않는다. 내가 보낸 메시지의 상대 `읽음` 표시는 어느 내 기기에서 보냈든 내 모든 기기에 보인다.

그래서 M6의 기본 단위는 "메일박스 기기"가 아니라 **내 기기끼리의 기록 맞추기**다. 모든 내 기기가 자기가 받고 보낸 것을 기록해 두고, 내 다른 기기와 연결되면 서로 빠진 것을 가져간다. 메일박스 기기는 이 기능에 더해 늘 켜져 있으려고 애쓰는 기기(트레이 상주, 절전 방지, 상시 연결)일 뿐이다 (설계자 판단).

## 2. 목표·비목표·실패 조건

**목표**

1. 모든 내 기기가 자기가 받아들인 kind 17 frame(App·Commit·Welcome·receipt)과 자기가 보낸 frame을 처리한 순서대로 기록한다(5절).
2. 내 기기 둘이 연결되면 서로 상대 기록에서 빠진 것을 순서대로 가져와 처리해 대화창, 상태, 알림에 반영한다(양방향, 6절).
3. 넘겨받은 암호문을 열 수 없으면 그 메시지를 연 내 기기가 평문 기록을 넘겨 빈칸을 남기지 않는다.
3a. 읽음 상태를 내 기기끼리 맞추고, 이미 읽은 메시지로는 알림을 띄우지 않는다(6.4절).
4. 폰에서 보내지 못한 메시지를 메일박스가 넘겨받아 대신 재시도한다(보내는 방향).
5. Windows: 트레이 상주, 절전 방지, 선택 가능한 자동 시작.
6. Android: 남는 기기를 메일박스로 쓰는 상시 연결 모드(선택).
7. M5에서 넘긴 진입 조건: 여러 기기에 빠짐없이 전달(10절).

**비목표**: 큐 서버와 메일박스 자동 판정(M8), 푸시와 백그라운드 알림(M7), 남의 기기나 서버를 메일박스로 쓰기, iOS를 메일박스로 쓰기, MLS 그룹(M9), 첨부(M10), 새 기기 연결 때 과거 기록 넘김의 사용자 흐름(설계 3.6절. 이번에 만드는 평문 넘김 경로를 나중에 재사용할 수 있다).

**실패 조건** (기술적으로 돌아가도 실패로 본다)

- 폰이 돌아왔는데 메일박스가 받아 둔 메시지가 폰 대화창에 빠져 있다(30일 보관 기간 안에서).
- PC가 꺼진 동안 폰으로 주고받은 메시지가, 두 기기가 다시 연결된 뒤에도 PC 대화창에 빠져 있다.
- 같은 메시지가 두 번 저장되거나 알림이 두 번 뜬다. 다른 내 기기에서 이미 읽은 메시지로 알림이 뜬다.
- 상대가 읽었는데 그 메시지를 보낸 내 기기가 아닌 다른 내 기기에서 `읽음`이 끝내 안 보인다.
- 메시지 순서가 보낸 순서와 다르게 보인다.
- 내 계정이 아닌 기기, 또는 해제된 내 기기가 보관분이나 평문 기록을 받는다.
- 평문 기록이 내 기기끼리의 인증된 채널 밖으로 나간다.
- 평소 쓰는 Android 폰에 고정 알림이 생긴다(사용자가 메일박스 모드를 켜지 않았는데).

## 3. 사용자 결정 (2026-11-06)

| 주제 | 결정 |
|---|---|
| 메일박스가 될 수 있는 기기 | **내 계정에 연결된 내 기기만**. 남의 기기·서버는 아니다 |
| 다시 켜졌을 때 모습 | 그사이 온 메시지가 알림과 대화창에 기록되어 있다 |
| 주 플랫폼 | Android. iPhone도 설계에서 빼지 않는다 |
| 평소 쓰는 Android 폰 | 상시 연결(고정 알림) 없이, PC 메일박스 + M7 푸시에 맡긴다 |
| PC 창 닫기 | 트레이에 남아 계속 받는다 |
| PC 절전 | 켜져 있는 동안 앱이 유휴 절전을 막는다. 노트북은 전원 연결 중에만 |
| 자동 시작 | 설정에서 고른다 |
| 처음 설정 | PC를 처음 연결할 때 화면 하나에 "이 PC를 메일박스로 쓰기"와 "Windows 시작 시 자동 실행"을 보여 주고 둘 다 켠 상태가 기본. 나중에 설정에서 바꾼다 |
| 보관 기간 | 내 기기가 모두 가져갈 때까지, 최대 30일 |
| 열지 못한 메시지 | 메일박스가 평문 기록을 내 기기끼리 넘긴다 |
| 맞추는 방향 | 양방향. PC가 꺼진 동안 폰으로 주고받은 것도 PC에 들어온다 |
| 읽음 | 내 기기끼리 읽음 상태를 맞추고(이미 읽은 것은 알림 없음), 상대의 `읽음` 표시도 내 모든 기기에 맞춘다 |

참고로 사용자는 PC를 밤에 끈다. 그 시간에는 메일박스가 없으므로 지금처럼 보내는 쪽 outbox가 들고 있다. 이 빈틈은 M8(큐)과 M7(푸시)이 메운다.

## 4. 사용자에게 보이는 것

- **폰(수신자)**: 다시 연결되면 그사이 온 메시지가 대화창에 원래 순서로 들어오고, 대화별로 묶인 알림이 한 번 뜬다(설계자 판단: 묶음 알림). 앱이 백그라운드여도 연결된 동안 받은 것은 같은 방식으로 알린다. 앱이 완전히 꺼진 동안의 알림은 M7이다.
- **상대(송신자)**: 내 메일박스가 받았으면 `전달됨`이다. 폰이 꺼져 있어도 그렇다(M5와 같은 규칙: 내 계정의 어느 기기든 받으면 전달됨).
- **읽음**: 폰이나 PC에서 실제로 대화를 열었을 때만 보낸다. 메일박스가 받아 둔 것만으로는 보내지 않는다(설계자 판단). 한 기기에서 읽으면 다른 내 기기들도 맞춰서 읽은 것으로 바뀌고, 그 메시지들의 알림은 뜨지 않거나 이미 떠 있으면 지운다(사용자 결정).
- **PC(다시 켰을 때)**: PC가 꺼진 동안 폰으로 주고받은 메시지가 PC 대화창에 원래 순서로 들어온다(사용자 결정). 폰에서 이미 읽은 것이므로 PC에서 알림은 뜨지 않는다.
- **PC**:
  - 창을 닫으면 트레이에 남는다. 트레이 메뉴는 "열기", "완전히 종료"(설계자 판단).
  - 설정에 "이 PC를 메일박스로 쓰기", "Windows 시작 시 자동 실행" 두 스위치.
  - PC를 처음 내 계정에 연결할 때 두 스위치를 켠 상태로 보여 주는 화면 하나.
  - 메일박스를 끄면 트레이 상주와 절전 방지도 꺼진다. 창을 닫으면 앱이 종료된다(설계자 판단).
- **Android 메일박스 모드(선택)**: 설정의 "이 기기를 메일박스로 쓰기". 켜면 가장 낮은 중요도의 "연결 상태" 고정 알림(상태바 아이콘 없음, 소리 없음)과 배터리 최적화 예외 요청이 나온다. 평소 쓰는 폰에서는 꺼져 있는 게 기본이다.
- **iPhone**: 메일박스가 되지 않는다. 앱이 열려 연결되면 메일박스에서 넘겨받는다.
- 로드맵의 화면 15–21(비공개 UI 목업 아티팩트)은 이 문서의 결정과 다르면 이 문서를 따른다.

## 5. 기기 기록 (`mailbox_store`)

### 5.1 무엇을 기록하나 (설계자 판단)

**모든 내 기기**(메일박스 기능을 켜지 않은 폰 포함)가 다음을 처리한 순서대로 `mailbox_store`에 넣는다. 양방향 맞추기(사용자 결정)에 필요하다.

- 상대 계정에서 와서 **받아들인**(`Ack`한) kind 17 요청 frame: App, Commit, Welcome, receipt. 받은 frame 바이트를 그대로 둔다.
- **이 기기가 보낸** kind 17 frame: 내 App 메시지, 내 receipt, 내 Commit·Welcome. 보낸(봉인한) 시점에 넣는다. 다른 내 기기는 같은 그룹 멤버라 이것을 열 수 있다.
- 내 다른 기기에서 받은 사본(M5 5.3 fan-out)과 동기화로 가져온 항목. 원래 보낸 기기와 원래 frame 그대로 넣는다. 그래야 세 번째 내 기기가 어느 기기에서 가져가도 빠지는 것이 없다.
- 넣지 않는 것: 이 기기가 열지 못해 DecryptFailed(class 1–5)로 답한 frame. 이런 frame은 M5와 똑같이 처리한다. 보낸 쪽이 다시 암호화해 보내고, 그것을 받아들이면 그때 넣는다. 메일박스가 열지 못한 frame을 보관하면 보낸 쪽이 `전달됨`으로 끝내 버려 M5 자동 복구가 돌지 않기 때문이다.

각 항목: 로컬 일련번호(`seq`, 단조 증가, 설계 3.4절), 대화 ID, 원래 보낸 기기(installation), 기록 시각, frame 해시(중복 제거용), frame 바이트. 같은 해시는 한 번만 넣는다.

### 5.2 보관 기간 (사용자 결정)

- 각 기기는 내 다른 기기마다 "어디까지 가져갔나"(`cursor`)를 기록한다.
- 해제되지 않은 내 다른 기기의 cursor가 모두 지나간 항목은 지운다.
- 그래도 받은 지 30일이 지나면 지운다.
- 해제된 기기의 cursor는 바로 지운다. 해제된 기기에는 아무것도 넘기지 않는다.
- 새로 연결된 내 기기의 cursor는 연결 시점의 다음 `seq`에서 시작한다. 과거 보관분을 받지 않는다(과거 기록은 설계 3.6절 범위, 이번 비목표).
- 저장 공간 상한은 두지 않는다(설계자 판단: 하루 1,000통 × 30일 ≈ 45 MB 수준). 구현자가 실제 크기를 재서 결과 문서에 적는다.
- 폰도 같은 규칙으로 기록을 둔다. 폰 기록은 PC가 꺼진 동안의 대화를 PC에 넘기는 데 쓴다.

## 6. 맞추기 (양방향)

### 6.1 프로토콜

설계 3.4절의 `MAILBOX_SYNC_REQ { since_seq }` / `MAILBOX_SYNC_RESP { entries, next_seq }`를 쓴다. 내 기기끼리 InstallationCert로 서로 인증한 세션 위에서만 오간다.

- 내 기기 둘 사이에 세션이 준비될 때마다(연결, 다시 연결, 앱이 앞으로 올 때) **양쪽이 각자** 상대 기록을 자기 cursor부터 요청한다. 메일박스 여부와 관계없다.
- 둘 다 켜져 있는 동안 새로 기록된 항목도 이 경로로 흐른다(새 항목이 생기면 상대에게 "새 항목 있음"을 알리고 상대가 요청한다. 구현 방식은 구현자 몫). M5 5.3 fan-out은 그대로 두지만, 빠짐없음은 이 맞추기가 보장한다.
- 응답은 frame 크기 상한 안에서 여러 페이지로 나눈다.
- 받는 기기는 항목을 `seq` 순서대로 기존 수신 경로(M5 receive_app·Commit·Welcome 처리)에 넣는다. 같은 암호문은 `processed_ct`로 거른다. 그래서 여러 메일박스가 같은 암호문을 넘겨도, 이미 직접 받은 메시지여도 한 번만 저장된다.
- 한 페이지를 다 처리해 저장한 뒤에 다음 요청의 `since_seq`로 cursor를 올린다. 처리 도중 앱이 꺼지면 같은 페이지를 다시 받고 중복은 걸러진다.
- 여러 내 기기가 있으면 각각에서 따로 가져온다. cursor는 상대 기기별이다.
- 처리할 때 frame의 "원래 보낸 기기"는 기록에 적힌 installation이다. 세션 상대 기기가 아니다. 내 메시지(내 다른 기기가 보낸 것)는 M5 사본과 같이 내 보낸 메시지로 저장한다.

### 6.2 순서와 MLS

메일박스는 메시지와 Commit을 받은 순서 그대로 넘기므로, 받는 기기는 Commit 직전 epoch의 메시지를 먼저 처리한 뒤 다음 epoch로 넘어간다. 그래서 오래 꺼져 있었어도 M5의 과거 epoch 한도(5)와 앞쪽 거리 한도(1,000)에 대개 걸리지 않는다.

넘겨받은 항목 처리 중 생기는 복호 실패는 송신자에게 DecryptFailed로 답하지 않는다. 송신자가 보낸 원래 시도는 이미 메일박스가 받아 끝났기 때문이다. 대신 6.3절로 간다.

### 6.3 열지 못한 메시지의 평문 넘김 (사용자 결정)

받는 기기가 넘겨받은 App 항목을 끝내 열지 못하면(예: 그사이 그룹이 새로 만들어짐, 상태가 너무 오래됨) 다음과 같이 한다.

1. 받는 기기가 그 항목의 `seq`(또는 frame 해시)를 넘겨준 기기에 알린다.
2. 넘겨준 기기는 자기가 이미 열어 저장한(또는 자기가 보낸) 그 메시지의 평문 기록을 보낸다. 기록에는 대화, 논리 메시지 키, 보낸 계정과 기기, 보낸 시각, 본문, 종류가 들어 있다.
3. 받는 기기는 그 기록을 원래 메시지와 같은 논리 키로 저장한다. 이미 있으면 무시한다. 대화창에서는 평소 메시지와 구분하지 않는다(설계자 판단).
4. 기록에는 받아들인(연) frame과 자기가 보낸 frame만 있으므로(5.1절) 넘겨준 기기에는 평문이 항상 있다. 그래도 없으면(예: 넘겨준 기기에서 대화를 지움) 그 메시지는 빠지고, 구현자가 그 경우를 결과 문서에 기록한다.

평문 기록은 내 기기끼리 InstallationCert로 인증된 세션 안에서만 오간다. 설계 3.6절은 "별도 대칭키로 암호화"를 말한다. 그 키를 어떻게 정할지는 구현자 몫이다(12절). 이 frame은 MLS 바깥에서 오가므로, 해제된 기기와 내 계정이 아닌 기기에는 절대 보내지 않는다.

평문 넘김으로 저장한 메시지에는 receipt를 보내지 않는다(설계자 판단). 상대는 이미 내 다른 기기에서 `전달됨`을 받았다. 읽음은 6.4절 규칙을 따른다.

### 6.4 읽음 맞추기 (사용자 결정 + 설계자 판단)

- **내가 읽은 것**: 한 기기에서 대화를 읽으면 그 기기는 지금처럼 상대에게 Read receipt를 MLS로 보낸다. 이 receipt는 5.1절에 따라 기록되므로 내 다른 기기들도 맞추기로 받는다. 내 다른 기기는 **내 계정이 보낸 Read receipt**를 "내가 다른 기기에서 읽음"으로 해석한다. 해당 메시지들을 읽은 것으로 바꾸고, 떠 있는 알림을 지우고, 자기는 receipt를 다시 보내지 않는다. M5는 receipt 사본을 버렸는데(`mls_store.rs` receipt copy drop), 이것을 바꾼다.
- **알림**: 맞추기로 들어온 메시지는 같은 페이지(또는 같은 맞추기 묶음)의 내 Read receipt를 먼저 반영한 뒤 알림 여부를 정한다. 이미 읽은 메시지로는 알림을 띄우지 않는다. 한 맞추기 묶음 안에서 메시지 뒤에 내 읽음이 오는 경우를 위해, 묶음을 다 처리한 다음 알림을 한 번에 띄운다(설계자 판단).
- **상대가 읽은 것**: 상대의 Delivered·Read receipt도 5.1절에 따라 기록되고 맞춰진다. 그래서 그 메시지를 보낸 기기가 아닌 다른 내 기기에서도 `전달됨`·`읽음`이 보인다. M5에서 다른 내 기기가 보낸 메시지(사본)는 상태를 추적하지 않았는데, receipt를 받으면 그 사본의 상태도 올린다(되돌리지는 않는다).
- 이 receipt 처리는 내 기기끼리만의 해석이다. 상대 쪽 프로토콜은 바뀌지 않는다.

## 7. 넘기기 — 송신 방향 (설계자 판단)

설계 3.2절과 3.4절의 `MAILBOX_OUTBOX_HANDOFF`다.

- 내 기기에 아직 상대에게 전달되지 않은 outbox 행이 있다. 이 상태에서 메일박스 기기와 세션이 있으면, 그 행의 봉인된 암호문을 메일박스에 넘긴다. 넘기는 때는 앱이 백그라운드로 가거나 꺼지기 직전이다. 메일박스가 연결되는 시점도 포함한다.
- 메일박스는 넘겨받은 암호문을 **그대로** 상대에게 재시도한다. 백오프 상한은 30초다(로드맵). 원래 기기도 계속 재시도할 수 있다. 같은 암호문이므로 받는 쪽이 중복을 거른다.
- **상대 쪽 변경 (프로토콜 변경)**: 지금 M5의 `open_app`은 MLS 송신 leaf가 세션 상대 installation과 다르면 거부한다. M6에서는 송신 leaf가 **세션 상대와 같은 계정의 현재(해제되지 않은) 기기**이면 받아들인다. 메시지 키와 보낸 기기는 세션 상대가 아니라 송신 leaf의 installation으로 기록한다. M5는 아직 배포되지 않았으므로 M5 상대와의 호환은 두지 않는다. 버전 구분 없이 M6 규칙만 쓴다.
- 메일박스가 자기 leaf로 다시 봉인하는 방식은 쓰지 않는다. 메시지 키에 installation이 들어가므로 상대에게 다른 메시지가 되어 두 번 보일 수 있기 때문이다.
- 상대가 `Ack`하면 메일박스가 그 결과를 원래 기기에 알린다(6.1절 맞추기 경로, 또는 연결돼 있으면 바로). 원래 기기는 메시지를 `전달됨`으로 바꾸고 자기 outbox 행을 정리한다.
- 상대가 DecryptFailed로 재암호화를 요구하면 메일박스는 그 행의 재시도를 멈추고 그 결과를 원래 기기에 넘긴다. 다시 암호화는 원래 기기만 한다(M5 상한 3 그대로). 원래 기기가 꺼져 있으면 돌아올 때까지 기다린다.
- 끝내 실패하면 원래 기기에서 `전송 실패`가 되고 재시도 버튼은 그대로 동작한다.

## 8. 메일박스 기기

### 8.1 Windows

- 메일박스가 켜져 있으면 창 닫기(X)가 앱을 끝내지 않고 트레이로 숨긴다.
- 전원 요청 `PowerSetRequest(PowerRequestSystemRequired)`를 잡아 유휴 절전을 막는다. 화면 꺼짐은 막지 않는다.
- 배터리로 돌아가는 노트북에서는 요청을 놓고, 전원이 다시 연결되면 다시 잡는다.
- 사용자가 직접 재우면(덮개, 전원 버튼, 시작 메뉴 절전) 그대로 잔다(설계 3.3절). Modern Standby 중에는 앱이 멈춘다.
- 자동 시작: 스위치가 켜져 있으면 로그인할 때 트레이로 시작한다(창을 띄우지 않음). 구현 방식(레지스트리 `Run` 키 또는 시작 프로그램)은 구현자 몫이다.
- 처음 연결 화면: PC가 기기 연결(M3)을 마친 직후 한 번 보여 준다. 기존 단일 기기 사용자(M6 업데이트 전부터 쓰던 PC)는 업데이트 후 첫 실행 때 한 번 보여 준다(설계자 판단).

### 8.2 Android 메일박스 모드 (선택)

- 앱이 화면에 보일 때만 켤 수 있다. OS가 백그라운드 시작을 막는다(설계 3.3절).
- `remoteMessaging` 포그라운드 서비스 + 별도 알림 채널 "연결 상태"(IMPORTANCE_MIN) + 배터리 최적화 예외 요청을 쓴다.
- 기기가 재부팅되면 사용자가 앱을 열 때까지 꺼져 있다. 부팅 시 자동 시작은 OS 제약상 하지 않는다(설계자 판단).
- Play 배포 시 `remoteMessaging` 사용 신고가 필요하다(로드맵 "사용자 준비").

### 8.3 iOS

메일박스가 되지 않는다. 6절 수신과 7절 송신 인계(앱이 백그라운드로 갈 때)는 그대로 쓴다.

### 8.4 메일박스 알림과 가동률

- **`MailboxAnnounce`**: 메일박스 기능을 켜거나 끈 기기가 내 다른 기기들에 알린다. 받는 기기는 이 정보로 동기화할 상대를 고르고, 앱이 앞으로 올 때 그 기기에 먼저 연결을 시도한다. 연락처에는 알리지 않는다(설계자 판단: 송신자는 M5 fan-out으로 연결된 내 기기 아무 데나 보내므로 알 필요가 없다).
- **7일 가동률**: 메일박스 기기가 자기 가동 시간을 7일 창으로 기록한다. M8의 "메일박스 자동 판정"이 쓸 값이다. M6에서는 기록만 하고 판정하지 않는다.

## 9. 발견과 연결

내 기기끼리는 설계 3.4절과 5.1절대로 찾는다. 주소 캐시, IdentityRecord(DHT), 같은 LAN의 mDNS(iOS는 Bonjour)를 함께 쓴다. 같은 네트워크일 필요는 없다. 다른 네트워크면 직접 연결을 먼저 시도하고, 안 되면 릴레이를 거친다(M2·M4 경로 그대로).

## 10. M5에서 넘긴 진입 조건

M5 결과 문서 "관찰"의 두 가지를 M6 안에서 먼저 고친다.

1. 세션이 없는 MLS 멤버 기기에 Commit·Welcome을 보내야 하면, 그 기기에 연결(dial)한다. 지금은 이미 있는 세션으로만 보내서, 상대 기기가 다시 연결해 올 때까지 대기열에 남는다.
2. `connect_account(peer)`가 그 계정의 다른 기기 세션을 not-ready로 만들지 않게 한다. 지금은 처음 응답한 기기 하나만 다시 인증한다.

메일박스가 늘 연결을 유지하는 기기이므로, 이 둘이 없으면 메일박스로의 Commit 전달이 막혀 6.2절 순서 보장이 깨진다.

## 11. 시험과 측정

로드맵 M6 완료 기준을 따른다.

- 자동(①): 메일박스 보관·cursor·30일 정리·해제 기기 cursor 삭제. 여러 메일박스가 같은 암호문을 넘겨도 한 번만 저장. 일련번호 순서대로 처리. 페이지 중간 종료 후 재개. epoch가 바뀌는 Commit을 사이에 둔 넘김. 평문 넘김(열지 못한 항목 → 기록 저장, 중복 무시, 내 계정 아닌 기기나 해제된 기기로는 거부). 송신 인계 → 메일박스가 전달 → 원래 기기 `전달됨`. 송신 인계 중 재암호화. 10절 두 진입 조건.
- 자동(①, actor 경로): A=[A1 폰, A2 PC 메일박스], B=[B1]. A1이 꺼진 동안 B1이 보낸 메시지를 A2가 보관하고, A1이 돌아오면 원래 순서로 한 번씩 받는다. 알림 이벤트는 대화별로 한 번이다.
- 자동(①, actor 경로, 양방향): A2가 꺼진 동안 A1과 B1이 주고받은 메시지(양쪽 방향)가 A2가 돌아오면 A2에 원래 순서로 들어오고, A1에서 이미 읽은 것은 A2에서 읽음이며 알림이 없다.
- 자동(①, 읽음): A1에서 읽음 → A2의 해당 메시지 읽음, 알림 없음/지움, A2는 receipt를 다시 보내지 않음. A1이 보낸 메시지를 B1이 읽음(A1 꺼짐, A2가 받음) → A1이 돌아오면 `읽음`.
- 자동(①, 송신 인계): 인계된 암호문을 B1이 A2 세션으로 받아들이고, 송신 기기는 A1로 기록된다. 해제된 A 기기나 다른 계정 기기의 leaf로 봉인된 것은 거부.
- 자동(①, 세 번째 기기): A=[A1, A2, A3]. A3는 A1만 연결돼 있던 동안의 대화도 A2에서 가져갈 수 있다(기록이 사본까지 넣으므로).
- 자동(④): 에뮬레이터 비행기 모드 → Windows 앱(메일박스)이 받음 → 비행기 모드 해제 뒤 에뮬레이터가 받음. 에뮬레이터 하나를 상시 연결 모드 메일박스로 둔 경우도 같은 시나리오로 돌린다.
- 기기 확인: 폰 비행기 모드 → PC가 받음 → 폰 복귀 후 같은 LAN에서 5 ms 안팎으로 받음. LTE로 복귀한 경우도 한 번 본다.
- 측정: 메시지당 `mailbox_store` 크기, 1,000건 넘김 시간.

## 12. 구현자에게 맡기는 것

- `mailbox_store`·cursor 표의 정확한 스키마와 v2→v3 이전.
- 동기화 frame의 종류 번호, 페이지 크기, 상대 기기별 cursor 저장 위치, "새 항목 있음" 알림 방식.
- 평문 넘김의 추가 암호화 키를 어떻게 정할지(설계 3.6절 "별도 대칭키"). 인증된 내 기기 세션만으로 충분하다고 판단하면 근거를 결과 문서에 적는다.
- 송신 인계 시점의 정확한 트리거(앱 수명주기 이벤트별)와 인계 대상 행의 기준.
- 묶음 알림의 문구와 Android·Windows 알림 API 사용.
- 트레이·전원 요청·자동 시작의 Windows API 선택.
- 가동률 기록 형식.
