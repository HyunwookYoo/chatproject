## 1. 의도

M6까지는 앱이 돌고 있어야 메시지가 들어오고 알림이 뜬다. 평소 쓰는 Android 폰은 상시 연결을 두지 않기로 했으므로(M6 사용자 결정), 앱이 꺼져 있거나 백그라운드에서 잠들어 있으면 메시지는 PC 메일박스나 보내는 쪽 outbox에 머물다가 폰 앱이 다시 열릴 때 들어온다.

M7은 **앱이 꺼져 있어도 새 메시지가 오면 폰에 곧바로 알림이 뜨게** 한다. 보내는 쪽이 받는 기기마다 푸시를 요청하고, 우리가 운영하는 무상태 푸시 프록시가 FCM(Android)·APNs(iOS)로 전달한다. 암호문이 푸시 버킷(2,900 B 이하) 안이면 푸시에 동봉하므로, 받는 기기는 연결 없이 복호해 보낸 사람과 내용을 알림에 보여 준다.

푸시는 **놓칠 수 있는 깨우기 신호**다(설계 8.3, 스파이크 C). 메시지의 원본은 지금처럼 직접 연결·메일박스·outbox가 책임진다. 푸시가 사라져도 메시지는 잃지 않고, 늦게 올 뿐이다.

성공의 모습: 잠긴 Android 폰과 iPhone에 상대가 보낸 메시지가 보낸 사람과 내용이 담긴 알림으로 1–2초 안에 뜬다. PC에서 그 대화를 읽으면 Android 폰의 알림이 지워진다.

## 2. 목표·비목표·실패 조건

**목표**

1. 서울 VPS에 올릴 무상태 푸시 프록시(`server/push_proxy`)를 만든다. FCM HTTP v1과 APNs(HTTP/2, 인증 키)로 보낸다. 배포 전까지는 이 PC에서 돈다.
2. 받는 기기가 대화마다 PushHandle을 프록시에서 발급받아 MLS 채널로 상대에게 알리고, 만료 전과 토큰이 바뀔 때 갱신한다.
3. 보내는 기기(또는 그 기기의 outbox를 넘겨받은 메일박스)는 직접 전달하지 못한 상대 기기마다 푸시를 보낸다.
4. Android: FCM 수신기가 Flutter 없이 같은 프로세스의 코어를 불러 복호·저장하고 알림을 띄운다. 앱 프로세스가 없을 때도 된다.
5. iOS: 알림 확장(NSE)이 동봉된 암호문을 읽기 전용으로 복호해 알림 문구를 만든다. 15 MB 안에서 돈다.
6. 다른 내 기기에서 읽으면 Android 폰의 알림이 조용한 푸시로 지워진다.
7. 알림 권한은 복구 문구 확인 직후에 묻고, 사용자는 설정에서 푸시를 완전히 끌 수 있다.
8. 이전 마일스톤이 M7로 넘긴 일을 처리한다(10절).

**비목표**: 큐 서버와 메일박스 자동 판정(M8), UnifiedPush(설계 8.4, 선택 기능으로 남긴다), MLS 그룹 대화의 푸시(M9), 첨부 알림(M10), Apple의 알림 필터링 entitlement 신청(설계 8.2. 승인 전에는 차단한 대화의 푸시가 "새 메시지"로 뜬다), 서울 자체 릴레이(M11), 실제 VPS 계약과 운영 자동화(사용자가 VPS를 마련하면 붙인다, 3절).

**실패 조건** (기술적으로 돌아가도 실패로 본다)

- 프록시가 무엇이든 디스크나 외부 저장소에 남긴다(로그 포함, 9.4절).
- 푸시 페이로드에 평문, 보낸 사람의 계정·기기 식별자, 대화 id가 들어간다.
- 같은 메시지로 알림이 두 번 뜬다(푸시와 직접 수신이 겹칠 때 포함).
- FCM 높은 우선순위 메시지를 받고도 보이는 알림을 띄우지 않는 경로가 있다(그러면 FCM이 그 앱을 강등한다, 설계 8.3). 예외는 이미 읽은 메시지 하나다(5.3절).
- NSE가 실패하거나 시간을 넘겼을 때 알림이 아예 사라진다(이때는 "새 메시지"로라도 떠야 한다).
- 푸시를 끈 사용자의 기기가 프록시에 무엇이든 보낸다.

## 3. 사용자 결정 (2026-11-14)

| 항목 | 결정 |
|---|---|
| 범위 | 서버, Android, iOS를 이번에 모두 만든다 (안 B) |
| 구조 | 직접 만든 Rust 프록시가 FCM과 APNs로 각각 보낸다. iOS에 Firebase SDK를 넣지 않는다 (안 A) |
| 서버 | 지금은 VPS가 없다. 개발과 CI는 로컬 프록시로 하고, 실기기 확인 직전에 VPS를 마련한다. 무료 등급(예: Oracle Cloud Always Free 서울 + 무료 서브도메인 + Let's Encrypt)으로 시작할 수 있다 |
| 다른 기기에서 읽었을 때 | Android는 조용한 푸시로 알림을 지운다(폰이 Doze 중이면 몇 분 늦을 수 있다). iOS는 앱이 열리거나 다시 연결될 때 지운다 (안 2) |
| handle 수명과 갱신 | 수명을 7일에서 **30일**로 늘린다(상위 설계 8.1을 바꾼다). Android는 하루 한 번 백그라운드 작업으로 갱신을 확인하고, iOS는 앱을 열 때와 백그라운드 새로 고침 때 확인한다 (안 1 + 2). 대가: 차단한 상대가 handle을 최대 30일 동안 rate limit 안에서 쓸 수 있다 |

## 4. 사용자에게 보이는 것

- **잠긴 폰(수신자)**: 메시지가 오면 대화별로 묶인 알림이 뜬다. 제목은 연락처 별칭, 본문은 메시지 앞부분이다(설계자 판단: 상위 설계와 로드맵의 "내용과 함께"를 따른다. M6의 "새 메시지 N개" 묶음 형식은 유지하고 마지막 메시지 앞부분을 더한다). 암호문이 푸시 버킷을 넘거나 복호하지 못하면 "새 메시지"로 뜬다.
  - Android는 큰 메시지도 수신기가 잠깐 연결해 받아 오면 내용으로 바꿔 띄운다(5.4절). 못 받으면 "새 메시지"로 남는다.
  - 잠금 화면에 내용을 보일지는 OS의 알림 설정을 따른다. 앱이 따로 숨기지 않는다(설계자 판단).
- **알림 누르기**: 그 대화가 열린다(M6과 같다).
- **다른 내 기기에서 읽음**: Android 폰의 그 대화 알림이 지워진다. iPhone은 앱을 열거나 다시 연결될 때 지워진다.
- **보내는 쪽**: 달라 보이는 것이 없다. `전달됨`은 지금처럼 받는 계정의 기기가 실제로 받았을 때만 붙는다. 푸시를 보낸 것만으로는 붙지 않는다.
- **온보딩**: 복구 문구 확인 바로 다음 화면에서 알림 권한을 묻는다(설계 8.6). 이미 온보딩을 마친 기기는 업데이트 후 처음 실행할 때 한 번 묻는다(설계자 판단). 거절하면 푸시를 끈 상태와 같다.
- **설정**: "푸시 알림" 스위치(기본 켜짐). 끄면 이 기기는 프록시에 아무것도 보내지 않고, 대화 상대에게 handle 철회를 알린다. 앱을 열 때만 메시지를 받는다(설계 8.5).

## 5. 받는 쪽

### 5.1 PushHandle 발급

handle은 프록시만 열 수 있는 AEAD 봉투다(설계 8.1). 기기는 프록시 키가 없으므로 **프록시에 발급을 요청한다** (설계자 판단: 상위 설계는 "받는 기기가 발급한다"고만 적었다).

```
POST /handle  { platform: fcm|apns, token, tag }  ->  { handle, expires_at }
PushHandle = AEAD(proxy_key, { platform, token, tag, issued_at, expires_at })
```

- `tag`는 받는 기기가 대화마다 만든 16바이트 무작위 값이다. 그 기기만 tag → 대화를 안다. 같은 대화라도 기기마다 다르다(설계자 판단: 대화 id를 쓰면 프록시가 대화를 계정 간에 이을 수 있다).
- 만료는 30일이다(사용자 결정). 기기는 발급받은 지 7일이 지나면(남은 기간 23일), 그리고 FCM·APNs 토큰이 바뀌면 다시 발급받아 상대에게 알린다(설계자 판단: 7일. 갱신이 몇 번 실패해도 3주의 여유가 남는다).
- 갱신 확인 시점 (사용자 결정):
  - Android: 앱을 열 때, 그리고 하루 한 번 백그라운드 작업(WorkManager 주기 작업, 네트워크 있을 때). 작업은 코어를 시작하고 handle을 다시 발급받아 `System { PushHandle }`을 봉인한다. 상대에게 바로 닿지 않으면 지금처럼 outbox에 두고, 내 메일박스가 있으면 넘긴다(M6 7절). 그 뒤 네트워크를 끈다.
  - iOS: 앱을 열 때, 그리고 백그라운드 새로 고침(`BGAppRefreshTask`) 때. iOS가 실행을 보장하지 않으므로 최선 노력이다.
  - Windows는 푸시를 받지 않으므로 handle이 없다.
- 발급은 rate limit을 받는다(9.3절).
- 프록시 키를 교체하면 이전 handle은 모두 무효가 된다. 프록시는 이전 키 하나를 더 받아 열 수 있게 둔다(설계자 판단).

### 5.2 handle 알리기

- 상대에게: 대화의 MLS 그룹으로 `System { PushHandle { handle } }`를 보낸다. 철회는 같은 메시지에 빈 handle이다. 상대는 (그 대화, 보낸 기기의 leaf)마다 가장 최근 것 하나만 둔다.
  - 이 시스템 메시지는 알림을 띄우지 않고, 상대 화면에 나오지 않으며, 읽음 대상도 아니다.
  - M6 기록(`mailbox_store`)에 남으므로 상대의 다른 기기도 그 handle을 안다. 상대가 어느 기기에서 보내든 푸시할 수 있다.
- 내 기기에게: 읽음 정리 푸시(7절)를 위해 내 Android 기기는 자기 handle 하나(tag는 "내 기기용" 값)를 kind 18 Announce에 실어 내 다른 기기에 알린다.
- 해제된 기기(M3)의 handle은 버린다. 그 기기의 leaf가 그룹에서 빠지면 함께 지운다.

### 5.3 받은 푸시의 페이로드

| 경우 | FCM data | APNs |
|---|---|---|
| 암호문 동봉 | `{ t: tag, e: base64(ct) }`, 높은 우선순위 | `aps.mutable-content: 1`, `aps.alert.loc-key: NEW_MSG`, `t`, `e` |
| 깨우기만 (버킷 초과) | `{ t: tag, w: 1 }`, 높은 우선순위 | `aps.mutable-content: 1`, `aps.alert.loc-key: NEW_MSG`, `t` |
| 읽음 정리 | `{ t: tag, r: 1 }`, **일반 우선순위** | 보내지 않는다 |

- `t`는 handle 안의 tag를 프록시가 꺼내 넣은 것이다. 보내는 쪽은 tag를 모른다.
- `e`는 MLS 암호문에서 **`group_id` 필드를 뺀 것**이다(설계자 판단). MLS PrivateMessage는 `group_id`를 평문으로 싣고, 지금 `group_id`는 대화 id(두 PeerId에서 계산할 수 있는 값)로 시작한다. 그대로 실으면 프록시·Google·Apple이 두 계정에 공통인 대화 id를 본다. 받는 쪽은 tag로 대화를 알므로 `group_id`를 다시 넣어 복호한다. 바이트가 줄 뿐 늘지 않는다. `epoch`는 평문으로 남는다(받아들인다).
- 보낸 사람 정보는 없다(설계 8.5). 보낸 사람은 받는 쪽이 복호해서 안다.
- 높은 우선순위 메시지는 보이는 알림으로 끝나야 하므로 `w`·`e`는 알림을 띄운다. 이미 직접 받아 알렸으면 그 대화 알림을 같은 내용으로 다시 고친다(소리 없이, M6의 `update`).
- **예외: 이미 읽은 메시지.** 다른 기기에서 이미 읽은 메시지면 알림을 띄우지 않는다(M6 사용자 결정 "이미 읽은 것은 알림 없음"과 M6 Ruling 31 "지운 알림은 되살리지 않는다"가 우선한다, 설계자 판단). 폰이 꺼진 동안 PC에서 읽고 폰을 켜면 FCM이 보관했던 푸시가 이렇게 올 수 있다. FCM이 이 앱의 우선순위를 낮출 위험은 받아들이고, 기기 확인에서 지켜본다.
- 읽음 정리(`r`)는 일반 우선순위라 보이는 알림이 필요 없다.

### 5.4 Android 수신기

- `FirebaseMessagingService`(Kotlin)를 둔다. Firebase는 Kotlin 의존성으로만 넣고 Flutter 플러그인은 쓰지 않는다(설계자 판단: 수신기가 Flutter 없이 돈다).
- 앱 프로세스가 없으면 Android가 수신기를 위해 프로세스를 띄운다. 수신기는 Flutter 엔진 없이 **코어를 직접 시작한다**: JNI 네트워크 컨텍스트와 `AccountKeyStore` 초기화(지금 `MainActivity`가 하는 것), `uniffiEnsureInitialized()`(M1a 이월 2), `core_start(storageRoot)`. 이미 Dart가 시작한 코어가 있으면 그것을 쓴다. 나중에 사용자가 앱을 열면 Dart는 이미 돌고 있는 코어에 붙는다(설계자 판단: 지금 `CORE`는 프로세스 하나에 하나다. 두 번째 `core_start`의 동작은 구현자가 확인한다).
- `e`가 있으면: 코어가 tag로 대화를 찾고, 받은 frame처럼 처리한다(복호, 저장, `mailbox_store` 기록, 중복이면 버림). 처리 결과로 알림을 띄운다.
- `w`만 있으면: 코어가 네트워크를 켜고 그 대화 상대 기기와 내 메일박스에 잠깐 연결해 밀린 것을 받는다(M6 pull). FCM이 주는 처리 시간 안에 끝나지 않으면 먼저 "새 메시지" 알림을 띄우고 받은 뒤 고친다. 연결 시도는 짧게 끝내고 네트워크를 다시 끈다(설계자 판단: 상한 20초. 처리 시간이 모자라면 구현자가 짧은 작업으로 넘긴다).
- `onDeletedMessages()`: 다음에 네트워크가 켜질 때 내 메일박스와 모든 대화 상대에게서 다시 받는다(설계 8.3).
- `onNewToken()`: 모든 handle을 다시 발급받아 알린다.

### 5.5 Android 알림은 네이티브가 띄운다 (설계자 판단)

지금은 Dart `Notifier`가 `ChatEvent.notify`를 받아 Kotlin에 알림을 부탁한다. 그래서 Flutter 엔진이 없으면(최근 앱 목록에서 쓸어 없앤 뒤, M6 알려진 한계) 알림이 나오지 않는다. 푸시 수신기도 같은 문제를 겪는다.

M7은 Android에서 **알림을 Kotlin이 코어 이벤트로 직접 띄우게** 바꾼다. 코어가 알림 내용(대화, 별칭, 안 읽은 수, 마지막 메시지 앞부분, 새로 울릴지 고칠지)을 UniFFI 콜백으로 Kotlin에 넘기고, Kotlin이 M6과 같은 채널·id 규칙으로 띄운다. Dart는 Android에서 알림을 띄우지 않는다. Windows는 지금처럼 Dart가 띄운다.

### 5.6 iOS 알림 확장

- **상태 파일**: 앱은 대화의 MLS 상태가 바뀔 때마다(메시지 처리, Commit, Welcome) 그 대화의 `export_snapshot`을 App Group 컨테이너의 대화별 파일에 쓴다. 파일 이름은 tag에서 만든다.
  - 파일 보호 등급은 `NSFileProtectionCompleteUntilFirstUserAuthentication`이다(설계자 판단: 잠긴 폰에서 NSE가 읽어야 하므로 `Complete`는 쓸 수 없다. M5 이월의 "None이 아닌 것"을 만족한다).
  - 대화를 지우거나 그 대화의 handle을 철회하면 파일도 지운다.
  - 별칭과 미리보기 길이 같은 알림 문구 재료도 같은 파일에 넣는다.
- **NSE 처리**(설계 12.3):
  1. `t`로 상태 파일을 찾는다. 없거나 `e`가 없으면 "새 메시지"로 띄운다.
  2. 그 암호문의 해시가 이미 처리한 목록(App Group 파일)에 있으면 같은 대화 알림으로 띄우고 끝낸다.
  3. 읽기 전용으로 복호한다(`chat_nse`). 그룹 상태는 바꾸지 않는다.
  4. 암호문을 App Group의 inbox 파일에 덧붙이고, 별칭과 앞부분으로 알림을 띄운다.
  5. 실패하거나 `serviceExtensionTimeWillExpire`가 오면 "새 메시지"로 띄운다.
- **앱**: 실행될 때와 포그라운드로 올 때 inbox를 순서대로 처리하고 비운다(중복은 `processed_ct`로 버린다). 그때 비로소 그룹 상태가 바뀌고 상태 파일이 새로 쓰인다.
- NSE는 상태 파일이 묵어서(앱이 그사이 처리를 못 해서) 복호하지 못할 수 있다. 그때는 "새 메시지"다. 같은 대화의 메시지가 연달아 오면 둘째부터 복호하지 못할 수 있다. 이것도 받아들인다(설계자 판단. 고치려면 NSE가 상태를 써야 하는데, 앱과 동시에 쓰면 그룹 상태가 깨질 수 있다).
- NSE 빌드에 SQLCipher·OpenSSL이 링크되는 문제(M5 이월)는 M1b 기준(피크 15 MB 미만)을 넘을 때만 고친다.

## 6. 보내는 쪽

### 6.1 누가 언제 보내나 (설계자 판단)

- 메시지를 봉인한 기기가 봉인할 때 한 번 보낸다. outbox가 메일박스로 넘어가도(M6 7절) 메일박스는 다시 푸시하지 않는다. 봉인할 때 이미 보냈고, iOS는 두 번째 푸시를 막을 수 없어 알림이 두 번 뜬다. 그래서 M6 넘기기 형식은 바꾸지 않는다.
- 받는 쪽 메일박스도 받은 것을 폰에 다시 푸시하지 않는다.
- 보내는 시점: 새 메시지(Text)를 봉인하면 상대 계정의 기기 중 **지금 살아 있는 세션으로 바로 전달하지 못한 기기**마다, 그 기기가 알린 handle로 한 번 보낸다. 재시도할 때마다 다시 보내지는 않는다(설계자 판단: 푸시 수는 받는 기기 수, 설계 8.1).
- 보내지 않는 것: 읽음·전달됨 receipt, Commit, Welcome, PushHandle 같은 시스템 메시지(설계 8.3: 조용한 신호는 높은 우선순위로 보내지 않는다).
- 푸시를 끈 기기와 알림 권한이 없는 기기는 아무것도 보내지 않는다. 보내는 쪽으로서의 푸시도 끈다(설계자 판단: 실패 조건 "프록시에 무엇이든 보낸다").

### 6.2 요청

```
POST /push  { items: [ { handle, payload } ... ] }  ->  { results: [ ok | gone | limited | bad ] }
```

- 한 요청에 여러 handle을 묶는다(설계 8.1). 암호문이 푸시 버킷 안이면 `e`를 싣고, 아니면 깨우기만 보낸다.
- `gone`(만료되었거나 열 수 없는 handle)이면 그 handle을 버린다. 다음 handle이 올 때까지 그 기기에는 푸시하지 않는다. FCM·APNs가 토큰 무효를 알리는 것은 지터 뒤라 이 응답에 담기지 않는다(9.2절).
- 실패와 `limited`는 버린다. 푸시는 다시 보내지 않는다(놓쳐도 되는 신호다).
- 프록시 주소는 빌드에 기본값을 넣고 설정으로 바꿀 수 있게 둔다(설계 2.3 BYO의 시작). 디버그 빌드만 `http://`를 허용한다(설계자 판단: VPS 전에는 이 PC의 로컬 프록시를 쓴다).

## 7. 읽음 정리 (사용자 결정 + 설계자 판단)

- 내가 어떤 기기에서 대화를 읽으면(M6 6.4의 `mark_read`), 그 기기는 **지금 세션이 없는 내 Android 기기**마다 그 기기가 알린 내 기기용 handle로 `r` 푸시를 보낸다. 같은 대화를 1초 안에 여러 번 읽으면 한 번으로 묶는다.
- Android 수신기는 `r`을 받으면 코어를 시작해 어느 대화를 정리할지 정한다. 대화를 알려 주는 정보는 푸시에 없다(tag는 "내 기기용" 하나뿐). 그래서 코어가 내 메일박스나 읽은 기기에 연결해 M6 맞추기를 한 번 하고, 그 결과로 알림을 지우거나 고친다. 연결하지 못하면 아무것도 하지 않는다(다음 연결 때 맞춰진다).
  - 설계자 판단: 대화를 푸시에 실으면 프록시가 대화를 알게 된다. 맞추기가 끝나면 상태가 정확히 맞으므로 이쪽을 고른다.
- 일반 우선순위라 Doze 중이면 몇 분 늦게 온다(사용자 결정에서 받아들였다, 스파이크 C S2).
- iOS에는 보내지 않는다. 앱이 열리거나 다시 연결될 때 M6 맞추기로 지운다.

## 8. 알림 권한과 끄기

- 온보딩: 복구 문구 확인 직후 화면에서 묻는다. Android 13 이상은 `POST_NOTIFICATIONS`, iOS는 `UNUserNotificationCenter` 권한과 원격 알림 등록이다. Windows는 묻지 않는다.
- M6이 메일박스를 켤 때 한 번 묻던 경로(`requestNotificationPermission`)는 이 화면으로 옮긴다. "한 번만 묻는다" 표시는 그대로 쓴다.
- 거절, 또는 설정에서 "푸시 알림" 끄기: handle을 모두 철회하고(빈 handle 알림), 토큰을 버리고, 다시 켤 때까지 발급·푸시를 하지 않는다. 앱이 열려 있는 동안의 알림(M6)은 OS 권한이 있으면 그대로 뜬다.
- OS 설정에서 권한을 나중에 끄면, 앱은 실행될 때 권한을 확인하고 위와 같이 처리한다.

## 9. 푸시 프록시 (`server/push_proxy`)

### 9.1 형태 (설계자 판단)

- Rust, axum + tokio, 실행 파일 하나(로드맵 5절 제안). 작업 공간의 새 crate. 봉투 형식과 요청 타입은 코어와 서버가 함께 쓰는 작은 crate로 나눈다.
- 설정은 환경 변수와 비밀 파일 경로뿐이다: 리슨 주소, 프록시 키(현재·이전), FCM 서비스 계정 JSON, APNs 인증 키(.p8)·키 id·팀 id·번들 id, APNs 환경(sandbox|production).
- TLS: 배포 때는 앞에 둔 리버스 프록시(Caddy 등, Let's Encrypt 자동)가 맡는다. 프록시 자체는 평문 HTTP로 localhost에 리슨한다(설계자 판단: 인증서 갱신을 프록시 코드에 넣지 않는다).
- 배포 전 개발: 이 PC에서 실행한다. 보내는 기기는 `/push`로, 받는 기기는 `/handle`로 프록시에 닿아야 한다(PC 앱은 localhost, 에뮬레이터는 `10.0.2.2`, 같은 Wi-Fi의 디버그 빌드 폰은 이 PC의 LAN 주소).
- `http://`는 디버그 빌드만 쓸 수 있고, iOS는 ATS 때문에 `https://`만 된다. 그래서 **iPhone 확인과 릴리스 빌드의 실제 푸시 확인은 VPS(TLS)가 생긴 뒤에 한다**(설계자 판단: 릴리스에 http 예외를 두지 않는다). VPS 전의 CI는 가짜 프록시·가짜 푸시로 시험한다(11절). M1a 이월 1(릴리스 빌드의 Kotlin→Rust 호출)은 가짜 푸시를 수신기에 넣어 확인하므로 VPS가 필요 없다.

### 9.2 동작

- `/handle`: 요청 형식을 검사하고 봉투를 만들어 돌려준다. 토큰이 진짜인지는 확인하지 않는다(그 대가는 rate limit이 막는다).
- `/push`: 각 handle을 열어(만료거나 열 수 없으면 `gone`) 결과를 바로 돌려주고, 0–3초 지터(설계 8.5) 뒤 FCM·APNs로 보낸다. 보내는 쪽은 지터와 발송을 기다리지 않는다(설계자 판단).
- FCM `UNREGISTERED`·APNs `410`은 보낸 쪽에 알리지 않는다(설계자 판단: 상위 설계 8.1의 "프록시가 보낸 쪽에 알린다"를 뺀다). 받는 기기는 토큰이 바뀌면 스스로 새 handle을 알리고(`onNewToken`, APNs 등록), 죽은 handle은 길어야 30일 안에 만료된다. 그동안의 푸시는 FCM·APNs에서 버려진다. 프록시는 그 결과를 로그의 결과 코드로만 센다.
- FCM: 서비스 계정으로 OAuth 토큰을 받아 메모리에 두고 만료 전에 갱신한다. APNs: 인증 키로 JWT를 만들어 HTTP/2 연결 하나를 유지한다. 스파이크의 `apns-probe` 발송 코드를 가져오면 M1b 이월 7의 흠을 함께 고친다.
- 크기: 페이로드는 각 서비스의 문서상 한도 4,096 B를 넘지 않는다(스파이크 C S4). 넘는 요청은 `bad`로 거절한다.

### 9.3 남용 방지

- handle마다 rate limit(설계자 판단: 분당 60, 순간 20). 발급은 보낸 IP마다(분당 30).
- 카운터는 프로세스 메모리에만 있고 재시작하면 사라진다(설계 8.1: 무상태 원칙에 어긋나지 않는다).
- 요청 크기 상한(64 KiB)과 한 요청의 item 상한(100).

### 9.4 무상태와 로그

- 디스크에 쓰는 것이 없다. 비밀 파일은 읽기만 한다.
- 로그에는 시각, 경로, 결과 코드, item 수, 걸린 시간만 남긴다. 토큰, handle, tag, 페이로드, 보낸 IP는 남기지 않는다(설계자 판단: 설계 8.1의 "프록시가 아는 것"을 늘리지 않는다. IP는 rate limit에 메모리로만 쓴다).
- 재시작한 프록시는 이전 상태 없이 같은 handle을 열 수 있어야 한다(키만 같으면 된다).

## 11. 시험과 측정

**자동 (CI)**

- 프록시 단위: 봉투 왕복, 다른 키·만료·변조 거절, 이전 키 허용, rate limit, 지터 범위, 크기·item 상한, 재시작 뒤 같은 handle을 연다, 로그에 금지 항목이 없다.
- 프록시와 가짜 FCM·APNs: 시험 안에서 띄운 가짜 HTTP 서버로 요청 모양(헤더, 우선순위, `mutable-content`, 페이로드 키)을 확인하고, `UNREGISTERED`·`410`을 받아도 프록시가 상태를 남기지 않는지 본다.
- 코어: handle 발급·7일 갱신·30일 만료·철회·토큰 변경, Android 주기 작업이 앱 없이 갱신을 봉인하고 outbox·메일박스로 넘기는 것, 직접 전달하지 못한 기기에만 푸시, 시스템 메시지는 푸시 안 함, 푸시와 직접 수신이 겹쳐도 알림 한 번, `e`·`w`·`r` 처리, `onDeletedMessages` 뒤 맞추기, 푸시를 끄면 프록시 요청 0.
- `group_id`: 페이로드의 `e`에 대화 id가 들어 있지 않고, 받는 쪽이 다시 넣어 복호한다(Android 경로와 `chat_nse` 모두).
- 크기: 푸시 버킷 암호문(이미 `push_bucket_ciphertext_fits_2900`)을 실은 실제 FCM·APNs 페이로드 JSON이 4,096 B 이하.
- Android 통합(에뮬레이터, 지금 CI): 가짜 푸시를 수신기에 직접 넣는다(시험 hook. 실제 FCM 없음). 앱 프로세스가 없는 상태에서 알림이 뜨고 대화가 저장되는지, 릴리스 APK로도 되는지 본다.
- iOS: NSE 빌드·포함 확인(지금 CI). 상태 파일 쓰기·지우기·보호 등급은 앱 쪽 단위 시험. `simctl push`는 NSE를 실행하지 않으므로(자동 시험 설계 6절) NSE 복호 경로는 Rust 시험(`chat_nse`)과 기기 확인으로 본다.

**실제 FCM (선택, 밤마다)**: Network E2E에 Google Play 이미지 에뮬레이터 작업을 하나 더해, 러너에서 로컬 프록시를 띄우고 실제 FCM으로 보낸다(설계자 판단: 로드맵은 "이 PC의 에뮬레이터에서만"이었지만, 이 PC에서 창이 뜨는 시험을 돌리지 않기로 했으므로 CI로 옮긴다). Firebase 서비스 계정을 저장소 시크릿에 넣어야 한다.

**기기 확인 (마지막, 사용자)**

- 잠긴 Android 폰(앱을 쓸어 없앤 상태 포함)과 iPhone에 내용이 담긴 알림이 뜬다. 지연을 잰다.
- PC에서 읽으면 Android 폰 알림이 지워진다.
- 큰 메시지(버킷 초과)가 Android에서 내용으로 바뀌고, iPhone에서는 "새 메시지"로 뜬다.
- iPhone NSE 피크 메모리가 15 MB 미만이다.
- M6에서 미룬 3대 시나리오(폰 끔 → 친구가 보내고 끔 → 폰 켬)를 함께 본다.

## 12. 구현자에게 맡기는 것

- 프록시 HTTP 경로·오류 형식·설정 이름, 공유 crate 이름.
- `System { PushHandle }`의 정확한 인코딩과, M6 기록·맞추기에서의 취급(알림·읽음 대상에서 빼기).
- 두 번째 `core_start`(수신기가 먼저 시작한 코어에 Dart가 붙기)를 지금 구조에서 어떻게 할지.
- Android 수신기의 처리 시간 관리(FCM 처리 시간 안에서 할지, 짧은 작업으로 넘길지).
- iOS 상태 파일과 inbox 파일의 형식, 처리한 암호문 목록의 크기 상한.
- 알림 문구의 미리보기 길이(지금 NSE는 48바이트).
- 가짜 푸시 시험 hook의 모양.

## 13. 사용자 준비

- **Firebase**: 운영용 프로젝트(또는 스파이크 프로젝트 재사용)와 Android 앱 등록, `google-services.json`(비밀이 아니므로 저장소에 넣는다, 설계자 판단), 새 서비스 계정 키. 새 키를 만들면 스파이크 키를 지운다(로드맵).
- **Apple**: 기존 APNs 인증 키(.p8)를 로컬 프록시에서도 쓸 수 있게 둔다. 앱 App ID에 Push Notifications 기능, App Group은 M1b 것을 쓴다.
- **수출 규정 답**: `ITSAppUsesNonExemptEncryption` 값(M1b 배포 1).
- **VPS** (실기기 확인 직전): 서울 리전 VPS 1대, 도메인 또는 무료 서브도메인. 그때 최신 무료 등급 조건을 다시 확인한다.
