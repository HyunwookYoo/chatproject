# 스파이크 A 결과 — 연결 성립과 직접 연결 비율

설계 문서 §5, §17 #3, §18의 스파이크 A다. 도구와 실행 방법은 [README.md](README.md)에 있고, 원본 JSON은 `results/` 아래에 있다.

## A1. 집 회선 PC ↔ KT LTE 폰 (2026-10-04)

### 환경

| 항목 | 값 |
|---|---|
| PC | Windows 11, 유선 이더넷, 가정 회선(Port-Restricted Cone NAT, IPv6 없음 — 분석 문서 §1.2) |
| 폰 | Galaxy Z Fold8 (SM-F971N), Android 17, KT LTE, Wi-Fi 끔 |
| 폰 네트워크 | IPv4는 CLAT `192.0.0.8`을 거친다(464XLAT, 즉 KT LTE는 IPv6 전용 + NAT64). 전역 IPv6 주소도 있다 |
| 릴레이 | n0 공개 릴레이, 싱가포르 `aps1` |
| 방식 | 매번 새 키로 콜드 연결. `--relay-only`(릴레이 URL만으로 dial, 실제 조회 방식과 같음) 5회 + 전체 티켓 1회, 방향마다. 연결 뒤 64 B 핑 20개(200 ms 간격) |

### 결과

| 방향 | 직접 연결 | 연결 성립(릴레이) | 직접 경로 전환 | 직접 RTT p50 / p95 | 릴레이 QUIC RTT |
|---|---|---|---|---|---|
| 폰(LTE)이 PC에 dial | **6/6** | 189–205 ms | 499–577 ms | 46–53 ms / 57–85 ms | 186–208 ms |
| PC가 폰(LTE)에 dial | **6/6** | 207–463 ms | 531–773 ms | 100–113 ms / 190–352 ms | 203–312 ms |

- **12번 모두 직접 연결로 넘어갔다.** 직접 경로는 IPv4였다. 폰은 KT NAT64를 거친 공인 주소(`39.7.x.x`)로, PC는 집 공인 주소로 연결됐다.
- 폰 쪽 공인 매핑 포트가 여러 번의 연결 내내 같았다. KT의 NAT64가 목적지와 상관없이 같은 매핑을 쓴다는 뜻이고(endpoint-independent mapping), 그래서 홀펀칭이 된다.
- IPv6는 쓰이지 않았다. 집 회선에 IPv6가 없어서다.
- 폰이 받기만 하는 방향(PC가 dial)에서 RTT가 약 2배였다. LTE 무선 구간의 절전 대기(DRX)로 보이지만 검증하지 않았다.

### 설계에 주는 의미

- 한국 이동통신(KT LTE) ↔ 가정 회선 조합에서는 직접 연결이 된다. 다만 회선 1개, 통신사 1곳, 12회 표본이다. 다른 통신사(SKT, LG U+)와 LTE ↔ LTE는 아직 재지 않았다.
- 모든 새 연결이 싱가포르 릴레이를 거쳐 시작하므로, LTE에서 첫 연결에 0.2–0.46초, 직접 경로 전환까지 0.5–0.77초가 걸렸다. 서울 릴레이로 바꾸면 이 시간이 크게 줄어든다(서울 왕복 4.4 ms, LTE 직접 RTT 약 50 ms 기준).

## 남은 측정 (2026-10-04 보류)

- **A2. LTE ↔ LTE**: PC를 iPhone 핫스팟에 붙이고(이더넷 분리) Android 폰(KT LTE)과 잰다. iPhone의 통신사에 따라 같은 통신사 / 다른 통신사 조합이 된다.
  - Git Bash에서 `bash scripts/wait-hotspot-then-run.sh`를 띄워 두고 핫스팟으로 바꾸면 자동으로 잰다. 폰은 USB로 연결해 둔다.
  - A1을 다시 재려면 `bash scripts/pc-home-vs-phone-lte.sh`를 쓴다. 두 스크립트 모두 끝나거나 실패하면 폰의 Wi-Fi를 되돌린다.
- SKT, LG U+ 회선은 장비가 생기면 잰다.
