# 스파이크 C (FCM) 결과

설계 문서 §8.3, §18의 스파이크 C 중 FCM 부분이다. 실행 방법은 [README.md](README.md)에 있다.

## 환경

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-04 |
| 기기 | Android 에뮬레이터 `sdk_gphone64_x86_64`, Android 16 (SDK 36), Google Play 이미지 |
| Play services | 26.26.34 |
| 네트워크 | 호스트 PC의 가정 회선 (한국). 에뮬레이터는 QEMU NAT를 거친다 |
| 앱 대기 버킷 | 10 (active) |
| Firebase 프로젝트 | `fcm-probe-project` |
| 발송 | 이 PC에서 FCM HTTP v1 (서비스 계정), 보낼 때마다 300 ms 간격 |

## S1. 켜져 있는 기기의 전달 지연

20통, 높은 우선순위, 데이터 3,900 B(푸시 버킷: base64 3,868 B + `seq`·`sent_ms`).

| 항목 | 값 |
|---|---|
| FCM 수락 | 20/20 (HTTP 200, 요청당 102–230 ms) |
| 수신 | 20/20, 누락 없음 |
| 지연 (발송 직전 → 앱 수신, 시계 보정) | p50 170 ms, p95 255 ms, 최대 490 ms(첫 통), 최소 131 ms |
| 우선순위 | 20통 모두 high로 도착 (강등 없음) |

지연에는 FCM HTTP 요청 시간(약 100–230 ms)이 포함된다. 시계 차이(기기 − PC = −286 ms)는 보정했다.

## S4. 페이로드 크기 한도

| 데이터 크기 (키+값) | JSON 크기 | 결과 |
|---|---|---|
| 3,900 B | 3,919 B | HTTP 200, 수신 |
| 4,000 B | 4,019 B | HTTP 200 |
| 4,077 B | 4,096 B | HTTP 200 |
| 4,096 B | 4,115 B | HTTP 200 |
| 4,200 B | 4,219 B | HTTP 200, 수신 |
| 4,500 B | 4,519 B | HTTP 200, 수신 |
| 4,600–4,900 B | — | HTTP 200 |
| 5,000 B 이상 | — | HTTP 400 `INVALID_ARGUMENT` "Message is too large. The maximum is 4K (4096 bytes)." |

- 문서상 한도는 4,096 B인데, 실제로는 4,900 B까지 받고 5,000 B부터 거절했다. FCM이 크기를 세는 방식이 우리 계산과 다르거나 여유를 두는 것으로 보인다.
- **설계는 문서상 한도 4,096 B를 기준으로 유지한다.** 문서화되지 않은 여유에 기대지 않는다. 푸시 버킷(데이터 약 3,900 B)은 문서상 한도 안에 들어간다.

## S2. Doze — 높은 우선순위와 일반 우선순위

`dumpsys deviceidle force-idle`로 깊은 Doze(IDLE)에 넣고, 화면을 끄고, 배터리 연결을 끊은 상태로 쟀다.

| 단계 | 결과 |
|---|---|
| Doze 중 높은 우선순위 10통 | 10/10 수신. p50 179 ms, p95 330 ms. 강등 없음 |
| Doze 중 일반 우선순위 10통, 5분 대기 | 0/10. 5분 뒤에도 기기는 IDLE |
| Doze 해제(`unforce`) 직후 | 일반 우선순위 10통이 해제 후 약 1초 안에 모두 도착. 보낸 지 약 303–305초 뒤 |

일반 우선순위는 Doze가 끝날 때까지 미뤄질 뿐 버려지지는 않는다.

## S3. 꺼진 기기의 보관 개수

비행기 모드 + Wi-Fi·데이터 끄기(핑 실패로 확인) → 1분 대기 → 높은 우선순위로 N통 발송(200 B) → 다시 연결 → 2분 대기.

| 꺼진 동안 보낸 수 | 다시 연결한 뒤 받은 수 | `onDeletedMessages` |
|---|---|---|
| 100 | 100/100 (보낸 시점부터 5.6–33 s) | 없음 |
| 101 | **0/101** | 호출됨 |
| 150 | **0/150** | 호출됨 |

Firebase 문서 그대로다. **꺼진 동안 100통을 넘으면 보관분이 전부 버려지고**, 앱은 `onDeletedMessages()`로만 그 사실을 안다.

## S5. 밀어 닫기 vs 강제 종료

| 상태 | 결과 |
|---|---|
| 프로세스만 종료(`am kill`, 밀어 닫기와 같은 효과, `stopped=false`) | 5/5 수신. p50 223 ms, 최대 811 ms(프로세스 시작 포함) |
| 강제 종료(`am force-stop`, `stopped=true`) | 0/5. Play services 로그에 `result=CANCELLED` |
| 강제 종료 상태에서 보낸 뒤 앱을 다시 실행 | 5통 중 1통만 도착. **나머지 4통은 사라짐** |

강제 종료된 앱에 온 FCM 메시지는 미뤄지는 게 아니라 대부분 버려진다. 일부 제조사는 최근 앱 목록에서 밀어 닫는 것을 강제 종료처럼 다루므로 실제 폰에서 다시 확인한다.

## 설계에 주는 의미

- 앱은 FCM을 "놓칠 수 있는 깨우기 신호"로 다뤄야 한다. 아래 세 경우에 메시지가 사라진다.
  - 꺼진 동안 100통을 넘었을 때
  - 앱이 강제 종료 상태일 때
  - 일반 우선순위 메시지가 Doze에 걸렸을 때(사라지지는 않지만 늦게 온다)
- 그래서 실행될 때와 `onDeletedMessages()`를 받았을 때 메일박스·큐·상대에게서 다시 받는 흐름이 꼭 필요하다(설계 8.3절).
- 채팅 메시지는 높은 우선순위로 보낸다. Doze 중에도 1초 안에 도착했다.

## S1 실제 폰 (Galaxy Z Fold8 SM-F971N, Android 17, 2026-10-04)

20통, 높은 우선순위, 데이터 3,900 B. 앱 대기 버킷 10(active), 시계 차이 −849 ms를 보정했다.

|---|---|---|---|
| 집 Wi-Fi | 20/20 | 183 / 344 / 380 ms | 모두 high |
| KT LTE | 20/20 | 211 / 529 / 551 ms | 모두 high |

## S5 실제 폰 — 최근 앱 목록에서 밀어 닫기 (Galaxy Z Fold8, Android 17)

사용자가 최근 앱 목록에서 앱을 직접 밀어 닫은 뒤 쟀다.

| 항목 | 결과 |
|---|---|
| 밀어 닫은 뒤 상태 | `stopped=false`. 프로세스는 남아 있었다 |
| 높은 우선순위 5통 | 5/5 수신. p50 352 ms, 최대 414 ms |
| `result=CANCELLED` | 없음 |

이 기기에서는 밀어 닫기가 강제 종료로 처리되지 않는다. 다른 제조사는 다를 수 있다.
